# v2.7.10 (2026-04-21)

## Bug 修复（v2.7.7c 补丁并入源码）

- [BUG-001] 扫码器设备类型 text_lon 对现场 WMax 固件完全无效
  - 症状: 数据库里历史 ScannerDevice.device_type='text_lon' 的记录，连上后发 ASCII 'LON\r\n' 到 55256，现场 WMax 扫码器根本不响应，前端显示"已连接"但永远扫不到码
  - 根因: ScannerPanel.vue 默认值从 text_lon 改到 auto 了，但老数据库的记录没迁移；_start_device 又没做自动升级
  - 修复: `_start_device` 检测到 `text_lon` 自动升级为 `auto`（走 WMax 三端口协议），并调用新增的 `_trigger_wmax_discover_once` 合并触发一次 UDP 发现 + 激活 RPT 上报
  - 影响文件: backend/services/scanner.py

- [BUG-002] WMax 扫码器现场不识别（trigger_scan/测试按钮都无效）
  - 症状: 现场扫码器连上 CMD 端口后，trigger_on/off 发命令不报错但扫码器一动不动；测试按钮走 flash_and_scan 5 秒闪光后完全没扫到码
  - 根因: v2.7.7 正式版为避免"灯一直闪"误判，把连接后的 `activate_rpt_reporting` 去掉改成 ondemand 触发式。但现场 WMax 固件根本不响应单次 Trigger 命令，只认"常开 RPT 上报"模式（这是官方 IDManager 抓包验证的行为）
  - 修复:
    1. `wmax/manager.py::auto_discover_and_connect` 两处（UDP 发现 + 已知设备恢复）连接成功后统一 `await dev.activate_rpt_reporting()`
    2. `scanner.py::_auto_discover_wmax_bg` 里"数据库已知 IP 直连"分支加 `_activate_rpt_once` 激活
    3. 新增模块级 `_rpt_activated_devs` 集合 + `_activate_rpt_once` 单次激活（按 `id(dev)` 去重，通过 `dev.on_disconnected` 钩子自动清理缓存，dev 重连时会重新激活）
    4. 新增 `_ensure_wmax_connected(ip, cause)` 在 `_wmax_trigger` / `test_connection` 入口检查连接、断开时自动重连并重新激活
    5. `test_connection` 的 WMax 分支改成 `activate_rpt_reporting + 收码 5s`（临时 tap 掉 `on_code_received` 采集，结束恢复），替换原本在现场扫不到码的 `flash_and_scan`
  - 影响文件: backend/services/scanner.py, backend/services/wmax/manager.py

- [BUG-003] 容器模式同一 label 跨帧累积超额误判 NG
  - 症状: 期望 1 根 pillar 的容器，实际现场只有 1 根；但 ByteTrack 在遮挡或重新出现时会给同一物体分配新 track_id，`items_ever_seen` 按 unique track_id 累加，`item_class_counts[pillar]` 变 2 > 期望 1 → 结账时标记 NG
  - 根因: v2.7.4 已加帧内 top-N 合并（同一帧超过 N 个时压成 N 个 track_id），但帧间累计那层没有上限，跨帧遮挡/重现仍会超额
  - 修复: `_update_container_grouping` 读 `steps_config` 生成 `max_recognized_per_label`，新 track_id 进入 box 前先看本 box 里该 label 已到上限没；到上限则只刷新最早那条的 `last_seen`（避免被误判 gone），不增加计数
  - 影响文件: backend/api/source.py

# v2.7.3 (2026-04-19)

本次发版核心是**共享报警灯**新功能（多工位共用一个物理报警灯 + 优先级合成），同时修复双工位 TensorRT 推理 imgsz 不传播、报警灯停检测/关软件不熄灭、扫码器重复保存等若干 v2.7.2 遗留问题。

## Bug 修复

- [BUG-001] 双工位 TensorRT 推理报 `input size 640x640 not equal to max model size 960x960`，导致检测无反应
  - 症状: 单工位下 `.engine` 模型推理正常；切到双工位（或多工位）后立刻报 AssertionError 且画面卡住、无检测结果
  - 根因:
    1. `source.py: load_model()` 从 `.engine` 读 `imgsz` 时，AutoBackend 还未实例化，落到默认 640
    2. `channel_manager.py` 的"缓存命中"和"模型共享"路径**没有**把 owner 通道的 `_model_imgsz / _is_native_pytorch / model_task / _original_pt_path` 复制到新通道，导致新通道用了 owner 的 model 对象但元数据是默认值
  - 修复:
    - `source.py` 新增 `_read_engine_metadata_imgsz(engine_path)`：直接打开 `.engine` 文件，解析头部 JSON metadata 拿 `imgsz`（不依赖 AutoBackend）
    - `load_model()` 优先调用上述函数；后续在 warm-up 完成后再做一次"从 `self.model.predictor.model.imgsz` 反向校正"作为兜底
    - `channel_manager.py` 三处（`load_model_for_channel` / `load_shared_model` / `_propagate_model`）增加属性传播
  - 影响文件: `backend/api/source.py`, `backend/api/channel_manager.py`
  - 验证: mock 单元测试 4 用例通过；**真机端到端需用户在双工位机器实测一轮**

- [BUG-002] 报警灯：检测停止/关闭软件后灯仍亮，副机检测时灯不亮
  - 症状:
    - 主机（双工位）：设置"工作指示灯常亮"，检测时正常亮，**点停止检测后不灭**，关闭软件后仍亮
    - 副机（单工位）：相同设置，**检测开始后灯不亮**，但手动测试灯和串口都正常
  - 根因:
    1. 前端"停止检测"实际调的是 `pause()` 而不是 `stop_detection()`，但 `pause()/standby()` 没调 `alarm_router.stop_idle_light()`
    2. `resume()/resume_inference()` 也漏调 `alarm_router.start_idle_light()`，导致暂停-恢复后灯不亮
    3. Electron 关机流程的 `shutdown_step("stop_detection")` 直接改 `is_detecting` 标志，绕过完整 stop_detection 逻辑；shutdown 末尾也未遍历所有 channel 的 alarm 做 `all_off + disconnect`
    4. `start_idle_light()` 多个静默 return（idle_light.enabled=False / alarm.enabled=False / 串口未连 / 协议不支持颜色），现场难排查为什么"检测了但灯没亮"
  - 修复:
    - `source.py`: `pause() / standby()` 加 `alarm_router.stop_idle_light(channel_id=self.channel_id)`；`resume() / resume_inference()` 加 `alarm_router.start_idle_light(channel_id=self.channel_id)`
    - `main.py`: `shutdown_step("stop_detection")` 改为遍历 `channel_manager.channels` 调用每个 `mgr.stop_detection()`；`shutdown_step("cleanup")` 与 `cleanup_on_exit()` 改为遍历 `alarm_router.managers` 调 `all_off + disconnect_all`
    - `alarm.py`: `start_idle_light()` 每个 silent return 都改成 `print(...)` 打印具体原因（idle_light 未启用 / alarm 未启用 / 串口未连 / 协议不支持颜色 / 写串口失败）
  - 影响文件: `backend/api/source.py`, `backend/api/alarm.py`, `backend/main.py`

- [BUG-003] 扫码器允许同 IP+端口重复保存到设备列表
  - 症状: 同一台扫码器在「自动发现」面板点了「保存到设备列表」后，再次点击会再保存一条；手动添加也不去重，UI 列表出现多条同 IP 的设备
  - 根因: `POST /scanner/devices` 和 `PUT /scanner/devices/{id}` 都没做 IP+port 唯一性校验；前端 `handleSave / addDiscoveredToDb` 也没本地查重
  - 修复:
    - `scanner.py: create_device()` 创建前查 IP+port，已存在 → 返回 **409** + 中文 detail（带占用方设备名和 ID）
    - `scanner.py: update_device()` 改 IP/port 时检查目标地址是否被其他设备占用；不改 IP 不会误判
    - `ScannerPanel.vue: handleSave()` 提交前本地查重（更快反馈）；`addDiscoveredToDb()` 打开"添加表单"前先查重，已存在直接 ElMessage.warning 不打开
    - 自动发现的临时 WMax 设备（id < -900，标记 `_auto`）不参与去重，避免误伤
  - 影响文件: `backend/api/scanner.py`, `frontend/src/views/MES/ScannerPanel.vue`
  - 验证: 端到端测试 7 用例通过（创建重复 / 同 IP 不同端口 / 改 IP 撞别人 / 改名不误判 / 改成新地址）

## 功能变更

- [FEAT-001] 共享报警灯：一个物理报警灯多工位共用 + 优先级合成（核心新功能）
  - 需求: 现场有客户只能装一根灯柱，但有多个工位（典型双工位主机）；旧方案两个 channel 配同一个 `port` 会抢串口失败、行为异常
  - 实现:
    - **配置层**: `alarm_config.json` 在 owner 通道下加可选字段：
      - `shared_with: [1, 2, ...]` — 共享给的工位号（不含自己）
      - `priority_order: ["ng", "warn", "ok", "idle"]` — 4 个事件类别的合成优先级
      - `event_priority_map: {event1: "ok", event2: "ng", ...}` — 项目事件名 → 优先级类别
    - **AlarmManager**: 新增 `_shared_channels / _channel_states / _priority_order / _event_priority_map / _current_visual / _state_lock`；新增 `set_shared_mode() / is_shared() / _recompose_and_apply() / _apply_event_visual() / _apply_idle_visual()`；`trigger_alarm / start_idle_light / stop_idle_light` 拆为 `_solo` 和 `_shared` 两路，按 `channel_id` 维护通道状态
    - **AlarmRouter**: `_load_all()` 扫描 `shared_with` 把多个 ch 映射到同一 manager 实例；`_save_all()` 共享 manager 只按 owner 序列化一次（去重）；`disconnect_all()` 也去重；`on_channel_removed()` 在共享时只摘 ch 不断串口
    - **运行时切换**: 新增 `AlarmRouter.reload_config_from_disk()` 与 `POST /alarm/reload`，前端保存共享配置后自动 reload，**无需重启软件**
    - **API**: `ConfigRequest` 增加 3 个共享字段；`/alarm/status` 返回 `is_shared / is_owner / owner_channel / shared_channels`
    - **前端 UI**: `frontend/src/views/Alarm/index.vue` 新增「共享报警灯」卡片（仅多工位时显示），仅在工位 1（owner）显示完整编辑面板（多选共享工位 / 4 个类别优先级 1-4 / 每个事件归属类别下拉 / 立即生效保存按钮）；被共享工位（ch≥1）显示只读提示「跟随工位 X」+ 一键跳到工位 1
  - 合成规则（`priority` 模式）:
    - 任一通道有未过期 NG → 红灯（NG 显示期间不被 OK 抢占）
    - 没 NG 但有警告 → 黄灯
    - 都没有但任一通道在检测中 → idle 灯（待机色）
    - 全部停 → 灯灭
  - 兼容性: 完全向后兼容。配置里没写 `shared_with` 时所有逻辑走 solo 路径，行为与 v2.7.2 一致
  - 影响文件: `backend/api/alarm.py`, `frontend/src/views/Alarm/index.vue`, `backend/data/alarm_config.shared.example.json`(新)
  - 验证: 共享模式 10 用例 + 运行时切换 5 用例全部通过

- [FEAT-002] 共享报警灯示例配置文件
  - 需求: 用户可能想跳过 UI 直接改 JSON，需要一个完整可抄的样板
  - 实现: 新增 `backend/data/alarm_config.shared.example.json`，文件头 `_README` 数组用中文说明字段含义、迁移步骤、合成规则
  - 影响文件: `backend/data/alarm_config.shared.example.json`(新)

## 已知问题 / 待验证

- TensorRT 双工位 imgsz 修复仅做了 mock 单元测试，**真机端到端需要用户在双工位机器拉一遍 .engine 模型实测**；如仍出现 imgsz 不匹配的报错请回报具体日志

## 现场操作建议

- **共享报警灯启用步骤**: 切到工位 1 → 打开「共享报警灯」卡片右上角开关 → 勾选共享给哪些工位 → 优先级保持默认 `NG=1, 警告=2, OK=3, 待机=4` → 点「保存共享配置（立即生效）」。**无需重启软件**
- **多扫码器接入**: 一个网口接不了多个扫码器，**用主动式以太网交换机**（推荐 TP-LINK TL-SG1005D，~50 元）。被动式 RJ45 一拖二会因信号冲突失败

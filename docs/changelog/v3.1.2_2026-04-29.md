# v3.1.2 (2026-04-29)

## 修复

- [BUG-312-001] 修复客户机日志 `KeyError: '泡沫槽3'` (容器分组迭代过程中并发删除)
  - 复现: `_update_container_grouping` 在同一帧内对多个箱子做"消失确认 → 结算 → end_cycle"。`_settle_box → _end_cycle` 会清空 `_box_objects`, 后续 `for box_did in list(...)` 拿到的快照里, 已结算的 key 就不在了。客户机日志 (10:48 时段) 抛了 4 次 `KeyError: '泡沫槽3'`, 每次让推理线程一帧丢掉, 间接拖慢了帧率。
  - 修复: `for box_did in list(self._box_objects.keys())` 后立刻加一行 `if box_did not in self._box_objects: continue`, 已被前一轮 settle 清掉的 key graceful 跳过, 不再 KeyError。
  - 影响文件: `backend/api/source_container_grouping_mixin.py`

- [BUG-312-002] 修复客户机录制视频全是 0 帧, 播放失败
  - 复现: 客户日志 1300+ 行 `[FFmpeg录制] 已停止, cycle_xxx.mp4, 共 0 帧`, 客户点播放显示失败。
  - 根因 1 (主因): `source_recording_thread_mixin.py` 没 `import FFmpegRecorder`, `_enqueue_frame_for_recording` 内部用 `FFmpegRecorder.MAX_RECORD_WIDTH` 触发 `NameError`。
  - 根因 2 (放大器): 包裹 `_enqueue_frame_for_recording` 的 `try/except Exception` 太宽, 把 `NameError` 一并吞掉, 客户跑了 45 分钟没人发现。
  - 根因 3 (掩盖证据): `FFmpegRecorder` 把 `subprocess.Popen(stderr=DEVNULL)`, FFmpeg 自己的报错也看不到。
  - 修复:
    1. 加 `from backend.api.source_recorder import FFmpegRecorder`
    2. `_enqueue_frame_for_recording` 把外层 except 拆成两段: 帧预处理失败 (`AttributeError`/`NameError` 等) 首次打印一次警告然后静默 drop, 队列 `queue.Full` 走"挤掉队首"原逻辑
    3. `FFmpegRecorder` 把 `stderr=subprocess.PIPE`, 起一条 `_drain_stderr` daemon 线程实时收 stderr 缓冲到 `_stderr_lines`; `release()` 时若帧数为 0 就把 buffered stderr 一次性打印, 客户能直接看到 FFmpeg 的真实报错。
  - 影响文件: `backend/api/source_recording_thread_mixin.py`, `backend/api/source_recorder.py`

- [BUG-312-003] 修复客户机 USB 摄像头 FPS 从 30 跌到 10 之后再也不回
  - 复现: 客户机日志里"捕获线程心跳" 10:48:32 之前一直 31 fps, 之后 45 分钟全程 10 fps; 推理线程延迟一直是 16~36ms (实际能跑 30+fps), 但捕获塞不进足够帧, 推理也被饿到 10fps。日志里 `!!! 帧读取慢` 全程只触发 11 次 — 不是单帧大卡, 是稳态 100ms/帧, 即相机硬件层面给的就是 100ms/帧。
  - 根因: `start_camera` 完全没碰 `CAP_PROP_AUTO_EXPOSURE`, UVC 摄像头默认开自动曝光; 工人开始作业 (大量遮挡日志同步出现) 时光线变暗, 相机自驱把曝光时间拉到 100ms, 帧率被驱动锁到 10fps。光线恢复后曝光不会自动回缩, FPS 一直锁住。
  - 修复: 项目 / 工位摄像头配置加两个新字段 `auto_exposure` (默认 `True` 完全向后兼容) + `exposure_value` (DSHOW/MSMF 上是 log2 秒, 默认 -6 ≈ 1/64s ≈ 15ms)。`start_camera` 加 `_apply_exposure_setting()` 跨平台辅助, Windows 下 `set(CAP_PROP_AUTO_EXPOSURE, 0.25/0)` + `set(CAP_PROP_EXPOSURE, log2_seconds)`, Linux 下 `set(AUTO_EXPOSURE, 1)` + 把 log2 秒换算成 V4L2 的 100us 绝对单位。前端单工位 + 多工位 UI 都加"自动曝光"开关 + "曝光等级"输入 (条件显示, 仅摄像头源可见, 带 tooltip)。
  - 影响文件: `backend/api/source_camera_start_mixin.py`, `backend/api/source_routes.py`, `backend/main.py`, `frontend/src/views/Source/index.vue`, `frontend/src/store/useSourceStore.js`

## 功能

- [FEAT-312-001] 多工位"广播扫码"新增主工位带动结算模式
  - 需求: 双工位扫码模式下, 同一码同时下发到 2 个工位 (例: 大件+小件混合工位)。两工位算法不同 (大件用 `all_gone`, 小件用 `container_grouping`), 结算节奏天然不一致 — 小件结算完了, 大件那边的"上一轮箱子还在等消失确认"; 共享扫码器更新 `_pending_workpiece` 后, 大件这一轮的 cycle 会被绑到下一个工件号, 数据串台。
  - 实现: `ScannerDevice` 加 `broadcast_settle_mode` (independent / primary)、`primary_settle_channel` (主工位 channel_id)、`primary_settle_min_items` (件数门槛, 默认 1)。
    - `independent` (默认, 行为不变): 每个广播工位各自跑各自的 settle 逻辑。
    - `primary`: 主工位 cycle 一结束 → `notify_cycle_settled(primary_channel)` → 遍历该扫码器的其他广播工位, 调 `force_settle_pending_cycle(min_items)`, 强制结算 (容器模式只结算装件数 ≥ 阈值的箱子, 空箱跳过, 防"幽灵箱"误结算)。
    - 防重入: `_force_settling_in_progress` 标志避免 `notify → force_settle → end_cycle → notify` 死循环。
  - UI: `ScannerPanel.vue` 在勾了 "≥2 个广播工位" 时露出新设置块 — 单选 "结算模式" (independent / primary), primary 模式下出 "主工位" 下拉 + "件数门槛" `el-input-number`; 切换到 primary 时弹一次输入框确认门槛值。
  - 影响文件: `backend/models/mes_models.py`, `backend/main.py`, `backend/api/scanner.py`, `backend/services/scanner.py`, `backend/api/source_session_lifecycle_mixin.py`, `backend/api/source_state_init.py`, `frontend/src/views/MES/ScannerPanel.vue`

- [FEAT-312-002] 集群汇总新增 "OK 不可被 NG 覆盖" 合并策略
  - 需求: 客户场景下站点上下文存在"返工"通道, 一件工件返工后再次扫码 OK 应能翻回 OK; 但 OK 后又出现的 NG 应当作"再扫了一遍误检", 不应把整体翻成 NG。原 latest 策略对同一 station 的多次报告"NG 优先且最新覆盖", 跟客户语义相反。
  - 实现: `ClusterConfig` 加 `station_result_strategy` (latest / ok_lock)。`_receive_station_report_locked` 分支:
    - `latest` (默认): 保持原行为, 同站多次报告中只要任一 NG 就整站 NG, 任意时刻最新报告覆盖 overall 状态。
    - `ok_lock`: 同站若已存在 OK, 后续 NG 报告**不更新** `is_good`, 只往 `sub_reports` 里写一条审计记录; 同站若已存在 NG, 后续 OK 报告允许翻盘到 OK (返工通道)。
  - UI: `ClusterPanel.vue` 当 `role === 'master'` 时露出 "站点结果合并策略" 单选 + 一段使用场景说明。
  - 影响文件: `backend/models/mes_models.py`, `backend/main.py`, `backend/api/cluster.py`, `backend/services/cluster_collector.py`, `frontend/src/views/MES/ClusterPanel.vue`

- [FEAT-312-003] ByteTrack `match_thresh` 暴露到项目设置
  - 需求: 客户现场 2~3 个箱子并列 + 工人遮挡, 默认 `match_thresh=0.8` 在遮挡瞬间 IoU 跌到 0.5 以下时容易丢 ID, 客户希望按现场调到 0.5~0.7 之间。
  - 实现: `_generate_custom_tracker_yaml` 从 `pipeline_config.tracking_match_thresh` 读取, 类型异常 fallback 0.8, 数值 clamp 到 [0.1, 0.99] 后写入 `bytetrack.yaml`。前端 `Project/index.vue` 跟踪选项里加"匹配阈值" `el-input-number` 字段 (min 0.1 max 0.99 step 0.05), 带 tooltip 说明。
  - 影响文件: `backend/api/source.py`, `frontend/src/views/Project/index.vue`

## 客户现场操作建议

1. **FPS 锁 10 修复**: 升级后进入 "输入源" 页, 把"自动曝光"开关切到"关", 默认曝光等级 `-6`。画面太暗就调到 `-5`, 配合 LED 补光。**不要再调到 `-4` 或更高**, 帧率会被压回 16fps。
2. **箱子被工人遮挡丢 ID**: 项目设置 → 跟踪选项, 把"匹配阈值"从 0.8 调到 0.5~0.6 试试; 同时建议打开"遮挡容忍超时" + "外观匹配 (HSV)" + "ID 锁帧"。
3. **双工位异步串台**: MES → 扫码器, 把"广播结算模式"从"独立"切到"主工位带动", 选大件那一路当主工位, 件数门槛设 1 (空箱不结算)。
4. **OK 被 NG 覆盖**: MES → 集群, 把"站点结果合并策略"切到 "OK 优先 (ok_lock)", NG 后的 OK 仍可翻盘, OK 后的 NG 写审计但不翻盘。

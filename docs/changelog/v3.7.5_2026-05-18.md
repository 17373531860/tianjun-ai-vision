## Bug 修复

### [BUG-001] 顺序模式下做了周期性强制动作仍然不清零（FIX-381 副作用）
- **症状**：客户配主流程顺序 A-B-C-D, 同时配"每 20 轮 / 每 600 秒"做一次保养动作 E（trigger_step=E）。**实测做完 E 之后, 周期强制动作的"未完成轮数 / 时间"依然继续累加, 没清零**——保养报警一直不消除。
- **根因**：v3.7.2 引入的 FIX-381 在 `process_step_detection` 里对"顺序 / 自定义-基于顺序"模式做了拦截——所有不在 `expected_seq`（主序列）里的步骤直接 `return`, 不进 `cycle.step_sequence`。本意是隔离"序列外步骤误判 NG"。**但保养类周期动作的 trigger_step（E）本来就在主序列外（A-B-C-D 不含 E）**, 也被一起拦了：
  - E 永远进不了 `cycle.step_sequence`
  - `_check_periodic_actions(cycle_steps, ...)` 永远在 `cycle_steps` 里看不到 E
  - `did_trigger = bool(cycle_step_set & trigger_labels)` 永远是 False
  - → counter / `_periodic_last_done_ts` 永远不重置 → 报警一直挂着
- **修复**：**方案"小账本"** — 给周期强制动作单独开一本旁路观察账本, 不污染 `cycle.step_sequence`（数据导出仍干净）, 只服务周期判定一个用途：
  - `source_periodic_actions_mixin.py`：
    - `_apply_periodic_actions` 初始化新状态变量 `_periodic_triggers_observed: Set[str]`（与 `_run_on_start_pending` 同模式懒初始化）。
    - 新方法 `_observe_periodic_trigger(step_label)` — 拿 step_label 比对所有规则的 `trigger_labels`（同时遵守 `channel_filter`）, 命中就记一笔到账本。轻量, 早出快出。
    - `_check_periodic_actions` 入口处 `cycle_step_set = set(cycle_steps or []) | _periodic_triggers_observed` 合并算 `did_trigger`, 让旁路观察的 E 也能触发 reset。
    - 判定完清空账本, 防串到下一轮。
  - `source_settlement_mixin.py`：`process_step_detection` 里 `if is_new_appearance:` 分支**最前面**（早于 FIX-381 拦截 return）调一次 `_observe_periodic_trigger(label)`。这样无论 label 是否被 FIX-381 拦截, 周期判定都能看见。
  - `source.py: reset_stats` 同步清账本, 防 reset 后残留上一周期的 trigger 影响判定。
  - `source_session_lifecycle_mixin.py: _discard_empty_cycle` finally 段也清账本, 防作废周期里观察到的 trigger 串到下一周期。
- **完全向后兼容**：账本只在有 `_periodic_actions` 规则时才有意义, 老项目（没配周期强制动作）`rules` 为空时 `_observe_periodic_trigger` 直接 early return, 零开销。不动数据导出、不动 cycle.step_sequence、不动事件触发流程。
- **测试**：新增测试类 `TestPeriodicTriggerObservedBypassesSequentialFilter`（`tests/test_periodic_actions_v352.py`）, 8 个用例覆盖：
  - observe 记账 / 过滤无关 label / 同 label 去重
  - **核心场景**：`cycle_steps` 不含 trigger 但旁路账本含 → reset 仍能触发
  - 判定后账本清空 / `reset_stats` 清账本
  - `channel_filter` 限定时 observe 也遵守
  - 时间维度 `_periodic_last_done_ts` 通过旁路账本路径同步重置
- **影响文件**：
  - `backend/api/source.py`
  - `backend/api/source_periodic_actions_mixin.py`
  - `backend/api/source_session_lifecycle_mixin.py`
  - `backend/api/source_settlement_mixin.py`
  - `tests/test_periodic_actions_v352.py`

### [BUG-002] 副模型检测框始终是默认色, 客户在步骤列表配的颜色失效
- **症状**：客户用副模型识别"错误放置"（默认 `display_color = #f59e0b` 琥珀黄）, 在 Project 页 → 步骤列表 → "检测框颜色"列**单独配了红色**, 但 Monitor 实时画面里检测框**仍然是黄色**, 跟设置不一致。同一处 tooltip 写"任何模式都生效", 自相矛盾。
- **根因**：v3.7.2 (FIX-381-B) 设计 `pickDetColor` 优先级时把"副模型 `display_color`"放在最高位：
  ```js
  // 旧逻辑（错的）
  if (副模型 && det.display_color) return det.display_color;  // 副模型色优先
  if (步骤有 box_color) return cfg.box_color;                  // 步骤色让位
  return is_ng ? NG : OK;
  ```
  设计本意：副模型整体识别色统一直观。**但客户对单个 label 配色的明确意图被忽视了**, 步骤列表里的 `box_color` 形同摆设。
- **修复**：翻转优先级 — **用户明确意图最高**：
  ```js
  // 新逻辑
  if (步骤有 box_color) return cfg.box_color;                  // 步骤级最高
  if (副模型 && det.display_color) return det.display_color;  // 副模型默认色其次
  return is_ng ? NG : OK;                                       // 兜底
  ```
  - `frontend/src/views/Monitor/index.vue: pickDetColor` 调整 if 顺序 + 注释更新（两处使用点的注释也对齐）。
  - `frontend/src/views/Project/index.vue` "检测框颜色"列 tooltip 文案改为：`该标签的检测框单独配色（任何模式都生效）。留空 = 副模型沿用其默认识别色 / 主模型沿用全局 OK/NG 颜色。设了颜色就以这里为准，副模型默认色让位。`——把语义讲清楚, 跟新行为对齐。
- **影响**：副模型如果**没配** `steps_config[*].box_color`（留空）, 行为与 v3.7.4 一致（仍用副模型 `display_color`）, 不会破坏现有项目视觉。配了 `box_color` 的步骤现在生效, 之前的"配了也没用"bug 修复。
- **影响文件**：
  - `frontend/src/views/Monitor/index.vue`
  - `frontend/src/views/Project/index.vue`

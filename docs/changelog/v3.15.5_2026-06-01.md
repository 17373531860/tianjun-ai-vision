# v3.15.5 (2026-06-01)

> 修复前端插件加载抢在后端就绪之前执行导致的 Network Error 放弃。现场 v3.15.4 客户机日志（由 v3.15.4 新增的诊断日志双通道精准抓到）显示：前端页面加载远早于后端冷启动完成（CUDA 预热 + 模型加载好几秒），旧逻辑一上来拉插件清单就 Network Error、然后一次性放弃，插件前端定制全程不加载。修法：插件 bootstrap 先轮询探活、等后端就绪（最多 90s）再拉。这是 v3.15.4 `file://` 三级 import 修复**更靠前的一环**（现场根本没走到 import 就卡在拉清单）。

## Bug 修复

- [BUG-001] 前端插件加载抢跑后端就绪 → Network Error 一次性放弃 — **P0**
  - 症状: v3.15.4 客户机重启后插件前端定制仍不生效；启动日志出现 `[⬛ PluginLoader] 拿 active manifest 失败 :: Network Error` 与 `[PluginTheme] apply 失败: Network Error`，且这两行出现在后端 `Application startup complete` **之前**
  - 根因: `main.js` 启动时 fire-and-forget 调 `themeStore.apply()` + `loadActivePluginFrontend()`，既不等后端就绪也不重试；而前端页面（`file://` 静态资源）加载远早于后端冷启动完成（后端要 CUDA 预热 + 大模型加载，日志实测 Backend ready 在前端页面加载之后好几秒）→ 前端一上来拉 `/plugins/active/manifest` 就 Network Error → 加载流程第一步就放弃 → 插件前端 ESM 根本没机会加载（现场根本没走到 v3.15.4 修的 `file://` 三级 import 那一步）
  - 修复: 插件 bootstrap 在 apply/load 之前先 `waitBackendReady()`：用 `/plugins/active/manifest`（无 active 插件也返回 200）轮询探活，每秒一次直到成功、最多等 90s 覆盖工控机冷启动 + CUDA 预热 + 大模型加载最坏情况；探活成功再拉主题 + 加载 ESM；全过程带 `[⬛ PluginBootstrap]` 日志
  - 影响文件: frontend/src/main.js

## 改进

- [IMP-001] v3.15.4 诊断日志双通道现场验证有效
  - 本次根因**完全靠 v3.15.4 新增的诊断日志双通道 + Electron renderer console 转发定位**（客户机启动终端直接出现 `[Renderer:WARN] [⬛ PluginLoader] ... Network Error`），无需开 DevTools、无需转发补丁、无需敲命令，印证了可观测性改造的价值
  - 同时确认 v3.15.4 主程序版本号读取修复生效（日志 `主程序版本 3.15.4`，不再是 `0.0.0`），后端插件 `startup_load OK`

## 升级须知

- 本版需走完整安装包重装（前端代码在 `app/dist` 内，无法热替换）
- 装双工位定制插件后，确保「设置 → 工位数」为 **2**，否则定制监控界面不渲染（v3.15.4 起已加提示条）

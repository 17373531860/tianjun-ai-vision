# v3.14.0 (2026-05-29)

> RFC 11「串行流水线结算 (Workpiece Flow Coordinator)」一次性闭环 (M0-M8 全部交付)。新增「单机内多工位串行流水线」原生能力: 同一工件依次走过 N 个摄像头工位, 全过才算合格。架构上与已有 ChannelGroup (并行联动, RFC 10) / cluster (跨机汇总) 完全独立、互不依赖, 同工位互斥。三种触发模式 (扫码 / 时间窗 FIFO / 物理 GPIO) 配齐, 福建金龙现场无扫码场景跑通 demo。无破坏性改动, 老项目 JSON / DB / 接口、未装插件场景字节级零差异。

## 拓扑定位

```
L0 单工位:        一个 cycle (DetectionCycle.is_good)
L1 单机多工位并行: ChannelGroup (v3.13.0), 同时刻结算
L2 单机多工位串行: WorkpieceFlow (v3.14.0 新增), 依次结算  ← 本版本
L3 多机集群:      cluster + BoxAggregation
```

L1 和 L2 **同一工位互斥** (启用时双向校验), 但层级独立、API 独立、UI 独立。

## 主线 — RFC 11 串行流水线结算

### [FEAT-001] **WorkpieceFlowConfig + WorkpieceFlowRun ORM 双表**

- **需求**: 客户串行装配线场景 (例: 工件先经摄像头 A 检尺寸, 再经 B 检表面, 再经 C 检装配) 没有原生支持, 主程序无法跨工位聚合成"该工件最终合格/不合格"。
- **实现**:
  - 新表 `workpiece_flow_configs` (流水线配置, 含 station_channel_ids 有序列表 / trigger_mode / fifo / 超时 / 短路 / plugin_data 等)
  - 新表 `workpiece_flow_runs` (每个工件流转的轨迹记录, 含 flow_uuid / serial_no / status / station_cycle_ids / station_results / final_result)
  - 通过 `Base.metadata.create_all` 自动创建; 启动迁移自动把上次进程残留的 `in_progress` run 全部标 `aborted` (防数据僵尸)
- **影响文件**: `backend/models/mes_models.py`, `backend/main.py`
- **关键词**: WorkpieceFlow / 串行流水线 / RFC 11 / workpiece_flow_configs / workpiece_flow_runs

### [FEAT-002] **WorkpieceFlowCoordinator 单例 + 5 态状态机**

- **需求**: 需要集中调度器把多工位 cycle 事件按 FIFO 顺序串起来, 自动追踪每个 in-flight 工件的当前工位 + 累计结果。
- **实现**:
  - 进程内单例 `WorkpieceFlowCoordinator`, 内部 `_flows / _channel_to_flow / _flow_to_in_flight / _in_flight_runs / _triggers / _timers` 全部由 `threading.Lock` 保护
  - 5 态闭环: `CREATED → STATION_RUNNING → STATION_DONE → COMPLETED_OK/COMPLETED_NG / SHORT_CIRCUITED / TIMEOUT`
  - FIFO 队列守门: `fifo_max_in_flight` 达上限拒绝新工件入队
  - `threading.Timer` 实现 `workpiece_timeout_ms` 超时, 3 种 `timeout_action`: `force_ng` / `drop` / `alarm_only`
  - 所有外部集成 (DB / alarm_router / plugin hooks / MES) 全部 `try-except` 隔离, 异常永远不打断主流程
- **影响文件**: `backend/services/workpiece_flow_coordinator.py` (新建 ~1080 行), `backend/api/source_session_lifecycle_mixin.py` (start_cycle / end_cycle 加 on_cycle_started/settled 钩子), `backend/api/channel_manager.py` (set_channel_count 减通道时调 on_channel_removed)
- **关键词**: WorkpieceFlowCoordinator / 状态机 / FIFO / threading.Timer / 短路 / 超时 / 隔离

### [FEAT-003] **3 种触发器策略 (策略/适配器模式)**

- **需求**: 客户现场有三类触发方式 — 节拍稳定无扫码场景 / 扫码定位场景 / 物理 GPIO 信号场景。
- **实现**:
  - `FlowTriggerBase` 抽象基类 (生命周期 `attach / detach`; 评估接口 `evaluate_cycle_start / evaluate_scan / evaluate_physical_signal`)
  - **TimeWindowTrigger** (M2): 监听入口工位 cycle_start 自动 FIFO 入队 + 自动序号 `auto-{flow_id}-{uuid8}` (适合福建金龙等无扫码节拍稳定场景)
  - **ScanTrigger** (M3): 复用 `mes_hooks.on_scan_received` + `entry` (broadcast 全部工位) / `each_station` 两种绑定策略 + 与 `scan_pair` 严格互斥 (mes_hooks._handle_scan 检测到 channel 属于 flow 时短路给 Coordinator)
  - **PhysicalTrigger** (M7): 接 `external_device` GPIO/Modbus 信号 + `dedup_window_ms` 去抖 (默认 500ms) + 自动序号 `{serial_prefix}-{ts}` (适合光电开关 / Modbus holding register 边沿触发)
- **影响文件**: `backend/services/flow_triggers/__init__.py`, `backend/services/flow_triggers/base.py`, `backend/services/flow_triggers/time_window_trigger.py`, `backend/services/flow_triggers/scan_trigger.py`, `backend/services/flow_triggers/physical_trigger.py`, `backend/services/mes_hooks.py`
- **关键词**: TimeWindowTrigger / ScanTrigger / PhysicalTrigger / scan_pair / broadcast_channels / dedup / 策略模式

### [FEAT-004] **REST API + Pydantic schema + 权限 + 互斥校验**

- **需求**: 给前端 / 插件 / 集成方提供完整的 CRUD + 诊断查询接口。
- **实现**:
  - 路由前缀 `/api/v1/workpiece-flows/`, 8 个端点: `GET POST` 列表 / 创建, `GET PUT DELETE /{id}`, `GET /{id}/state` (运行时 in-flight 工件), `GET /{id}/runs` (历史轨迹分页), `GET /runs/{run_id}` (单 run 详情)
  - Pydantic schema 全字段类型校验 + 名字唯一 + station_channel_ids 至少 2 / 无重复 / int >= 0
  - 创建或 PUT 启用时与 `ChannelGroup` + 其他 enabled flow 双向互斥校验 (同 channel 不能同时属于两者)
  - 启用状态下禁止删除 (返 409) / 禁止改 stations (返 400)
  - 新增 2 权限: `system.workpiece_flow.view` (查询) / `system.workpiece_flow.manage` (CUD)
- **影响文件**: `backend/api/workpiece_flows.py` (新建), `backend/api/__init__.py`, `backend/core/permissions.py`
- **关键词**: REST API / Pydantic / 权限 / channel_group 互斥 / system.workpiece_flow.view / .manage

### [FEAT-005] **5 个插件 hook + 2 个 PluginHost 主动 API**

- **需求**: 客户需要在工件流关键节点挂插件做扩展 (跨工位质量分聚合 / 自定义超时处理 / 短路报警 / MES 异步导出等)。
- **实现**:
  - 5 个 hook:
    - `workpiece_flow_enter` (工件进入流水线)
    - `workpiece_flow_station_done` (某工位完成)
    - `workpiece_flow_completed` (流水线完成, returnable `override_final_result` 允许插件改写最终 OK/NG)
    - `workpiece_flow_timeout` (工件超时, returnable `override_timeout_action` 允许插件改写超时动作)
    - `workpiece_flow_short_circuit` (短路触发)
  - 2 个 PluginHost 主动 API: `list_workpiece_flows()` / `query_workpiece_flow_state(flow_id)` (需 manifest 声明 `runtime.workpiece_flow_observe` capability)
- **影响文件**: `backend/plugin_system/hook_dispatch.py`, `backend/plugin_system/registry.py`, `docs/plugin-system/design/01_manifest_schema.md`
- **关键词**: plugin hook / override_final_result / override_timeout_action / PluginHost / runtime.workpiece_flow_observe / capability

### [FEAT-006] **Monitor 加 indicator slot + Settings 加 Tab**

- **需求**: 前端需要让用户配置流水线 + 查看 in-flight 工件状态。
- **实现**:
  - Monitor 加 `monitor.workpiece-flow.indicator` slot, 默认实现展示 in-flight 工件列表, 客户插件可全覆盖 (`TjSlot` 标准用法)
  - Settings 加「流水线串行」Tab + 3 种 trigger_mode 表单切换 (time_window / scan / physical 各显示对应字段) + 启用前预检 + 运行时 state 查看对话框
  - 新建 `frontend/src/api/workpiece_flow.js` 客户端封装 (与 `auth.js` / `cluster.js` 风格一致)
- **影响文件**: `frontend/src/views/Monitor/index.vue`, `frontend/src/views/Settings/index.vue`, `frontend/src/views/Settings/WorkpieceFlowPanel.vue` (新建), `frontend/src/api/workpiece_flow.js` (新建)
- **关键词**: Monitor slot / Settings Tab / monitor.workpiece-flow.indicator / WorkpieceFlowPanel

## 共存策略 (查清边界)

| 子系统 | 策略 |
|---|---|
| `ChannelGroup` (RFC 10, 并行) | 同工位互斥 (创建 / 启用时双向校验) |
| `cluster` (跨机) | L2 完成后正常推 MES, cluster 端按现有逻辑 box 汇总. v3.14 v1 不做 flow→box 联动 |
| `scan_pair` (v3.3) | Flow 启用时 channel 属于 flow 的扫码事件直接给 Coordinator, 跳过 scan_pair (语义冲突, 文档明示) |
| `AlarmRouter` | 短路/完成/超时直接调 `trigger_alarm`, 复用现有报警链路 |
| `Workpiece` 体系 | Flow 完成时调 `WorkpieceService.set_result` 写工件最终结果, 复用 MES 推送 |

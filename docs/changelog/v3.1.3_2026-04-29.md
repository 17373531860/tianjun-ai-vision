# v3.1.3 (2026-04-29)

## 修复

- [BUG-313-001] 修复视频文件回放偶发 ffmpeg 多线程断言导致后端 worker 崩溃 / API 永久卡死
  - 复现: 客户/开发机用本地视频文件作为输入源, 终端瞬时刷出
    `[swscaler @ 0x...] bad src image pointers` 加一行
    `Assertion fctx->async_lock failed at libavcodec/pthread_frame.c:175`,
    随后 `lsof :8001` 仍 LISTEN, 但任何 API 请求 timeout, 前端 MJPEG 黑屏。
    `pstree` 看 uvicorn worker 子进程已经是 `<defunct>` 僵尸。
  - 根因: OpenCV 内置 ffmpeg 启用了多线程解码 (libavcodec frame-level threading),
    某些视频文件 / seek 时序下 `pthread_frame.c:175` 的 `assert(fctx->async_lock)`
    会失败 → C `assert()` 触发 SIGABRT → uvicorn worker 子进程整个 abort 退出。
    我们用 `--reload` 启动, reloader 主进程**只**监视文件变化,
    不监控 worker 是否存活, 所以 worker 死了不会被复活, 8001 端口由主进程
    持有依然 LISTEN, accept 之后没人处理 → 永远 timeout。
  - 修复: 启动时 `os.environ.setdefault("OPENCV_FFMPEG_CAPTURE_OPTIONS", "threads;1")`,
    强制 OpenCV 调 ffmpeg 用单线程解码, 直接消除 pthread_frame 那条断言。
    在 `backend/main.py` 顶端 (cv2 被任何模块间接 import 之前) 兜底,
    `start_backend.sh` 也 export 同名 env (双保险, 客户包/开发机都覆盖)。
    本机/打包后视频回放都不再触发该断言, 也不再有 worker 突然死掉的风险。
  - 影响文件: `backend/main.py`, `start_backend.sh`
  - 性能影响: 视频文件单线程解码相对多线程慢一些, 1080p H.264 实测影响可忽略,
    4K 高码率才有差异。摄像头 / RTSP 输入源走的不是这个 codepath, 不受影响。

- [BUG-313-002] 修复跟踪模式下"步骤统计"表永远停在 `--/待检测`, 即使物品已被 YOLO 数到
  - 复现: 项目 logic_mode=tracking, 镜头里出现某个标签 (例如"线槽"), 物品清点
    卡片 counted 已涨, 但右侧"步骤统计"表里该步骤的"状态"列始终是 `--`, "结果"
    列始终是空 — 双工位 / 四工位的卡片 2 列表也一样, 永远不翻 OK。
  - 根因: 步骤表的 `tableData[i].status` 在 `updateStepsFromBackend` /
    `updateAllChannels` 里**只**靠 `backendCounters._currentCycleSteps`
    (后端 `current_cycle_steps`) 驱动, 而后端这个字段是 detection / SOP 模式
    专用的 — 跟踪模式从来不推这个字段。跟踪模式真正的进度信息推到了
    `tracking.item_checklist`, 但只有 line 576 的"物品清点"卡片在用,
    步骤表完全没接通。
  - 修复: 在两条更新路径加跟踪模式补丁 — 当 `tracking.item_checklist[label].counted > 0`
    (普通) 或 `_boxes[bid].items[label].counted > 0` (容器, 任意箱子算命中)
    时, 把对应步骤翻成 `status='completed'` + `cycleResult='ok'`。
    单工位 SOP 卡片 + 步骤统计表, 双工位 / 四工位卡片 2 列表 + 详情面板表,
    全部覆盖。
  - 影响文件: `frontend/src/views/Monitor/index.vue`

## 功能

- [FEAT-313-001] 多工位 Monitor 加 per-channel MES 信息条 (与单工位行为对齐)
  - 需求: 客户在双 / 四工位现场反馈 — 单工位下方的"操作员 → 工件号 / 未绑码
    / 等待扫码"提示条非常关键, 但多工位模板里完全没有, 工人无法快速看到当前
    工位是否已扫码、绑了哪个工件号、扫码异常时的"未绑码"红字告警。
  - 实现: `Monitor/index.vue` 新增三个工具方法 (`getMesDataFor`/
    `getDisplayWorkpieceFor`/`shouldShowMesBarFor`) + per-channel 状态
    (`workpieceOverridesByCh`/`workpieceOverrideTimers`/`workpieceHideTimers`)。
    - 双工位 (`channelCount === 2`): 在每个工位的视频面板与计数器行之间
      插一行紧凑 MES 信息条, 显示工件号 / OK NG 标签 / 未绑码红字 / 订单进度
      / "等待扫码..." / 清除按钮。
    - 四工位 (`channelCount > 2`): 每个小卡片在视频上沿覆盖一行超紧凑 MES
      标签 (工件号 / 未绑码 / 等待扫码), 选中工位的详情面板顶部一行完整 MES 信息条。
    - OK / NG 3.5s hold 行为: 跟单工位完全一致 — 总产量从 N → N+1 的瞬间,
      把当前 mes.workpiece 用 OK/NG 状态覆盖 3.5s 让工人看到本轮判定结果,
      然后清空回到"等待扫码..."。
    - 显示条件放宽: 工位 `isRunning || isDetecting` 即显示 (默认显示
      "等待扫码..."), 不再要求"必须有 workpiece 或扫码事件"才出现, 避免
      画面上空白让工人误以为系统没启动。
  - 影响文件: `frontend/src/views/Monitor/index.vue`

## 客户现场操作建议

1. **后端"突然不响应"复盘指引**: 如果再次看到 8001 端口在但 API 全部 timeout,
   先 `pstree -ap <uvicorn-pid>`, 看 worker 子进程是否 `<defunct>`。本版本
   修复后这种情况不应再出现, 如果仍发生说明是别的崩溃路径, 需抓终端最后
   30 行日志。
2. **跟踪模式步骤翻 OK**: 升级后跟踪模式下步骤统计表 / 工位卡片的 2 列状态
   表, 都会按"任一物品 counted > 0 → 该步骤 OK / 已检测"实时翻牌, 不需要
   等扫码周期结束。
3. **多工位 MES 条**: 升级后双 / 四工位 Monitor 自动展示, 无需配置。"等待扫码..."
   不代表错误, 只表示该工位本周期还没接收到扫码; 红色"未绑码"才是需要工人
   立即处理的告警。

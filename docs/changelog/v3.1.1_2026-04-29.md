# v3.1.1 (2026-04-29)

## 功能变更

- [FEAT-311-001] 新增称重器"即时快照"配对模式 (pairing_mode = instant)
  - 需求: 客户反馈"流水线连续上料,工件来不及回零下一工件就到了; 结构上是 1 工件 1 工位, 不允许丢数据"。原 stable 模式的"等稳定值再绑条码"在这种场景下要么 buffer 残留把新条码误绑到旧工件的稳定值, 要么干脆等不到稳定值导致丢数据。客户明确要求: "扫码那一瞬间(或最近一次接收到称重器的数据)是多少就绑定多少"。
  - 实现:
    - **配对模式字段**: `ExternalDevice` 新增 `pairing_mode VARCHAR(16) DEFAULT 'stable'` 列, `DeviceConnection` 同步新增同名字段。两个值:
      - `stable` (默认, 原逻辑): 等连续 N 次差值 ≤ Δ 才视为稳定 → 用稳定值中位数派发; 配合 v2.7.10 的"扫码迟到补发"在已稳定状态下也能补绑。
      - `instant` (新): 扫码事件触发瞬时派发 — 用 `last_parsed` 里"最近一次任意状态的称重读数"立即派发, **派发后立即从 buffer 里 pop 该条码**。下一帧称重数据到达时 buffer 已空, 不会重复派发。
    - **set_barcode 双分支**: instant 分支调 `_instant_dispatch_on_scan`, 取 `last_parsed` 立即派发 + 清 buffer; 若秤还没出过任何读数 (`last_parsed=None`), 把条码留在 buffer 里, 等下一帧 `_on_raw_data` 兜底派发。
    - **_on_raw_data 双分支**: instant 模式不走稳定状态机 (`_handle_weight_stability`) 也不走有重无码告警 (`_check_weight_no_barcode_alarm`), 默认只更新 `last_parsed`; 仅当 buffer 里有"扫码先到"的残留条码时才派发并清 buffer (兜底通道)。
    - **API + UI**: `DeviceCreate`/`DeviceUpdate` Pydantic 加 `pairing_mode`, `_serialize` 输出。`ExternalDevicePanel.vue` 新建/编辑对话框新增"配对模式"下拉 (仅称重器可见), 两种模式各自带一段使用场景说明; instant 模式下隐藏"稳定值参数面板"和"有重无码告警"配置项 (这两个在 instant 模式下永远不触发, 暴露反而误导用户)。
  - 影响文件: `backend/models/mes_models.py`, `backend/main.py`, `backend/services/external_device.py`, `backend/services/external_device_pipeline.py`, `backend/services/external_device_models.py`, `backend/api/external_device.py`, `frontend/src/views/MES/ExternalDevicePanel.vue`

## 已知行为差异 (instant 模式 trade-off)

- 工件 A 没拿走 B 直接压上时, B 扫码会用 (A+B) 的合重派发 — 物理限制, 唯一替代方案是回零等待, 客户已明确拒绝。
- `last_parsed` 可能略旧 (称重器 1Hz 推送时, 最大 ≤1 秒前的读数) — 客户措辞"最近一次接收到称重器的数据"已涵盖此语义。
- 秤物理掉线期间扫码会丢中间事件 (buffer 被后续扫码覆盖, 只有最后一条会在秤恢复后兜底派发) — 这是异常态, 通过设备健康检查发现。

## 三道防重复 +1 防线 (instant 模式下仍然有效)

1. 扫码器侧滑动窗口 dedup 抑制同码连发 (v2.7.16 已有)
2. set_barcode 派发完立即 pop buffer, 后续称重帧不会用同码再触发派发 (本次新增)
3. 集群侧 `cluster_collector` 检测 `is_recovery=True` 时不再 `_increment_cluster_orders` (v3.1.0 已有)

## 工具 / 测试

- [TOOL-311-001] 新增称重器配对模式端到端仿真脚本
  - 内容: `tools/test_weight_pairing.py` 用 Mock 服务屏蔽 DB / cluster 副作用, 覆盖 7 个场景:
    1. stable 模式抖动期不派发 → 稳定后派发一次 (回归)
    2. stable 模式扫码迟到 → 稳定值补发 (回归)
    3. instant 模式无条码不派发, 只更新 last_parsed
    4. instant 模式"称重先到 + 扫码后到"立即派发并清 buffer
    5. instant 模式"扫码先到 + 称重后到"兜底派发
    6. instant 模式不回零连续流: A=5kg → 扫 BC_A 派发 (5, BC_A); B 压上变 8kg → 扫 BC_B 派发 (8, BC_B)
    7. instant 模式同码扫一次后, 后续多帧称重数据不会重复派发
  - 用法: `python tools/test_weight_pairing.py` (7 PASS / 0 FAIL)

# v3.60.1a (2026-09-21) — 热补丁

> 六和芯子装配工位一现场反馈（2026-09-20 录像）：少扫码（芯子 7/8、未扫工装收尾码）时视觉末步（模具盖板）照样结算 OK，多码采集面板该组码一直挂着不翻篇、与下一件混码。
> 基础版本 v3.60.1。补丁包 `patches/v3.60.1a/`（bat + hotfix.py + 后端 2 个 py + 带截图补丁说明 PDF）。仅适用 v3.60.1。

## Bug 修复

- [BUG-001] 少扫码时视觉周期仍报 OK、扫码组永不收口
  - 根因: 扫码组只有 closing（扫收尾码）/ all_filled / timeout 三个收口点，收尾码不来组永远开着；`ng_pending` 挂起只报提醒不翻转视觉侧判定——视觉结算与扫码结算互不知晓。
  - 修复（主线 `settle_on_vision_cycle`，默认关）: ①`ScanCollectEngine.peek_vision_settle_gate` 推理线程零阻塞探针（try-lock + 纯缓存不碰 DB），视觉末步结算瞬间查缺码，缺码文案并入周期 NG reason（`_settle_detection_cycle` 融合）→ 本件当场 NG 一件一账；②`settle_by_vision_cycle` 在 `mes_hooks._handle_cycle_end` 异步收口——缺码按 `ng_missing` 落库导出关组（跳过挂起、`fire_events=False` 不借事件面防双报），码齐按 OK 收口；③配置卡新增「随视觉周期结算」开关 + PUT 链路 + 填入示例预置开。
  - 流程约束: 开启后收尾码必须在视觉末步完成前扫（先扫工装码再盖盖板）。
  - 影响文件: backend/services/scan_collect.py, backend/services/mes_hooks.py, backend/api/source_settlement_mixin.py, backend/api/scan_collect.py, frontend/src/views/MES/ScanCollectConfigCard.vue

## 补丁包（现场部署形态）

- 出厂 v3.60.1 的 `source_settlement_mixin` / `mes_hooks` 是 Nuitka 编译件（CORE_FILES），不能整文件替换 → `hotfix.py` 猴子补丁：包装 `VideoSourceManager._settle_detection_cycle`（结算瞬间探针有缺码则拦截 `_trigger_event` OK→NG 并追加缺码原因）+ 包装 `MESHookManager._handle_cycle_end`（尾接 `settle_by_vision_cycle` 收口）。
- `services/scan_collect.py` / `api/scan_collect.py` 是源码出厂 → 整文件替换（带 `PATCHED_V3601A` 标记，bat findstr 内容校验）。
- 出厂 asar 前端无开关 UI → 补丁强制开（DEFAULT_CONFIG 置 True + 探针/收口跳过配置键判断 + hotfix 对缓存盖章），重启即生效零配置；下个完整包露出开关按项目可配。
- bat 遵守 v3.56.0a 血泪规矩: 纯 ASCII + CRLF、无 taskkill/timeout、关软件靠操作员 pause 确认、每步落 `patch_log.txt`、`.bak_v3601a` 备份 + 标记校验防"没换上也报成功"。

## v3.60.1b 修订（2026-09-21 当夜，现场 backend.log 复盘）

- [BUG-002] a 版现场实测: OK→NG 翻转生效，但**扫码组收口不生效**（面板挂着、催扫继续）
  - 根因: 收口挂在 `MESHookManager._handle_cycle_end` 上，而现场扫码器开了「须先扫码才开始周期」（`scan_required`）——多码采集独占消费扫码、从不写单码绑定 `_pending_workpiece` → `start_cycle` 恒被 "requires scan first, no pending workpiece, skip cycle start" 跳过 → 周期行不建 → `on_cycle_end` 钩子从不触发 → 收口是死代码。副作用连带：该工位数据页一条周期记录都不落。
  - 修复（补丁 b 版 + 主线同步）: 收口改由视觉结算侧自兜底——`_settle_detection_cycle` 探针命中时起后台线程（自开 DB 会话，不占推理线程）调 `settle_by_vision_cycle` 关组；`_handle_cycle_end` 路径保留做双保险（收口幂等，组空即返回，不双报）。主线 `source_settlement_mixin._close_scan_group_async`，开关默认关零开销（探针不命中不起线程）。
  - 现场配套建议: 该工位扫码器连接关闭「须先扫码才开始周期」——多码采集下该条件永远满足不了，只造成周期记录不落库。
  - 影响文件: backend/api/source_settlement_mixin.py, patches/v3.60.1b/hotfix.py

## v3.60.1c 修订（2026-09-21 上午，a 包现场事故全面复盘）

> 工程师反馈：打 a 包后「之前重复结算的老毛病又来了」。不是 v3.60.1 `_held_visible` 被改坏，是 a 包让扫码侧继续自行挂起/出账，一件两账，看起来像复发。

- [BUG-003] a/b 未收回扫码侧结算主权 + 无组归属锚
  - 根因（现场日志三链）: ① `settle_on=closing` + `ng_pending` 在视觉收口之前就把组挂起，下一件母排码「超出应扫数量」拒收，催扫/补扫转 OK 再出一账；② 收口挂 `_handle_cycle_end`，`scan_required` 下周期行不建、钩子不跑；③ 无锚探针/收口把下一件刚开的组当成本件缺码。
  - 修复: 开启 `settle_on_vision_cycle` 后 closing/挂起/超时全部让位；收口唯一路径 `_settle_detection_cycle` → `_close_scan_group_async`（带末步出现时间锚，码齐也收）；拆除钩子关组；`vision_cycle` 收口跳过 `vision_gate`。热补丁 **不包装** `_handle_cycle_end`。
  - 现场配套: 下层母排仍须 5s + 等待不被打断 + 末步完成结算（a 包改不了这些；00:45 日志仍是 delay=2 / uninterruptible=False）。
  - 影响文件: backend/services/scan_collect.py, backend/api/source_settlement_mixin.py, backend/services/mes_hooks.py, patches/v3.60.1c/*

# v3.1.0 (2026-04-28)

## 功能变更

- [FEAT-310-001] 新增工单"绑定范围" — 工单按项目/工位/集群三选一计件
  - 需求: 客户反馈"集群汇总显示已完成,但工单完成数量一直 0"。排查发现 `WorkOrder` 在 v3.0.0 之前**只能按 `project_id` 绑定**,而前端工单创建表单**根本没暴露 `project_id` 字段**——导致 `get_active_order(project_id=...)` 永远查不到活跃工单,所有工单都不会 +1。同时客户在多机集群部署下,期望"工单建在主机就是整个集群的统计单位",而不是每台机各自维护。
  - 实现:
    - **数据模型**: `WorkOrder` 新增三个字段 `binding_scope` (project/channels/cluster) + `target_channels` (JSON list) + `target_stations` (JSON list,保留作扩展位 UI 不暴露)。
    - **服务层**: `WorkOrderService._normalize_binding(data, strict)` 统一三选一校验+互斥清空;`get_active_order(project_id, channel_id, station_id)` 重写成按 scope 路由匹配,cluster 模式跳过(由 cluster_collector 触发);新增 `find_cluster_orders(station_ids=None)` 给集群计件链路使用,默认按 priority + created_at 取首条。
    - **集群计件链路**: `cluster_collector._check_and_dispatch` 在 `gw.dispatch("box_complete",...)` 推送成功后(且非 `is_recovery`)调用 `_increment_cluster_orders`,**1 个 box_serial = 1 件**。校正重推/超时补偿不重复计件。
    - **API**: `OrderCreate`/`OrderUpdate` Pydantic 加新字段;`_serialize_order` 输出新字段。`receive_external_order` (外部 MES 推送) 走 `strict=False`,允许 `project_id` 为空入库,前端列表用红色 tag 提示"未绑定项目"。
    - **前端 UI**: `OrderPanel.vue` 新建/编辑对话框顶部独立一行 radio (按项目/按工位/按集群站点) **必填**,不进模板字段系统;按 scope 联动显示"项目下拉"/"工位多选"/"集群说明"。集群模式简化为整集群计件,不再要求选站点(主机即代表集群)。
    - **列表绑定列**: 新增"绑定"系统列(可在字段配置里改名/隐藏),三种 scope 用不同 tag 颜色显示;`binding_scope=project AND project_id IS NULL` 的老工单显示红色 ⚠ "未绑定项目, 不会计件"提示。
  - 影响文件: `backend/models/mes_models.py`, `backend/main.py`, `backend/services/work_order.py`, `backend/services/mes_hooks.py`, `backend/services/cluster_collector.py`, `backend/api/mes.py`, `frontend/src/views/MES/OrderPanel.vue`

- [FEAT-310-002] 集群模式工单 = 主机单点 (不需要选目标站点)
  - 需求: 用户反馈"集群肯定是直接选主机,为什么会选某个站点"——对客户来说工单建在主机就是整个集群的代表,不需要分站点细分。
  - 实现: 前端 cluster 模式不再显示 target_stations 多选,改成一段说明文字。后端 `find_cluster_orders` 默认无 station 过滤、按 priority + created_at 取首条 in_progress cluster 工单。`target_stations` 字段在数据库保留(将来想做"分站点工单"还能用),UI 不暴露。
  - 影响文件: `frontend/src/views/MES/OrderPanel.vue`, `backend/services/work_order.py`

## Bug 修复

- [BUG-310-001] 静默 cluster-only 部署下 `_handle_session_start` 的"没找到工单"日志
  - 症状: cluster 模式工单本来就不参与 session_start 绑定(由 cluster_collector 在 box_complete 时直接 +1),但 `_handle_session_start` 找不到工单时会打印 `[MES] Session#X chN 没找到活跃工单`,在纯 cluster 部署下每开一次 session 都刷一条,日志噪声大。
  - 修复: 改为静默(`pass`)。诊断渠道转交给前端工单列表"未绑定"红色 tag + cycle_end 现有的 "Cycle#X 结束但未绑定工件" 日志,不丢可观测性。
  - 影响文件: `backend/services/mes_hooks.py`

## 数据库迁移

- 自动迁移 (启动时通过 `backend/main.py` 的 `migrations` 列表自动 ALTER TABLE):
  - `work_orders.binding_scope VARCHAR(20) DEFAULT 'project'`
  - `work_orders.target_channels TEXT` (JSON)
  - `work_orders.target_stations TEXT` (JSON)
- 老库无破坏性变更,所有老工单默认 `binding_scope='project'`,如果 `project_id` 为空会在前端列表显示红色"未绑定"提示。

## 已知行为差异

- 集群模式下,**同一时刻只让一条活跃 cluster 工单计件**(按 priority + created_at 取首条)。如果客户需要多条 cluster 工单同时跑,需要后续扩展(`target_stations` 字段已经预留)。
- 用户中途把工单从 `draft/pending` 切到 `in_progress` 不会自动绑到当前正在跑的 session — 必须先切到 `in_progress` 再开始检测,或者重启 session。这是 v3.0.0 之前就存在的设计,本版本未改动。

# v3.9.0 (2026-05-23)

## 主线：last_first 结算模式 + 跨周期组类二 + per_item v3.9 五项补丁

> **客户场景驱动**：打螺丝/装配工序中，工件流转到末步时立即出值；操作员中途放弃当前件、直接重做首步即可。本版补足三类老结算模式无法覆盖的客户场景，并把跨周期组的"上下周期成员先后到达"做成正交独立的状态机，避免和顺序结算逻辑互相搅。

## 功能变更

### [FEAT-001] 新增结算模式：末步结算 + 首步开周期 (`last_first`)

- **需求**：客户产线 A→B→C→D 4 步流水。末步 D 一出现立刻判定（不等消失），跳过 D 直接重做 A 表示放弃当前件→旧周期立即 NG，新周期重启。三类老结算模式（first_step / last_step / no_anchor）都无法覆盖这种"末步即结算 + 首步即起新周期"的双锚行为。
- **实现**：在 `source_settlement_mixin.py` 新增 `_process_last_first_mode` 状态机，作为 `_update_step_stats` 的前置过滤层（仅 `pipeline_config.settlement_mode == 'last_first'` 时生效，其它模式严格守门绕过）。状态机 6 条核心规则：
  - **R1 末步锚结算**：D 出现 → 立即结算当前周期 + 进入"等待首步"状态 + D 加入屏蔽集合（防余像反复触发）
  - **R2 首步锚开周期**：在等待首步状态下 A 出现 → 退出等待 + A 启动新周期
  - **R3 D 缺位 fallback**：当前周期已有 A 但缺 D，A 再次出现 → 上周期立刻结算 NG（缺末步）+ 自动建新周期
  - **R4 首步缺位顶替**：State 0/2 + 序列中间步骤先到 → 退出等待 + 该步骤直接顶替成首步
  - **R5 末步余像屏蔽**：D 在屏蔽集合中 → 整帧吞掉，不参与任何后续路径
  - **R6 屏蔽集合释放**：本帧出现组外有意义步骤 → 清空屏蔽集合
- **强互斥（前后端双层校验）**：`last_first` 与 `strict_mode` / 跨周期组 `cross_cycle` / `per_item` / `detection`/`tracking` logic_mode / `custom` 模式且 `base_mode != sequential` 全部互斥。后端 `_apply_pipeline_config` 自动覆盖兜底；前端 `Project/index.vue` 选中后弹橘色约束提示卡 + 自动取消所有步骤的 `strict_order`。
- **隔离性**：UAT 验证 Phase D 显示 `first_step` 模式跑同一剧本时 R3 触发次数 = 0，证明零影响其他模式。
- **影响文件**：
  - `backend/api/source_state_init.py`（新增 `_pending_first_step` 字段）
  - `backend/api/source.py`（`_clear_step_runtime_state` 清字段）
  - `backend/api/source_settlement_mixin.py`（核心状态机 +280 行）
  - `backend/api/source_step_stats_mixin.py`（前置路由钩子）
  - `backend/api/source_project_config_apply.py`（运行时兜底）
  - `backend/api/source_events_check_mixin.py`（跳过基于消失的旧路径）
  - `backend/schemas/project.py`（settlement_mode 加 last_first 枚举）
  - `frontend/src/views/Project/index.vue`（radio + 约束提示 + watch 联动 + 保存校验）
- **关键词**：last_first、末步结算、首步开周期、双锚状态机、R3 fallback、打螺丝放弃件、settlement_mode

### [FEAT-002] 跨周期组（类二）`cross_cycle` 状态机重构

- **需求**：工件出 box 时序"上周期末步 D 余像 + 下周期首步 A"会同时落在一帧或前后帧，老逻辑里两者会被塞进同一个 `simultaneous_groups`，导致上周期没结算下周期就开了。客户希望这两者独立成"跨周期组"，由专用状态机处理上下周期成员的先后到达 + 屏蔽集合 + 等待超时。
- **实现**：新增 `_process_cross_cycle_groups` 函数，独立处理跨周期组的 7 种状态迁移（上周期成员先到、下周期成员先到非空周期、等待中另一侧到达、等待中非组内步骤到达、等待超时、屏蔽集合维护、屏蔽集合一次性清空）。`_process_simultaneous_groups` 只处理类一同帧组，互不干扰。
- **影响文件**：`source_settlement_mixin.py`、`source_step_stats_mixin.py`
- **关键词**：cross_cycle、跨周期组、屏蔽集合、box 时序、上下周期成员、状态机重构

## Bug 修复

### [BUG-001] last_first 模式下旧的"基于消失"结算路径误触发

- **症状**：开发期间发现 D 出现已经触发 R1 结算后，D 消失又会被 `_check_events` 里基于"末步消失"的旧逻辑再触发一次结算，导致同一周期被结算两次。
- **根因**：`_check_events` 的旧分支没有判断 `settlement_mode`，对所有模式都跑一次"末步消失 → 结算"。
- **修复**：在 `source_events_check_mixin.py` 加 `if self.settlement_mode in ('first_step', 'last_first'): pass`，让两种"基于出现"的模式跳过基于消失的兜底路径。
- **影响文件**：`backend/api/source_events_check_mixin.py`

## 已知限制

- `last_first` 不能与 `tracking`/`detection` logic_mode 共存（前后端拒绝保存/激活）
- `last_first` 与 `custom` 模式只能在 `base_mode='sequential'` 时配合（base 为其他时拒绝）
- 跨周期组屏蔽集合复用 `_blocked_labels` 字段，因此 `last_first` + `cross_cycle` 强互斥（屏蔽集合不能同时承担两种语义）

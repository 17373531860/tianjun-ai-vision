# v3.51.1 (2026-08-14)

> 捷昌 B 站双工位虚拟战役补丁版。发 v3.51.0 后按用户要求搭了全虚拟双工位环境
> （synthetic 剧本源跑真实 tracking 管线 + 假 TCP 扫码器跑真实 E 模式协议），
> 60 项断言复现全部现场场景（码状态一致性 / 统一播报 / 扫码门 / 残留状态 /

> 未开启相关功能的客户零差异。剧本归档 `tests/uat/virtual_dual_station/`。

## Bug 修复

- [BUG-001] 「新码强制收旧账」对齐件即结算的挂账周期完全失效
  - 症状: 双工位广播下一箱条码后，上一箱没凑齐的工位账本不收 NG、周期一直挂着；
    下一箱在该工位永远开不出结果，前端显示一直"检测中"
  - 根因: `force_settle_pending_cycle` 非容器分支用 `current_cycle_uuid` 守门；
    v3.50.0a 周期守门把 DB cycle 推迟到结算时才建，等待中的挂账账本 uuid 恒为
    None → 守门静默 return 0，强制结算从未执行
  - 修复: 守门改为只认内存账本活跃标志 `_tracking_cycle_active`
  - 影响文件: backend/api/source_session_lifecycle_mixin.py

- [BUG-002] 扫码器拒码后灯不回亮，产线卡死要人工重启扫码
  - 症状: E 模式下扫了已 OK 的码（strict_ok_dedup 拒绝）/ 冷却期重复码 / 在检
    期间的新码被拒后，扫码器灯保持灭，后续正常条码也扫不进
  - 根因: `mes_hooks._handle_scan` 三条拒绝路径直接 return，从不通知扫码器服务；
    scanner 侧 `_wait_cycle_resume` 等一个永远不会来的周期结算，LON 永不重发
  - 修复: mes_hooks 增加 `_notify_scan_rejected`（三条拒绝路径全接入）；scanner
    增加 `notify_scan_rejected` 按派发通道聚合，**全部**派发通道都拒绝才
    `_rearm_after_full_reject` 清空等待状态重发 LON（部分通道接受则不干扰）
  - 影响文件: backend/services/mes_hooks.py, backend/services/scanner.py

- [BUG-003] 工位组绑死档（force_ng）超时仍给已合格工位播"已合格"
  - 症状: timeout_action=force_ng 语义是"不聚齐全组判 NG"，但超时时已 OK 的
    工位还是收到"等待超时, 本工位已合格"播报，与整体 NG 结论矛盾
  - 修复: `_finalize_aggregation` 超时且 force_ng 时改为对全组统一播报整体
    NG（event_id=2），并把已到成员的 cycle 组结果回写 NG_BY_TIMEOUT；
    fallback_independent 档保持补播已合格不变
  - 影响文件: backend/services/channel_group_coordinator.py

- [BUG-004] 组级 NG 覆盖（pending_override）无过期时间，跨轮污染后续周期
  - 症状: 某工位收到组内 NG 广播后周期迟迟不结算（如物品一直没齐），几分钟后
    完全无关的下一轮结算被残留的 NG 覆盖改判
  - 修复: `_pending_override` 配套 `_pending_override_deadline`（60s TTL），
    `get_pending_override` 过期作废并打日志；`on_channel_removed` 同步清理
  - 影响文件: backend/services/channel_group_coordinator.py

- [BUG-005] 豁免名单 ID 漂移兜底不看标签，换新品种被吞、永不入账
  - 症状: 齐件即结算后旧箱物品拿走，几秒内（max_lost_sec 窗口）同一位置摆上
    下一箱的**另一种**物品 → 新品被当作"旧的已结算物品换了 track_id"永久豁免，
    账永远凑不齐，下一次扫码整箱被强制 NG（现场高频操作：原位换料）
  - 根因: 漂移兜底只按 IoU>=0.6 判定"同一件"，未校验类别
  - 修复: 豁免条目登记 label，漂移转移只认同标签（老条目无 label 兼容匹配）
  - 影响文件: backend/api/source_tracking_mixin.py

- [BUG-006] 统一播报"全部合格"弹的是红色不合格 Toast
  - 症状: 两工位都合格、统一播报触发时，前端弹出红色"不合格"提示（真机截图
    抓到），操作员会误判为 NG
  - 根因: 统一播报走 `fire_external_event_response`，其事件日志 `toast_id`
    默认值写死 'ng'（该路径历史上只服务包装/称重类报警事件）
  - 修复: 默认值按事件类型取——合格事件（id=1）默认 'ok'，其余保持 'ng'；
    事件配置显式配了 toast_id 的照旧优先
  - 影响文件: backend/api/source_event_trigger_mixin.py

## 功能变更

- [FEAT-001] synthetic 剧本源支持 tracking 逻辑模式（测试基础设施）
  - 需求: 捷昌类跟踪模式配置（齐件即结算+扫码门+工位组）此前无法虚拟回归——
    synthetic 路径固定走非跟踪管线，剧本 detections 自带的 track_id 被丢弃
  - 实现: synthetic 取帧后按项目 logic_mode 决定 is_tracking，tracking 项目
    走 `_update_tracking_stats` 真实管线；其余模式行为不变
  - 影响文件: backend/api/source_inference_loop_mixin.py

- [FEAT-002] 虚拟双工位 UAT 剧本归档
  - 内容: `tests/uat/virtual_dual_station/`——假 TCP 扫码器（fake_scanner.py，
    真实 E 模式 LON/LOFF 协议）+ 一键配环境（vsetup.py）+ 4 个剧本 60 断言
    （vcase1 主链路 / vcase2 删码复活 / vcase3 统一播报 / vcase4 残留大扫除），
    README 含启动方法与覆盖矩阵
  - 影响文件: tests/uat/virtual_dual_station/*

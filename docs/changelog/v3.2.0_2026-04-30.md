# v3.2.0 (2026-04-30)

## 修复

- [BUG-320-001] 容器 ID 漂移幽灵箱深层修复 (v3.1.4 阈值过滤之外的兜底)
  - 复现: 客户机 JC1 项目 (单工位, container_box_mode='multi') 拿测试视频
    `d5eb9a3f...mp4` (98s, 30fps) 跑全程, 视频里实际只有 2 个真实物理箱
    + 1 个中途出现又移走的箱子 = 真相 2 OK + 1 NG。但 v3.1.4 跑出 14 NG
    (跳过 3 个空箱后), 因 ByteTrack 在工人手部遮挡时频繁切换 box 的
    track_id, 老条目里有部分装件却被切走, 30 帧 gone-confirm 后入账 NG。
  - 已审计上游层: source_tracking_mixin.py 的 phase2 id_match 已经做过
    `recently_lost re-id` (5 秒窗口 IoU + 外观特征复用 display_id),
    但跨 5 秒接管的边界场景 (工人长时间遮挡 / 泡沫盖一会能识别一会不能)
    接不住, 仍会让一个真实物理箱被切成多个独立 _box_objects 条目。
  - 根因 (代码层面): _update_container_grouping line 76-130 在 box did
    第一次进入 _box_objects 时无条件创建新条目, 没有"重用同位置 gone-confirm
    老条目"的兜底。多箱模式下尤其严重, 单箱模式因 single_box_mode 主箱挑选
    会自动屏蔽其他 box 较少受影响。
  - 修复: _update_container_grouping 新建 _box_objects 条目前加 active 接管
    检查 — 当 `pipeline_config.container_id_drift_merge_iou > 0` 启用时,
    扫已存在 _box_objects 里 `gone_frames > 0 且 ≤ container_id_drift_merge_max_gone_frames`
    的老条目, 找 IoU ≥ 阈值最高的, 找到就复用老 did 继续累计装件 (改写
    `obj.display_id` + `_tracking_display_map[tid]` + 重置老条目 `gone_frames=0`),
    不开新条目。这是 phase2 之外的最后一道兜底。
  - 测试视频离线仿真效果: v3.1.4 (17 settle / 2 OK 15 NG) →
    v3.2.0 启用 IoU=0.5 (12 settle / 2 OK 10 NG, 合并 5 次接管)。
    注: 不附带 retroactive 撤销已 settle 老 NG (验证发现会误吞真实
    "没装齐就移走"的合理 NG, 副作用过大)。
  - 默认值: `container_id_drift_merge_iou=0` (关闭, 老项目升级行为不变)。
    新建项目模板可改 `0.5` 让现场体验改进。
  - 影响文件: `backend/api/source_container_grouping_mixin.py`

## 功能

- [FEAT-320-001] 项目设置加 "ID 漂移合并 IoU" 配置项
  - 实现: 项目设置 → 跟踪选项 → 容器策略行 (容器策略下拉框 + 结算最少件数)
    后面紧挨着加 "ID 漂移合并 IoU" `el-input-number` (min 0, max 1, step 0.05,
    精度 2 位小数), 默认 0 (关闭)。带 tooltip 解释 v3.2.0 active 接管原理 +
    三档语义 (0=关闭 / 0.5=推荐合并 / 0.7+=保守) + 副作用警告 (传送带场景
    可能误合并)。
  - 持久化路径: `pipeline_config.container_id_drift_merge_iou`,
    `pipeline_config.container_id_drift_merge_max_gone_frames` (默认 30,
    跟 gone_confirm_frames 一致, 暂不暴露 UI)。
  - 默认 0 = 老项目升级后行为不变 (兼容承诺)。客户需要时可在项目设置手动
    调到 0.5 启用兜底, 不需要后端配置文件。
  - 影响文件: `frontend/src/views/Project/index.vue`

## 客户现场操作建议

1. **默认行为不变**: 升级后 `container_id_drift_merge_iou` 默认 0 (关闭),
   v3.1.4 的 `container_settle_min_items=1` 阈值过滤继续生效。如果
   v3.1.4 已经把客户合格率拉回到可接受水平, 不动 v3.2.0 配置即可。
2. **现场遮挡严重时启用**: 在项目设置 → 跟踪选项 → 容器策略行最右边的
   "ID 漂移合并 IoU" 调到 0.5, 重启检测即可。这是 phase2 外的兜底,
   只在工人手部遮挡导致 ByteTrack 切 ID 跨 5 秒以上才生效。
3. **副作用提醒**: 传送带场景下 "老箱离开后新箱刚好移到原位置" 可能被误
   合并成同一物理箱, 导致原本的 NG 被新箱接管装齐变成 OK。如果客户机现场
   有这种工艺, 把阈值调高到 0.7+ 让位置必须几乎完全重合才合并。
4. **跟 ByteTrack 调参的关系**: 优先调 `tracking_match_thresh` (现有项目
   设置可改) 到 0.5~0.6, 这能从源头减少 ID 漂移; v3.2.0 的合并是兜底,
   不是治根。如果两个一起调, 先单独调 match_thresh 看效果再决定是否还需
   要启用 v3.2.0。

# v3.10.0 (2026-05-25)

## 主线：用户系统完整闭环 + 彻底删除旧 operators 系统

> **客户场景驱动**：从 v3.0 起一直用的"操作员"系统只是一个**无验证、单选、文件落盘**的简单标签，无法满足多客户对账号鉴权、按角色屏蔽功能、机器对机器接口隔离的真实需求。本版引入**完整的多角色用户系统**（5 张新表 + bcrypt 密码 + token 鉴权 + 端点级权限 + M2M API Key），同时通过 **5 阶段 strangle 模式**彻底删除旧 operators 系统，零数据丢失、零客户感知。**总开关默认关闭**：未启用账号鉴权的客户体验与 v3.9 完全一致。

## 功能变更

### [FEAT-001] 用户系统数据模型 + 后端鉴权内核

- **需求**：建立完整的"账号 → 角色 → 权限"三层数据模型，支持密码哈希、会话 token、磁盘持久化（让后台无 token 进程也能感知"当前登录人"）。
- **实现**：
  - **5 张新表**（`backend/models/auth_models.py`）：
    - `users` — 账号（username/password_hash/display_name/is_active/created_at）
    - `roles` — 角色（code/name/description/permissions(JSON list)）
    - `user_roles` — 多对多绑定
    - `session_tokens` — token 持久化（user_id/token/expires_at）
    - `api_keys` — M2M API Key（key_hash/scope/...）
  - **核心模块 5 个**（`backend/core/`）：
    - `auth.py` (226) — bcrypt 密码哈希 + token 内存池 + 磁盘持久化（`session_tokens.json` / `current_user.json`）
    - `auth_deps.py` (247) — `get_current_user` / `require_perm` / `require_role` FastAPI 依赖
    - `api_key.py` (193) — `require_api_key(scope)` M2M 依赖
    - `permissions.py` (175) — 权限目录 + 通配符匹配引擎（`*` / `module.*` / 精确匹配）
  - **3 个内置角色**（启动时 `main.py:_seed_builtin_roles` 幂等 seed）：
    - `admin` 权限 `["*"]` — 超级管理员
    - `engineer` ~30 条权限 — 工程师，除"账号鉴权 Tab"外全开
    - `operator` 仅 `monitor.view` + `monitor.detection.control` — 操作员，只能按 3 个按钮（开始/停止/待机）
- **关键不变量**：`auth_enabled=false` 时 `get_current_user` 直接返回 `SUPERUSER`，所有 `require_perm` 依赖全放行，**客户体验零差异**。
- **影响文件**：
  - `backend/models/auth_models.py` (174 新增)
  - `backend/core/{auth,auth_deps,api_key,permissions}.py` (841 新增)
  - `backend/main.py`（启动迁移 + `_seed_builtin_roles`）
  - `requirements.txt`（新增 `bcrypt>=4.0.0`，**不**用 passlib 因为版本冲突）
- **关键词**：用户系统、bcrypt、session_tokens、current_user.json、require_perm、auth_enabled、零差异、内置角色

### [FEAT-002] 后端用户系统 API + 前端登录页 + 路由守卫

- **需求**：暴露完整的"登录/登出/启用-关闭鉴权/用户 CRUD/角色 CRUD/权限目录"API，前端集成 token 注入、路由守卫、菜单可见性。
- **实现**：
  - **后端 API**（`backend/api/`）：
    - `auth.py` (274) — `/auth/login` / `/logout` / `/me` / `/status` / `/enable-auth` / `/disable-auth` / `/permissions/catalog`
    - `users.py` (186) — `/users` 用户 CRUD + 角色绑定
    - `roles.py` (136) — `/roles` 角色 CRUD + 权限编辑
  - **前端**：
    - `frontend/src/store/useAuthStore.js` — Pinia store（token 持久化 `tianjun:auth_token` + currentUser + authEnabled + canAccessRoute + hasPermission 通配符匹配）
    - `frontend/src/api/auth.js` — axios 封装 + 请求拦截器（自动注 `Authorization: Bearer <token>`）+ 响应拦截器（401 清 token）
    - `frontend/src/views/Login/index.vue` — 登录页（支持 redirect query）
    - `frontend/src/router/index.js` — `beforeEach` 守卫调 `authStore.canAccessRoute(path)`，未授权跳登录页
- **关键扩展点**：路由权限映射 `ROUTE_PERM_MAP`，新加业务路由不需要改 store（默认放行）。
- **关键词**：auth API、Login view、useAuthStore、Bearer token、路由守卫、canAccessRoute、ROUTE_PERM_MAP

### [FEAT-003] 端点级 `require_perm` 4 轮标记（R1-R4 共 ~160 端点）

- **需求**：所有"写操作 + 危险读操作"必须打权限标记。读操作（视频流、检测状态、Monitor 显示）保持公开，操作员能看不能改。
- **实现**：经过 7 个决策点（D1-D7）的边界讨论后，分 4 轮渐进式标记（避免大块改动同时出错难定位）：
  - **R1**: 项目 / 模型 / 检测控制 / Monitor advanced（清零计数）
  - **R2**: 视频源 / 报警 / 模型 / 系统设置
  - **R3**: MES 工单 / 工件 / 缺陷 / 扫码器 / Gateway / 集群（除 M2M 端点）/ 外设
  - **R4**: M2M API Key 端点（cluster.report/heartbeat、license-cache、mes 接收）走独立的 `require_api_key` 体系
- **D1-D7 关键决策**：
  - D1: 「清零计数」拒绝给 operator → 新加 `monitor.detection.advanced` engineer 起步
  - D2: 报警手动测试端点（trigger/stop/idle-light）→ `alarm.edit` 仅工程师
  - D5: M2M 端点（副机心跳/MES 接收/license 缓存推送）走 API Key 体系，不走 token
  - D6: wmax.py 30+ 端点逐个标 `system.wmax.manage`（粒度精细但重复 30 次）
  - D7: sessions.py 内部端点不标（后端自调时可能无 token，安全起见放开）
- **影响文件**：约 25 个 API 模块文件，~160 个 `dependencies=[Depends(require_perm("..."))]` 注解
- **关键词**：require_perm、端点级权限、R1-R4、D1-D7 决策、wmax、cluster 心跳、license-cache、M2M

### [FEAT-004] M2M API Key 系统

- **需求**：副机集群上报、MES 主动接收、license 缓存推送这类**机器对机器**接口不能用人类 token（无人值守，无法过期管理）。需要独立的"长寿命 + scope 隔离 + 一次性查看"API Key 体系。
- **实现**：
  - **数据模型**（`backend/models/auth_models.py:APIKey`）：`key_hash` (SHA256) / `scope` / `name` / `is_active` / `last_used_at` / `created_by`
  - **后端 API**（`backend/api/api_keys.py` 143）：
    - `GET /api-keys` 列表（不返回原文，仅 hash 前缀）
    - `POST /api-keys` 创建 → 返回原文一次（`tj_<scope>_<32_random>` 格式）
    - `PATCH /api-keys/{id}` 启用/禁用
    - `DELETE /api-keys/{id}` 删除
  - **校验依赖**（`backend/core/api_key.py` 193）：`require_api_key("cluster")` / `require_api_key("license.cache")` 等
  - **4 个 M2M 端点改造**：
    - `POST /cluster/report` + `POST /cluster/heartbeat` → `require_api_key("cluster")`
    - `PUT /system/license-cache` → `require_api_key("license.cache")`
    - `POST /mes/orders/receive` → `require_api_key("mes.receive")`
- **前端 UI**：`Settings/AuthPanel.vue` 新增"M2M API Key 管理"卡片，仅 `system.apikey.manage`（admin）可见
- **关键词**：API Key、X-API-Key、SHA256、scope、M2M、cluster.report、license-cache、一次性查看

### [FEAT-005] Settings AuthPanel 完整 UI

- **需求**：管理员能在 Settings 页一站式完成"启用鉴权 → 创建用户 → 改密 → 编辑角色权限 → 创建 API Key"全流程。
- **实现**（`frontend/src/views/Settings/AuthPanel.vue` 综合面板）：
  - **总开关启用对话框**：必须同时填首个超级管理员（admin_username + admin_password + admin_display_name）
  - **用户列表 + CRUD**：表格展示 + 创建/编辑/禁用/删除 + 角色多选
  - **角色权限编辑器**：分组权限树（按 module 折叠）+ 全选/反选 + 通配符快捷选项 + admin 角色保护性警告
  - **API Key 管理**：创建后明文展示对话框（仅一次）+ 列表展示 hash 前缀 + 启用/禁用 + 删除

- **关键扩展点**：权限树按 `permissions.py:CATALOG` 动态渲染，新加权限只需改一处
- **关键词**：AuthPanel、启用对话框、角色编辑器、API Key 明文对话框、权限树、CATALOG

### [FEAT-006] Navbar / BottomBar 身份显示统一切换（阶段 6）

- **需求**：顶栏 + 底栏旧的"作业员: <inspectorName>"标签必须能感知鉴权状态，避免"作业员 + 账号"同时出现的冗余 / 误导。

## Breaking 变更

### [BREAK-001] 删除旧 operators 系统（5 阶段 strangle）

- **背景**：旧 `operators` 系统是 v3.0 以来的简单标签机制（一张表、6 个 API、文件落盘 `current_operator.json`），与 v3.10 用户系统语义冲突且无价值。本版彻底删除，但通过 **5 阶段渐进式 strangle 模式**保证零客户感知。
- **5 阶段执行**：
  - **阶段 1** — 前端 UI 隐藏：所有 operator 相关 UI 元素加 `v-if="!authStore.authEnabled"` feature flag
  - **阶段 2** — 前端代码清除：物理删除所有遗留代码（Settings 操作员管理 Tab、Monitor 操作员选择器、Data 页操作员过滤器）
  - **阶段 3** — 后端 API 410 Gone：`backend/api/operators.py` 所有 6 个端点返回 `410 Gone`，header `X-Deprecated-Replacement: /api/v1/users`
  - **阶段 4** — 数据归属重定向：`DetectionSession.operator_id` / `DetectionCycle.operator_id` 字段名保留但 FK 改指 `users.id`；`source_session_lifecycle_mixin.py` / `source_routes.py` / `services/mes_gateway.py` / `services/export_context.py` / `api/sessions.py` 7 处查询全部从 `Operator` 改查 `User`；导出 / MES 字段名 `{operator.*}` 保留，语义改为"当前登录用户"；新加 `set_current_active_user(user_id)` / `get_current_user_id()` 写 `current_user.json` 给后台无 token 进程
  - **阶段 5** — 旧表 + 类彻底清除：
    - `backend/models/models.py` 删除 `Operator` 类 + `relationship`
    - `backend/api/operators.py` 完全清空（仅留 410 Gone 骨架 74 行）
    - `backend/main.py:migrate_database()` 新加 `DROP TABLE IF EXISTS operators` 自动迁移
    - `tests/test_alarm_and_operator.py` 删除 `TestOperatorPersist` 类
- **兼容性保证**：
  - 老 `DetectionSession.operator_id` 历史数据中**不变**（FK 改指 `users.id` 后历史值变成"悬空指针"，但 FK 用 `ondelete=SET NULL` 不会引发约束错误）
  - 导出模板 `{operator.*}` 字段名**继续可用**，新数据指向登录用户
  - MES payload `{operator.*}` 字段名**继续可用**，无需客户改模板
- **UAT 验证**：5 阶段累计 ~80 项 UAT 全过，phase5 26/26 + 回归 phase3 20/20 + phase4 41/41 全通
- **关键词**：strangle pattern、410 Gone、operator 删除、DROP TABLE、operator_id 重定向、零客户感知、ondelete SET NULL

## 已知限制

- **首个超管丢失场景**：admin 是唯一拥有 `*` 权限的角色；如果首个 admin 用户被删除（DB 直改），客户需要重启后端走"首次启用"流程重新创建。**前端 UI 已禁止删除最后一个 admin 用户**，但 DB 直改不防。
- **`session_tokens` 持久化**：token 落盘 `session_tokens.json`，文件被删后所有用户会被强制登出。**重启不会清 token**（持久化的全部理由）。
- **M2M API Key 原文丢失**：创建时原文仅返回一次，丢失后需重新创建。**DB 不存原文，无法找回**。
- **DEV 环境 vs 客户机权限对齐**：开发期间常需要客户端关闭 auth 跑测试，**所有 UAT 脚本前置都强制 `auth.enabled=false`**，跑完不自动启用，避免污染开发环境。
- **`feat/plugin-system` 长期分支需吸收本版**：插件系统 + DB 迁 PG 分支与 user-system 都改了 `core/`，合并时需对齐 `migrate_database()` + auth 模块。

## 客户升级说明

**对所有客户**（无论是否要用账号鉴权）：
1. 升级到 v3.10.0 后，启动时会自动执行 `DROP TABLE operators`，老 operator 数据**会丢**
2. `DetectionSession.operator_id` / `DetectionCycle.operator_id` 历史值变成"悬空指针"，导出 / MES 推送中 `{operator.*}` 字段会变成空字符串（不会报错）
3. **默认体验不变**：`auth.enabled=false`，所有人 = 隐式超级管理员，全功能开放

**想用账号鉴权的客户**：
1. 进 Settings → 账号鉴权 Tab → 点"启用账号鉴权"
2. 在对话框里填首个超级管理员（username + password + display_name）
3. 启用成功后跳转登录页，用刚才的账号登录
4. 进 Settings → 账号鉴权 → 创建工程师/操作员账户 + 分配角色
5. 操作员账户默认仅可见 Monitor + 3 个按钮（开始/停止/待机），其他菜单全部自动隐藏

**关闭账号鉴权**：admin 登录后进 Settings → 点"关闭账号鉴权"，恢复零差异默认体验

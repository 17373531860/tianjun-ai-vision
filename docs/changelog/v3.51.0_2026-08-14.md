# v3.51.0 (2026-08-14)

> 主题：**捷昌 B 站双工位整改批次**——把 v3.50.0a 现场热补丁全量收编进正式版（堆损坏崩溃治本 / E 码-合格-码 / 扫码后才计数 / 广播全 OK 亮灯 / channel-config 绑定保护 / 齐件即结算周期守门等 17 条），并新增四项现场闭环修复：开机黑屏收尾兜底、激活项目收养策略可配、工位组统一播报（两工位都合格才一起报 OK）、数据清理联动解封条码。**新增项全部默认关或保持存量行为，不配置零差异。**

## Bug 修复

- [BUG-013] 修复: 开机第一时间黑屏，部分工位视频源恢复被打断后再也不起
  - 症状: 双工位开机后监控页黑屏；日志显示 ch1 恢复成功后紧跟一串 `fully stopped and released resources`，ch0 的自动恢复被打断且无后续重试
  - 根因: 后台恢复线程整个恢复过程长达 ~18s（模型加载+CUDA 预热+逐工位开相机），期间前端首屏"激活绑定项目"会停输入源，与恢复线程抢同一台相机；原有的 4 秒二次恢复窗口远小于竞争窗口，抢输后直接放弃
  - 修复: `auto_restore_video_sources` 尾部新增**收尾兜底轮**——恢复流程全部走完后再等 5s，把"已配源但没在跑"的通道最后拉一次，并补一轮自动开始检测；幂等，全部在跑时零动作
  - 影响文件: backend/main.py

- [BUG-014] 修复: 数据页删了某条码的所有记录后，强制去重仍永久拒绝该码重扫
  - 症状: 现场删除某码全部记录后重扫，仍被"该条码已判合格，已拒绝（强制去重）"拦下；两工位广播同一码时出现一边"已登记"一边被拒的错位
  - 根因: `strict_ok_dedup` 查的是 MES 工件表 `status=ok`，数据中心清理（clear/all、clear/range）只删 session/cycle/step 记录、从不动工件状态，"删记录=可重来"的用户心智不成立
  - 修复: 清理端点联动 `_unlock_ok_workpieces`——被删周期（经 WorkpieceInspection）关联的 status=ok 工件重置回 registered；全量清理解封全部 ok 工件；响应里返回 `workpieces_unlocked` 数量；失败只打日志不阻断清理
  - 影响文件: backend/api/sessions_maintenance.py

## 功能变更

- [FEAT-008] 新增: 「启用项目时自动接管未绑定工位」开关（系统设置·显示设置页，默认开=存量行为）
  - 需求: 多工位下某通道绑定曾被 bug 抹掉（v3.50.0a BUG-011 的历史遗留脏数据）后，任何一次"启用项目"都会把该无绑定工位收养进当前项目并写死持久化绑定，现场感知为"删了个标签，两个工位的项目又都变成小件了"
  - 实现: SystemConfig KV `activate.adopt_unbound`（默认 '1'）；关闭后 `_sync_project_config_to_channels` / `_reload_model_for_active_project` 只同步"已显式绑定本项目"的通道，不收养无绑定通道、不改写任何绑定。新端点 `GET/PUT /api/v1/projects/activate-config`（声明在 `/{project_id}` 之前）。启动期 `auto_load_active_project` 的运行时兜底不受影响（不落盘）
  - 影响文件: backend/api/projects.py, frontend/src/views/Settings/index.vue

- [FEAT-009] 新增: 工位组统一播报 `unified_ok_report`（工位组互通面板，仅 synchronized_all_ok 策略可配，默认关）
  - 需求: 捷昌 B 站一把广播枪覆盖双工位清点同一箱，要求"两个工位都检测合格才一起报合格放行"——扫码器亮灯 v3.50.0a 已做到全 OK 才亮，但 OK 事件/灯/语音/前端 toast 仍各报各的
  - 实现: 开关存 `ChannelGroup.plugin_data`（不动主 schema、无迁移）；`_trigger_event` 里个体 OK 的用户感知面（toast `show_notification`、`_dispatch_event_alarm`）被抑制——结算/计数/落库/MES 全部照旧；组聚齐全 OK 后 `_finalize_aggregation` 对全部成员统一 `fire_external_event_response(1, remind_only=True)` 播一次合格（复用各通道事件1 配置的灯/语音/toast，不重复计数）；超时 fallback 时对已 OK 成员补播个体合格防"永远没反馈"；NG 永不抑制（安全侧，且 all_ok 组的 NG 广播照旧）。与扫码器"广播全 OK 才亮灯"天然同拍
  - 影响文件: backend/services/channel_group_coordinator.py, backend/api/channel_groups.py, backend/api/source_event_trigger_mixin.py, frontend/src/views/Settings/ChannelGroupPanel.vue

- [FEAT-010] 收编: v3.50.0a 现场热补丁全部 17 条进正式版（BUG-001~012 / FEAT-001~007，明细见 CHANGELOG 的 v3.50.0a hotfix 段）——堆损坏 0xC0000374 治本（原子释放+通道生命周期锁）、E 码-合格-码扫描模式、扫码后才计数 `tracking_scan_gate`、广播枪全 OK 才亮灯、channel-config merge 不再抹 project_id 绑定、齐件即结算周期守门 `_soc_ensure_db_cycle`、`link_to_cycle` 幂等、相机打开候选后端×退避等。发正式版后现场不再依赖 hotfix.py 重绑路径

## 已知问题 / 现场配置提醒（发版说明必须带）

- 第二台扫码器 192.168.0.2 现场全程连接超时，且其"绑定工位"配置为 2（系统只有工位 0/1）被自动降级到 ch0——需现场检查网线/IP，并在 MES→扫码器面板把绑定工位改对

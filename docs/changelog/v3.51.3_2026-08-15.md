## Bug 修复

- [BUG-001] Windows 摄像头枚举无物理去重，同一台相机列成两台，双工位同选互抢到超时
  - 症状: 现场接 2 个 USB 摄像头 + 工控机自带 1 个，「刷新设备列表」列出 4 个，
    第 3、4 项是同一台物理机；双工位分别选中 3 和 4 保存启动，后开的工位卡到
    前端 60s 超时才报笼统的"被占用"。枚举本身也慢（逐 index 盲试开）。
  - 根因: `_detect_cameras_windows` 用 `cv2.VideoCapture(i, CAP_DSHOW)` 盲扫
    index 0~4，能开就算一台——同一台 USB 相机在 DirectShow 注册多个 filter
    （带 IR 副摄的复合设备/驱动重复注册）时必然重复；列表名字全是"摄像头 N"
    无法分辨；且枚举时试开设备还可能干扰其他工位正在采集的相机。
  - 修复: Windows 枚举改为优先用打包内 ffmpeg `-list_devices -f dshow` 列设备
    （快、带设备真名、不试开），按 USB 设备路径 `(vid, pid, serial)` 去重同一
    物理机的重复 filter（两台同型号相机 serial 不同不会误合并）；"使用中"
    标记从只看 ch0 扩到全部工位；ffmpeg 不可用/解析失败/非 Windows 自动回退
    老试开法，零行为差异。
  - 测试: `tests/test_camera_enum_dedup_v3513.py` 解析器两代 ffmpeg 格式 +
    现场剧本去重（4 列 3）+ 同型号双机不误并 + 兜底回退，17 条全绿；
    Mac 真机枚举端点实调 + 前端 Source 页真浏览器验证"(索引 0, 使用中)"渲染。
  - 影响文件: backend/api/source_routes.py
  - 附注: 设备路径已具备"按唯一标识绑相机"的数据基础，v3.51.2 已知问题里的
    "索引漂移开错相机"立项时可直接复用。

- [BUG-002] 双工位选同一摄像头 index 无预检，后开方卡满重试循环逼近 60s 超时
  - 症状: 与 BUG-001 现场同一现象的另一半——即便真是同一 index，后开工位
    也要走满 3 轮 DSHOW+MSMF 退避 + FPS 探测才失败，报错不指明被谁占。
  - 根因: `_start_camera_locked` 没有跨通道占用预检；通道生命周期锁只防同通道
    并发，不防两工位抢同一物理设备。
  - 修复: 打开相机前先查其他工位是否正持有同一 device_index，命中立即抛
    "摄像头 N 正在被工位 X 使用，请先停止该工位或选择其他摄像头"；预检挡在
    `self.stop()` 之前，不会为一次注定失败的打开先停掉本工位旧源。
  - 测试: Mac 真机 E2E——ch0 开真相机 1.9s 成功，ch1 抢同一台 **14ms** 明确
    报错，ch0 采集毫发无损（is_running=True、监控页 FPS 28 画面正常）。
  - 影响文件: backend/api/source_camera_start_mixin.py

- [BUG-003] SQLite 侧车文件损坏后 `disk I/O error` 无任何处理，后端 down 掉且再也拉不起来
  - 症状: 现场切换输入源时报 SQLite `disk I/O error`（"库文件可能被锁了"），
    后端 down 掉或重启拉不起来。
  - 根因: 强杀（Electron 兜底 taskkill /f）/断电后 `-wal/-shm` 半写入损坏，
    之后任何连接一碰库就报错；全仓只兜了 locked/busy，`disk I/O error` 原样
    炸穿；启动时 import 期 `create_all` 直接挂死 = "软件拉不起来"；且退出
    链路从不做 WAL checkpoint，损坏窗口常开。
  - 修复: ① 启动 `create_all` 捕获可自愈的 SQLite I/O 故障（Windows 文案
    `disk I/O error` / POSIX 同类损坏文案 `unable to open database file`），
    把 `-wal/-shm` 隔离为 `.corrupt-<时间戳>`（保留现场不删）后重试一次——
    主库含最后一次 checkpoint 前全部数据，只丢 WAL 未合并的最近几笔，起得来
    远好于起不来；② 退出钩子收尾加 `PRAGMA wal_checkpoint(TRUNCATE)`，把
    未合并写入落回主库并截断 WAL，把强杀损坏窗口缩到最小。PG 方言不受影响。
  - 测试: Mac 真库 E2E——人工损坏 -wal 复现打不开 → 真后端启动自愈
    （日志：隔离 `sql_app.db-wal.corrupt-20260815_082642` → 自愈成功）→
    API 读写正常（POST 项目 201 落库）→ SIGTERM 退出 checkpoint 把 12KB WAL
    清零。单测覆盖隔离函数不动主库/无侧车 noop/退出钩子含 checkpoint。
  - 影响文件: backend/main.py
  - 附注: 现场该报错的根治方向仍是切 PG（多工位并发写离开 SQLite 单文件锁），
    本版把 PG 组件真正交付（见 FEAT-001）；SQLite 自愈是存量机器的兜底防线。

## 功能变更

- [FEAT-001] CI 安装包收编嵌入式 PostgreSQL 可选组件（修复 v3.49 交付缺口）
  - 需求: v3.49 的 installer.iss 写了 `#ifdef IncludePostgres` PG 组件与完整
    初始化流程（initdb→注册服务→建库→写 db_config.json），但 CI 打包只传
    `/DMyAppVersion`，从未传过 `/DIncludePostgres`——v3.49~v3.51.2 所有发出的
    安装包里根本没有 PG 选项，用户以为切了 PG 实际全程跑在 SQLite 上。
  - 实现: build.yml 新增 "Stage PostgreSQL portable" 步骤——下载 PG 16.15
    Windows x64 官方便携包（3 次重试，失败硬红阻断发版，不允许再次静默发出
    无 PG 的包）、裁掉 pgAdmin/StackBuilder/symbols/doc/include 只留
    bin/lib/share、铺到 `electron\dist\pg-portable\` 并校验 `bin\initdb.exe`；
    ISCC 编译加 `/DIncludePostgres`。安装界面出现 "Install embedded
    PostgreSQL database" 可选项（默认不勾选，行为与历史一致）。
  - 测试: PG 通路在真 PG 16 库上全链路验证——后端以 DATABASE_URL 启动
    create_all 建 53 张表、API 写入 201、psycopg2 直查数据在、db-info 显示
    postgresql；CI db-matrix 同款 PG 测试子集本地真库 710 passed。
  - 影响文件: .github/workflows/build.yml

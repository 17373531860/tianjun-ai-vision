# v3.1.4 (2026-04-29)

## 修复

- [BUG-314-001] 修复容器多箱模式幽灵箱误报 NG (客户机现场合格率 30% → 真实合格率)
  - 复现: 客户机 jc 项目 (单工位, container_box_mode='multi') 录屏显示
    检测 126 / OK 38 / NG 85, 合格率 30.2%; 已结算 92 (OK 26 / NG 67),
    NG 占 73%。NG TOP3 三个步骤 box / cable_hook / pillar_no_core 同 NG 率
    完全相同 53.x%。50 秒一口气结算 6 个箱子里 5 个 NG (画面里只有 1 个真实
    箱子在流转)。
  - 根因 (代码层面已审计 source_container_grouping_mixin.py 全文):
    1. 工人遮挡瞬间 ByteTrack 给真箱新 track_id => display_id 也变 =>
       _update_container_grouping line 60-75 把它当新 box 启动新条目。
    2. 老条目还在 _box_objects 里, 等 30 帧 gone-confirm。期间老条目
       item_class_counts={} 永远是空 (新物品全归到新 box_did 名下)。
    3. 30 帧后 _settle_box 触发, expected_no_container 整列 missing =>
       is_ok=False => 入账 NG。这就是为什么 NG TOP3 三个步骤 NG 率永远完全
       相同 = 这些 NG 箱子都被当"全步骤缺件"。
    4. 50 秒批量结算 = 多个老条目集中到达 gone-confirm, 一齐入账 NG。
  - 修复: _settle_box 入口加阈值前置过滤 — 当 box.item_class_counts 总件数
    < pipeline_config.container_settle_min_items (默认 1) 时, 直接 pop
    不入账, 既不计 OK 也不计 NG, 不写 StepRecord, 不 trigger_event。这从
    根本上让"幽灵空箱"无法污染 OK/NG 计数。
  - 关键边缘情况: pipeline_config.container_settle_min_items 显式置 None
    或空字符串时, 不会 fallback 到 0 (那样会**关闭**过滤), 而是 fallback
    到默认值 1; 阈值 = 0 是显式关闭过滤 (退化到 v3.1.3 行为, 仅排查回归用)。
  - 影响文件: `backend/api/source_container_grouping_mixin.py`

## 功能

- [FEAT-314-001] 容器结算最少件数阈值 UI 可调
  - 实现: 项目设置 → 跟踪选项 → 容器策略下加 "结算最少件数" `el-input-number`
    (min 0, max 100, step 1, 默认 1), 带 tooltip 解释幽灵箱原理与三档语义
    (默认 1 / 关闭过滤 0 / 现场遮挡严重时调高)。
  - 默认值: 1 (至少装 1 件才视为真箱)。客户升级后无需手动配置即可消除
    幽灵 NG; 如需还原 v3.1.3 行为可手动设 0 (不推荐, 仅作排查回归用)。
  - 持久化路径: `pipeline_config.container_settle_min_items`, 与
    `force_settle_pending_cycle(min_items)` 兼容互补 (前者 _settle_box 兜底,
    后者 broadcast 主工位强制结算时跳过空箱不立即结算)。
  - 影响文件: `frontend/src/views/Project/index.vue`

## 客户现场操作建议

1. **合格率回升验证**: 升级到 v3.1.4 后, 重启应用, 看 jc 项目的合格率应
   从 30.2% 直接跳到接近真实工艺合格率 (估计 70%~90%, 取决于实际漏装率)。
   NG TOP3 三个步骤同 NG 率 53.x% 这个特征会消失, 转为各步骤独立 NG 率。
2. **件数阈值**: 默认 1 件足够过滤掉空箱幽灵。若现场遮挡极严重导致**真箱**
   也被切成多个 box_did 且每个都 < 3 件, 可酌情调到 3 让真箱也能跨 ID
   合并; 但更推荐先把 ByteTrack 匹配阈值 (v3.1.2 起可调) 调到 0.5~0.6
   减少 ID 漂移源头。
3. **多工位场景**: 双工位/四工位现场同样吃这个修复, 不需另配 — `_settle_box`
   是所有结算路径的最终终点, 无论是 gone-confirm 触发还是 broadcast primary
   force_settle 触发, 都会走阈值过滤。
4. **若需恢复 v3.1.3 行为**: 项目设置把"结算最少件数"调到 0, 仅作排查回归
   用, 不建议生产环境长期使用。

## 功能变更

### [FEAT-001] 周期性强制动作支持"按时间触发"
- **需求**：客户产线生产间断（工人下班 / 吃饭 / 切换工序），整个周期不会推进，但仍处于"检测中"状态。原有按 cycle 数触发的强制保养动作（清洁治具 / 上油 / 校准）此时**不会**触发提醒——客户希望"超过 N 分钟没做就报警"。
- **实现**：
  - **Schema 扩展**：`pipeline_config.periodic_actions[*]` 新增字段 `time_interval_seconds`（=0 关闭，>0 启用按时间触发）。与现有 `interval`（按次数）**OR 关系**，谁先到期谁先报警；做 trigger_step 时同时重置两个维度。`interval=0 + time_interval_seconds=0` 的规则视为无效会被跳过。
  - **后端运行期**：
    - `source_periodic_actions_mixin.py` 新增状态变量 `_periodic_last_done_ts: Dict[str, float]`（懒初始化在 `_apply_periodic_actions`，与现有 `_periodic_counters` 同模式）。
    - 新方法 `_check_periodic_actions_time_only(now)` 仅检查时间维度，由 `inference_loop` 主循环每 5 秒 throttle 调一次（与现有 60s 缓存清理 / 600s GPU 清理同款机制）→ 即使生产停了，只要 detection 还在跑，时间维度仍会主动报警。
    - 触发判定收口到 `_maybe_emit_periodic` 同时支持 count + time 两维度，cooldown / once / every_cycle 节流走新版 `_should_trigger_overdue_v2`。
    - `_check_periodic_actions`（cycle_end 路径）完成动作时**同时** reset counter 和 last_done_ts。
    - `reset_stats` / `reset_periodic_counter` / `_check_periodic_actions_on_first_step` 三处都同步刷新 `_periodic_last_done_ts`。
  - **持久化升级**：`DATA_DIR/counters/project_X_chY_periodic.json` 从 `{rule_id: counter}` 升级为 `{"counters": {rule_id: counter}, "last_done_ts": {rule_id: ts}}`。`_restore_periodic_counters` 兼容老格式（自动识别后向兼容读）。
  - **状态返回**：`get_periodic_actions_status` 新增字段 `time_interval_seconds / time_elapsed_seconds / time_remaining_seconds / time_state / count_state`，整体 `state` 字段取次数 vs 时间维度中**更严重**那个（severity: ok < due < overdue）。
  - **前端 Project 页**：`周期性强制动作`卡片新增"超时秒数（多少秒没做就报警，0=关闭）" `el-input-number`（最大 86400 秒 = 24 小时）；`initProjectDefaults` / `addPeriodicAction` / `handleSaveProject` 三处同步默认值与序列化；老项目缺字段时默认 0 = 行为完全不变。
  - **前端 Monitor 页**：`周期性强制动作`卡片状态行追加时间维度展示（`⏱ Xs / Ys + 还有/超期`），进度条按"次数 vs 时间维度更接近爆表那个"渲染（`getPeriodicProgress`），新增 `formatRemainingTime` 工具把秒数渲染为 `45s / 32m15s / 1h10m` 格式。reset 按钮乐观更新时也清掉 `time_*` 字段。
- **完全向后兼容**：老项目不动，缺字段都按 0 / disabled 处理，行为与 v3.7.3 一致。
- **测试**：
  - 单元测试 `tests/test_periodic_actions_v374_time.py`（11 个用例）：覆盖解析 / 校验 / 时间触发 / cooldown 节流 / 完成动作同步重置 / 老项目兼容 / 持久化新旧格式 / 状态返回。

## Bug 修复

### [BUG-001] 开发机 `./start_frontend.sh` 在 Node 18 下报 `crypto.hash is not a function`
- **症状**：开发同事跑 `./start_frontend.sh`，报错 `TypeError: crypto.hash is not a function`，前端起不来。
- **根因**：项目 Vite 升到 7.x 后要求 Node ≥ v20.19，但很多开发机系统 node 仍是 18（Ubuntu 24.04 默认 v18.19.1）。脚本没做版本检测就直接 `npm run dev`。
- **修复**：`start_frontend.sh` 启动前探测 node 主版本，< 20 时自动通过 nvm 切到已装的 v20/22/24 最高版本：
  - 只匹真实已装的版本（排除 nvm ls 输出里 `lts/krypton -> v24.15.0` 这种**未真正安装**的别名行）。
  - 用 `nvm use --delete-prefix` 处理某些 .npmrc 配置导致 nvm use 退出码非零的情况，切换后**重新校验** node -v 来判定是否真生效，不看退出码。
  - 没装 nvm 的客户机 / 已装 node ≥ 20 的环境**完全不受影响**，走原路径。客户机走 Electron 打包好的 dist，根本不会跑 vite，与本修复无关。
- **影响文件**：`start_frontend.sh`

## 已知问题 / 后续

- **SE9 (Sophon BM1688) ARM64 适配**：本次发版**不带** SE9 改动，相关代码隔离在 `feature/se9-arm64` 分支。SE9 上的 sophon-sail 集成、bmodel 转换、装机脚本仍在调试中，待客户机端走完完整 UAT 后再单独发版（参考 `docs/SE9_部署指南.md`）。Windows 客户不受影响。
- **inference loop time_only 5s 节流**：节流粒度选 5s 是和现有 `last_debug_time` 同款；客户希望更精细 (1s) 的话需要权衡 inference 主循环 CPU 占用，目前默认 5s 与"分钟级" / "小时级"超时阈值匹配良好。

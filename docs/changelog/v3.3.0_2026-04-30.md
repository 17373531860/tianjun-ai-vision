# v3.3.0 (2026-04-30)

## 功能

- [FEAT-330-001] 扫码闭环结算 (码-码闭环) — 扫码 A 开周期, 扫码 B 结算 A 并开新周期
  - 复现痛点: 客户场景下容器装件节奏快, 物理消失 / ROI 退出 / gone-confirm 超时
    等 cycle 触发条件经常误触发或漏触发 — 装到一半挪一下盒子被当成 ROI 退出 NG;
    装齐后还没扫码就被超时强制 NG; 单箱模式 + ByteTrack 切 ID 容易漏判。客户希望
    把 cycle 节拍交给"扫码工件号"这件最可靠的事 — 扫一次开周期, 扫第二次就说明
    前一件已结束, 立刻把前一件按"是否曾装齐过"结算 OK / NG。
  - 已审计上游层: 现有 bind_timing 只支持 `mid_cycle` (扫码立即绑当前周期) 和
    `cycle_start` (扫码后等下个周期开始绑), 都依赖检测引擎自己探测 cycle 边界
    (物理消失 + gone-confirm); 扫码事件只用来"绑工件号", 不直接驱动 cycle 节奏。
    当工人节奏与 gone-confirm 阈值 / ROI 设计不匹配, 就会出 NG 错判, 客户得不停
    调阈值。
  - 实现 (后端):
    - `mes_models.py / scanner.py / api/scanner.py` 新增字段
      `scan_pair_max_wait_sec INTEGER DEFAULT 0` (扫 A 后等待 B 的最大秒数,
      0 = 不超时), main.py 加自动 migration。
    - `mes_hooks.py` 新增 scan_pair 状态机:
      - `_scan_pair_active[ch] = {serial_no, wp_id, scanned_at}` 当前窗口的开始码;
      - `_scan_pair_timeout_timers[ch]` 每窗口的 threading.Timer 超时定时器;
      - `_handle_scan_pair_event()` 是 `_handle_scan` 在 bind_timing='scan_pair'
        分支的入口 — 同码二次扫软忽略 + 推 dup_warning toast / 不同码触发结算
        前一窗口 + 起新窗口 + 重新起超时定时器;
      - 多工位广播下用 `_scan_pair_resolve_broadcast_channels(ch)` 解析共享窗口,
        broadcast_chs[0] 做主分发, 兄弟 ch 的同事件 dispatch no-op (一个扫码事件
        会被 scanner.py 对 N 个广播 channel 各调一次, 必须去重);
      - 超时回调 `_on_scan_pair_timeout(ch)` 强制 force_ng=True 收尾窗口;
      - `settle_scan_pair_for_stop(ch, discard)` 提供给前端"停止/待机弹窗"调用。
    - `source_session_lifecycle_mixin.py` 新增 `settle_for_scan_pair(force_ng,
      reason)` — 容器模式遍历所有 _box_objects 按 sticky `was_complete` 判 OK/NG
      (force_ng=True 时一律 NG); 非容器模式按 sticky `_tracking_was_complete`
      判定。复用 `_force_settling_in_progress` 防重入标志。
    - `source_container_grouping_mixin.py`:
      - `_box_objects[did]` 加 `'was_complete': False` 字段, sticky — 一旦 is_complete
        曾经为 True 永久 True, 直到 _settle_box() pop 出去;
      - 在 scan_pair 模式激活时 (查询 mes_hooks.is_scan_pair_mode), 关掉 gone-confirm
        触发的自动 `_settle_box` (扫码节拍接管), 仅维护 sticky was_complete flag,
        但仍刷 last_seen / 重置 gone_frames 等基本状态;
      - `_settle_box` 加新关键字参数 `via_scan_pair: bool` + `scan_pair_force_ng: bool`,
        OK/NG 判定切换路径: scan_pair 路径用 was_complete (允许工人扫前从箱里拿件
        再扫下一码, 最后帧件数可能不齐, 但只要"曾齐过"就算 OK), 老路径维持
        current_is_ok 不变, 完全保持 v3.1.x 行为。
    - `source_tracking_mixin.py` 在 `_update_tracking_stats` 帧末检查 expected_items
      是否全部覆盖, 是则置 `_tracking_was_complete = True` (sticky); 与 _rebuild_checklist
      的 max(tracking, stack) 合并策略保持一致。
    - `source_checklist_mixin.py._settle_counting_cycle` 加 `_scan_pair_settle_hint`
      识别 — 此标志由 settle_for_scan_pair 设置, 此时 OK/NG 判定切到
      `_tracking_was_complete` (sticky), 而不是基于当前帧的 missing/extra。
    - `source.py._reset_counting_cycle` + `source_state_init.py` 清掉 sticky flag
      防止跨周期串台。
  - 实现 (前端):
    - `ScannerPanel.vue` "绑定时机"下拉新增第三项 `码-码闭环` (value=`scan_pair`),
      切换时自动锁定 `scan_required=on` / `scan_mode≠C` (single_per_cycle)
      / `late_scan_bind_window_sec=0`, 并弹一次 ElMessage.info 提示。同时露出
      `scan_pair_max_wait_sec` el-input-number 让用户配置超时。
    - `Monitor/index.vue` 在 stopDetectionHandler / standbyHandler /
      stopDetectionForChannel / standbyForChannel 入口前调
      `confirmScanPairBeforeStop(ch)` — GET /scanner/scan-pair/active 查到
      active_serial 非空就弹 ElMessageBox: [结算 (默认)] / [丢弃] / [取消],
      调 POST /scanner/scan-pair/stop 收尾。
    - `handleScanToast` 识别 `scan_pair_dup_warning` 标志, 单独弹
      ElMessage.warning("重复扫码: SN_XXX - 等待新码")。
  - 实现 (API): `backend/api/scanner.py` 新增两条 REST:
    - `GET /scanner/scan-pair/active?channel_id=N` 返回当前窗口的开始码
    - `POST /scanner/scan-pair/stop` body `{channel_id, discard}` 收尾窗口
  - 互斥保护: scan_pair 模式与 mid_cycle / cycle_start 完全互斥 — 进入 scan_pair
    时 _handle_scan 直接 return, 不再走老 bind_timing 分支; 离开 scan_pair 时
    上一窗口的 timer 在 on_channel_removed 里被清理。
  - 默认值: 老项目升级后 `bind_timing` 仍是 'mid_cycle', 行为不变 (兼容承诺)。
    客户需要时手动切到"码-码闭环"启用。

## 客户现场操作建议

1. **默认行为不变**: 升级后所有现有扫码器仍是 `mid_cycle`, 行为完全不变;
   不主动切到"码-码闭环"则零影响。
2. **启用步骤**: MES → 扫码器 → 编辑 → "绑定时机"下拉切到"码-码闭环",
   保存; 系统会自动启用先扫后检 / 关闭迟到补绑 / 锁掉 C 单次/周期扫描。
   再设一个 "超时秒数" (建议 30~60 秒, 0 = 不超时), 重启检测即可。
3. **判 OK/NG 逻辑**: 容器场景下"曾经装齐过"就算 OK, 即便扫第二码时工人已经
   从箱里拿走了几件 — 这跟传统 cycle 周期判定 (基于最后一帧或 gone-confirm
   触发那一刻的件数) 不同, 客户得跟产线工人对齐这个新约定。
4. **多扫码器场景**: 不支持"一工位多扫码器" (不在原拓扑里); 但"一扫码器
   广播多工位"完全支持 — 所有广播工位共享同一码窗口, 一码同时开 N 个工位,
   下一码同时结算 N 个工位。
5. **超时配置**: 默认 0 (不超时), 节拍稳定的工位推荐保留默认; 节拍可能漏扫
   的工位 (例如夜班 / 新工人) 设 30~60 秒, 漏扫时被强制 NG 提醒补救。
6. **停止/待机时**: 系统会弹窗询问"最后一码是结算还是丢弃" (默认结算)。
   选丢弃 = 这枚工件不计入产能; 选结算 = 按曾齐过判 OK/NG。

## Bug 修复

- [BUG-001] 相机格式探测 Strategy 3 在 macOS 误入 V4L2 重开，留死句柄致永久 "No Source"
  - 症状: 启动输入源接口返回成功、`is_running=True`、采集心跳照跳、检测状态一切正常，
    但监控页画面永远是黑底 "ChN - No Source" 占位图；快照恒为 ~10KB 占位 JPEG。
    与哈金森现场"检测界面加载不出画面，但是又能检测到步骤"同款表现。
  - 根因: `_start_camera_locked` 格式探测 Strategy 3 的守门写的是
    `platform.system() != "Windows"`（"非 Windows 就按 Linux 处理"），macOS 误命中：
    AVFoundation 明明正常出帧（实测 30fps），仅因 fourcc 非 MJPG 就被 `release()`，
    再用 macOS 上不存在的 `CAP_V4L2` 后端重开必然失败；失败分支只有
    `if isOpened()` 没有 else 兜底，揣着 `isOpened()=False` 的死句柄继续往下走完
    全部启动流程 → 采集循环里 `read()` 永远返回 False（0ms 即失败），
    `current_frame` 永不更新，进入"接口成功但永远无画面"的僵尸态。
  - 修复: ① 守门收紧为 `platform.system() == "Linux"`（V4L2 重开本来就只对 Linux
    有意义）；② V4L2 重开失败时走 `_open_camera_capture` 候选兜底把摄像头拿回来，
    拿不回来显式抛错；③ 新增终检——任何策略分支走完，句柄必须 `isOpened()`，
    否则显式抛"打开后句柄失效"异常，宁可报错也不进僵尸态。
  - 测试: `tests/test_camera_open_fallback.py` 新增 2 条守门断言
    （Strategy 3 仅 Linux / 终检拒绝死句柄），相机回归 17→19 条全绿；
    Mac 真机仿真 S1~S8 共 67 断言全过。
  - 影响文件: backend/api/source_camera_start_mixin.py
  - 附注: Windows 客户机走不到该 macOS 分支，但同族风险（探测中途 release 重开、
    失败后无兜底）在 Windows DSHOW/MSMF 选优路径由 v3.50.0a/v3.51.x 的生命周期锁
    与候选兜底覆盖；本修复补齐 mac/dev 侧最后一块，并以"终检"堵住所有平台的
    僵尸态出口。

## 测试与验证（不改产品行为）

- [TEST-001] Mac 真实摄像头生命周期仿真 UAT 归档
  - 内容: `tests/uat/mac_camera_sim/` 四个剧本 + README：
    S1 正常打开 / S2 外部进程占用 / S3 双通道抢同一物理相机 / S4 运行中调参重开 /
    S5 快速开停×6 并发竞态 / S6 kill -9 强杀重启自动恢复（含前端竞态干扰轮）/
    S7 双工位真模型完整恢复（源+模型+检测三件套、绑定不串）/
    S8 双工位绑不同模型重启各回各的 + 停开改参不重置不黑屏 + 邻工位不殃及。
    共 67 断言，2026-08-14 全过。
  - 结论: 双工位"关软件再开"自动恢复链（项目→模型→视频源→检测自动开始）、
    激活收养开关、停止/改参数不重置绑定，均在真实相机 + 真实 YOLO 模型
    （MPS 推理）下验证通过。

# v3.9.1 (2026-05-25)

> v3.9.0 之后的累积增量：事件交互手动确认 + PT/CT 显示口径可配 + Splash 启动体验定制化 + 步骤显示稳定性修复。
> 没有新增 `logic_mode`，纯粹是对现有模式的强化 + bug 修复，patch 级。

## 功能变更

### [FEAT-001] 事件手动确认 — require_ack / ack_resets_periodic

- **需求**: 客户产线对 NG / 自定义警告事件希望"弹提示框 + 冻结检测 + 等工人按确认后才继续"。一类典型场景：NG 周期工人要重做，需保留 NG 计数但重置当前周期；另一类：周期性强制动作（如未压墨提示）不希望客户没确认就被反复触发轰炸。
- **实现**:
  - 后端事件配置项加 `require_ack`（每个事件独立开关）+ `ack_timeout_sec`（超时自动确认，默认 0 不超时）。`_trigger_event` 检测到 `require_ack=true` 时把事件挂到 `_pending_ack` 内部状态，主推流线程检测到该状态后停止帧推送，等前端调 `POST /detection/ack-event` 才放行。
  - 周期性强制动作走独立路径 `_emit_periodic_notification`，原本绕过 `_trigger_event`。本次统一接入：周期性事件同样支持 `require_ack` + 新增 `ack_resets_periodic`（确认后重置该规则的 N 轮计数器，否则下一帧立即再触发，客户报障"未压墨提示框关不掉一直弹"）。
  - 前端 Monitor 页加全屏 overlay 拦截一切交互，按"确认"按钮调 ack API；Project 页加 `require_ack` / `ack_timeout_sec` / `ack_resets_periodic` 3 个 UI 控件，事件列表里每个事件单独配置。
- **影响文件**:

  - `backend/api/source_capture_loop_mixin.py`

### [FEAT-002] PT 计算口径可配 — span / visible 累计可见时长

- **需求**: 客户场景里一个步骤的标签可能从早到晚都被 YOLO 识别到（涂黑残留 / 翻面后还在画面 / 上一件还摆在工位等），老的"跨度"PT 把 18 秒识别周期算成 18s，但客户实际操作只用 2 秒。
- **实现**:
  - 后端永远计算两份 PT 字段：
    - `step_durations` / `cycle_sum_step_durations`（跨度 span，老字段，CSV 导出和 history 下游消费者都不变）
    - `step_visible_seconds`（新字段，每帧累加 `detected_labels` 里每个 label 的 `_dt`，上限 1.0s 防 FPS 极低时单帧大跨度污染）
  - 前端 `formatStepPT` 按 `systemStore.display.monitor.ptCalcMode` 选源：`'span'` 默认 / `'visible'` 用累计值。
- **影响文件**:
  - `backend/api/source_routes.py`（透出 `step_visible_seconds`）
  - `backend/api/source_state_init.py`（字段初始化）
  - `backend/api/source_step_stats_mixin.py`（每帧累加逻辑）
  - `backend/api/source_session_lifecycle_mixin.py`（周期开始清零，间隙保留）
  - `frontend/src/store/useSystemStore.js`（`ptCalcMode` 默认 `'span'`）
  - `frontend/src/views/Settings/index.vue`（监视设置卡片加下拉）
  - `frontend/src/views/Monitor/index.vue`（`formatStepPT` 切换数据源）

### [FEAT-003] 结算后强制保留显示 — resultHold

- **需求**: 客户产线工人在末步完成的瞬间看不到 "OK + PT 数字"，下一周期立刻覆盖。
- **实现**:
  - `systemStore.display.monitor.resultHoldEnabled` + `resultHoldSeconds`（默认关，开启时默认 1.5s）。
  - 周期结算后 `armResultHold(N)` 起 timer，期内冻结 `cycleSumStepDurations` / `stepInflightDurations` / `stepDurations` / `stepVisibleSeconds` 不被 polling 替换；期满主动清屏对齐 `_newCycleStarted` 字段集合。
- **影响文件**:
  - `frontend/src/store/useSystemStore.js`
  - `frontend/src/views/Settings/index.vue`
  - `frontend/src/views/Monitor/index.vue`

### [FEAT-004] 启动动画手势相机配置 — auto/specific/disabled

- **需求**: 客户工厂工控机经常装了 Todesk / 向日葵等远程虚拟相机，老逻辑没绑 USB 时走 `facingMode: user` → 浏览器随机挑 → 经常拿到虚拟相机。工业相机方案下工位 1 没绑 USB，跟启动动画想用的相机解耦。
- **实现**:
  - 后端 `channel_manager.py` 加 `get_splash_config` / `set_splash_config` 方法（直接读写 `workstation_config.json` 顶层 `splash` 字段，不动 `channels` / `channel_count`）；路由层加 `GET /workstations/splash-camera` 和 `PUT /workstations/splash-camera`（注意必须放在 `/{channel_id}/...` 之前，否则被 catch-all 抢走）。
  - 前端 Settings 加新卡片『启动动画手势相机』：模式下拉 `自动 / 指定相机 / 关闭手势` + 扫描可用相机按钮（先调一次低分辨率 `getUserMedia` 拿摄像头权限才能 `enumerateDevices()` 拿到设备名称）+ 选择对话框。
  - Electron `splash/main.js` 摄像头选择策略改三档：
    - `auto`：完全等价老逻辑（工位 1 USB 绑定 → 系统默认）
    - `specific`：`deviceId.exact` 强制锁定，找不到直接走"指定相机不可用（自动播放）"兜底，**不再回退到 todesk 这种虚拟相机**
    - `disabled`：直接跳过 `getUserMedia`，进自动播放，连授权弹窗都不弹
- **影响文件**:
  - `backend/api/channel_manager.py`
  - `frontend/src/views/Settings/index.vue`
  - `electron/splash/main.js`

### [FEAT-005] Splash 鼠标点击跳过手势

- **需求**: 客户工厂工控机一般没键盘 / 客户不知道按 ESC 能跳过手势，眼睁睁看着粒子球转半天。
- **实现**:
  - 抽出统一入口 `skipToReady(reason)`，原本 ESC keydown 的状态转换逻辑（`COLLAPSE` → 1.2s 后 `EXPLOSION`）封装其中。
  - 新增 `window.addEventListener('click', ...)`，排除 `<button>` `<a>` `<input>` `<select>` `<textarea>` 等已有交互元素（`closest()` 沿祖先树检查），其他任何位置点击触发 `skipToReady('CLICK')`。
  - 守门只看阶段（仅 IDLE / HOVER 响应），动画播到一半 / 已 READY 阶段的二次触发被吞掉，状态机不会被打断。
- **影响文件**:
  - `electron/splash/main.js`

## Bug 修复

### [BUG-001] 严格顺序 PT 起点 anchor 修正 — 解决 CT < PT 之和、负 interval

- **症状**: 客户严格顺序模式（strict_order=true）下，CT=6.21s 但 PT 加起来比 CT 大很多，更别说步骤间 interval；尤其翻转步骤 PT 高达 7.5s，而客户实际翻转只用 0.6 秒。
- **根因**: 翻转标签在"正面涂黑"还在进行时就被 YOLO 提前识别，PT 起点被记录到上一步骤还在执行的时刻 → duration = last_seen - start_time 横跨了两步操作 → 严格顺序下 interval 出现负值（步骤的"完成时间"早于"开始时间"）。
- **修复**: 引入 `_resolve_step_pt_anchor(label, fallback_start)` 助手函数，严格顺序步骤的 PT 起点强制 `max(fallback_start, last_step_completed_time)`，确保起点不早于上一步完成时刻。应用到 5 个 PT 写入点：
  - `_supplement_step_durations`（settle 时补计）
  - `_flush_active_steps_pt`（cycle 结束时 flush）
  - `_check_sequential_mode` / `_check_custom_sequential_mode` 两条补计路径
  - `step_inflight_durations`（in-flight 实时 PT，必须用同一 anchor，否则步骤完成时 PT 从大数字"啪"地跳到小数字，造成"PT 闪一下"）
- **影响文件**:
  - `backend/api/source.py`（新增 `_resolve_step_pt_anchor`）
  - `backend/api/source_sequential_mixin.py`
  - `backend/api/source_session_lifecycle_mixin.py`
  - `backend/api/source_step_stats_mixin.py`
  - `backend/api/source_routes.py`

### [BUG-002] 步骤状态机锁定 — 已检测不因画面残留回退到待检测，消除文字闪烁

- **症状**: 用户视频实测：周期内某步状态文字反复在"已检测 ↔ 待检测"切换，闪完 PT 涨一点。例如反面涂黑步骤在帧 50 显示"已检测"PT '--'，帧 55 又变回"待检测"PT '--'。
- **根因**: Monitor `updateStepsFromBackend` 4458 行状态机里 `_inFrame` 优先级最高 → 步骤已 join cycle_steps（`thisPosCompleted=true`），客户继续做这一步时 YOLO 检测框时有时无：
  - 标签出现 → status='active' → UI 渲染"待检测"（UI 1037 行只把 'completed' 渲染成"已检测"）
  - 标签消失 → status='completed' → UI 渲染"已检测"
  - 反复抖动 → 文字闪烁，inflight PT 每帧涨一点
  - `_passedThisStep` 老豁免只在"后续步骤已往前走"时生效，客户做这一步的中段后续还没识别 → 不豁免 → 闪
- **修复**: 调整状态机优先级：步骤一旦 `thisPosCompleted=true` 或被 backup 覆盖，直接锁 `'completed'`，不因画面残留回退。`'active'` 只剩"步骤识别到但还没 join 周期"那种瞬时态（实务上极短，主要给 `join_cycle=False` 的静态步骤用）。
- **影响文件**:
  - `frontend/src/views/Monitor/index.vue`

### [BUG-003] 删除 cycleResetTimer 1.2s 强制清屏 — 解决周期切换时步骤显示"先空再补"

- **症状**: 周期完成后约 1.2 秒，步骤状态会先变 'pending'（待检测，PT '--'），但同时 `cycleSumStepDurations` 字典里还残留上一轮的 PT 值 → 出现"翻转 待检测 PT 10.6s OK"这种状态/PT 不一致的快照。
- **根因**: 前端有两条独立的清屏路径打架：
  - `cycleResetTimer`（1.2s 固定 setTimeout）：清 step.status 但不清 cycleSumStepDurations
  - `_newCycleStarted`（cycle_id 翻新时触发）：清完整字段集合
  - 两个 timer 互相错开 → 1.2s 窗口内出现"status 已清 + PT 没清"的不一致状态
- **修复**: 删除 `cycleResetTimer` 整套机制，清屏路径统一由 `_newCycleStarted` 驱动（cycle_id 翻新时一次性清空所有字段：step.status / cycleResult / cycleSumStepDurations / stepInflightDurations / stepDurations / stepVisibleSeconds / 滚动游标）。`lastScrolledIdx = -1`（SOP 卡片栏滚动游标）也从 cycleResetTimer 块移到 `_newCycleStarted` 分支。
- **影响文件**:
  - `frontend/src/views/Monitor/index.vue`

### [HOTFIX-001] Splash 跳过手势路径卡死 EXPLOSION 末态

- **症状**: 客户工控机（触摸屏，无键盘鼠标）启动 v3.9.1 后，触摸屏幕想跳过启动动画 → splash 跑完塌缩/爆炸 → 卡在满屏粒子辐射星空 + 中央橙黄光球，右下角虽然写着 `READY · 就绪` 但 splash 不退出、主程序不显示，等多久都不行。
- **根因**:
  - Splash 状态机里 EXPLOSION → READY 的过渡条件是 `stageProgress >= 1.0 && backendReady`（`electron/splash/main.js` 1570 行）。
  - `backendReady` 标志原本只在两处会被打开：①手势识别成功后 `events.HAND_DETECTED` 等 3800ms 模拟"虚拟后端 ready"②调试快捷键 R 直接置 true。
  - v3.9.1 加的"鼠标/触摸点击跳过"和 v3.8.2 加的"ESC 跳过"都走同一个 `skipToReady` 函数，但**只触发了视觉阶段切换，没碰 `backendReady`** → 爆炸跑完没人打开这个标志 → 永远卡在 EXPLOSION 末帧。
  - 视频里"右下角 READY ✓"实际是进度条文案显示的阶段标签，不是真到了 `Stage.READY`，文案有误导。
  - ESC 跳过同款 bug 自 v3.8.2 起就埋下，因为工控机一般没键盘 + 客户不知道有 ESC 快捷键，长期没被触发；v3.9.1 触摸点击太自然，工厂触摸屏一摸就复现，把这个潜伏 bug 顶出来。
- **修复**: `skipToReady` 函数补一行 `backendReady = true`（同时修好 ESC + 鼠标 + 触摸三条路径）。塌缩 + 爆炸跑完会自然进入 READY 阶段 → 等真后端 IPC 通知 → 进度条冲 100% → `splash:finished` 关 splash → 显主程序。
- **影响文件**:
  - `electron/splash/main.js`（`skipToReady` 函数体内补一行 + 旁注 hotfix 历史）
- **发布产物**: 中转仓 `17373531860/tianjun-releases` v3.9.1 Release 附件
  - `patch_v3.9.1a.bat`（4.1 KB，CRLF 编码，备份原 app.asar 后替换）
  - `app.asar`（20 MB，修过的 electron asar 包）
- **客户操作**: 下载这两个文件到同一目录 → 双击 bat → 重启软件。回退方法：把 `resources\app.asar.bak_v3.9.1` 改名回 `app.asar` 即可。

### 顺带发现的同根问题（v3.9.2 待处理）

- Splash 进度条"虚拟阶段标签"显示 `READY · 就绪` 时实际可能还没进 `Stage.READY`，文案有误导。建议下版本把阶段标签和真实 `currentStage` 解耦，或者直接显示真实阶段。
- `backendReady`（动画内部"虚拟 ready"标志）和 `backendReadyFromIPC`（主进程真后端 ready 标志）是两个独立变量，命名相近容易引起此类遗漏。建议下版本统一概念或重命名以避免再踩。

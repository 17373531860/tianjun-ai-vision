# v2.7.6 (2026-04-21)

## Bug 修复

### [BUG-001] 扫码器在"开始检测"后不发 LON 命令，静默失败
- **症状**: 客户现场扫码器连上了（`测试`按钮能扫、闪灯、蜂鸣），但点"开始检测"后检测一轮都不扫。日志显示"扫码器已绑定"但没发 LON。
- **根因**:
  1. `resume_inference()` / `standby()` / `resume()` 三个从 standby 恢复 / 待机的路径都没调 `start_scanning()` / `stop_scanning()`——只有 `start_detection()` 一条路径调。从 standby 切检测时走的恰好是 `resume_inference()`，LON 根本发不出去。
  2. `start_scanning(channel_id=N)` 只按 `conn.broadcast_channels` 或 `[conn.channel_id]` 做命中判断。UI 上"绑定工位"填成 `1` 但单工位系统只有 `ch0`，整条扫码器被跳过；且失败路径是 `continue` 静默丢弃，没日志。
  3. 多处 `try: ...; except: pass` 把异常吞了，排查极困难。
- **修复**:
  - `backend/api/source.py`: `VideoSourceManager.resume() / standby() / resume_inference()` 每个都加 scanner `start/stop_scanning` 调用，异常路径统一 `traceback.print_exc()`，不再静默
  - `backend/services/scanner.py`: 新增 `_known_channel_count()` 读实际 `channel_count`；新增 `_resolve_bound_channels(conn)` —— 任何超出 `ch_count` 或 `<0` 的绑定自动降级到 `ch0`，并打 warning 提醒用户去改配置
  - `start_scanning` / `stop_scanning` 不再静默跳过，skip 原因（`status != connected` / `ch_conf / bcast / resolved` 不命中）全打印出来
- **影响文件**: `backend/api/source.py`, `backend/services/scanner.py`

## 功能变更

### [FEAT-001] 称重器稳定值判定 + 抖动/空载过滤
- **需求**: 每次读数都会被派发（包括 0.00、抖动中的瞬时值），MES / 集群收到一堆垃圾；客户要求只上报"稳定后的有效重量"，扫码时段内尽量保留最稳的那个值。
- **实现** (`backend/services/external_device.py`):
  - `DeviceConnection` 新增配置字段：`stable_enabled` / `stable_delta` / `stable_count` / `zero_threshold`
  - 运行时状态：`_stable_samples` 队列 / `_stable_state` (`idle` / `stabilizing` / `stable`) / `_stable_value` / `_last_reported_value`
  - `_handle_weight_stability`:
    - `|value| < zero_threshold` → 切 `idle`，清 barcode buffer，丢弃
    - 积累 `stable_count` 个样本；`max - min ≤ stable_delta` 判稳；取窗口**中位数**作上报值（抗抖动 + 代表扫码窗口内"最稳的那个"）
    - 稳定窗口内不重复上报，除非值漂移超过 `stable_delta`
  - `stable_enabled=False` 时完全退回旧行为
- **默认值**: `stable_enabled=True`, `stable_delta=0.05 kg`, `stable_count=5`, `zero_threshold=0.05 kg`
- **Migration**: `backend/main.py` migrate_database 增加 `external_devices.stable_enabled / stable_delta / stable_count / zero_threshold / weight_no_barcode_alarm_enabled / weight_no_barcode_alarm_delay_sec`
- **影响文件**: `backend/services/external_device.py`, `backend/models/mes_models.py`, `backend/api/external_device.py`, `backend/main.py`, `frontend/src/views/MES/ExternalDevicePanel.vue`
- **测试**: `test_stable_weight.py` 6 用例全过

### [FEAT-002] "有重无码"告警（默认关闭 + 可配置延迟）
- **需求**: 稳定重量持续 N 秒但 barcode buffer 一直为空 → 提示操作员漏扫。但"有重就报"会刷屏，必须可配置延迟，且必须**默认关闭**。
- **实现** (`backend/services/external_device.py::_check_weight_no_barcode_alarm`):
  - 触发: `stable_state=stable` 且 `|value| >= zero_threshold` 且 barcode buffer 空 且 持续 `weight_no_barcode_alarm_delay_sec` 秒
  - 动作: `MESGateway.dispatch("weight_no_barcode", {device_name, channel_id, value, elapsed_sec, ...})` + `alarm_router.trigger_alarm("weight_no_barcode", channel_id)`
  - 扫到条码后计时器立即清零，单次只报 1 次不刷屏
- **默认**: `weight_no_barcode_alarm_enabled=False`, `weight_no_barcode_alarm_delay_sec=10`
- **影响文件**: 同 FEAT-001
- **测试**: `test_stable_weight.py` 含 3 个相关用例（默认关闭 / 超时触发 / 扫码清计时）

### [FEAT-003] 传动杆 (class 5) 误判过滤：空间共现 + 软时序 Gate（默认关闭）
- **需求**: 当前 `best(7).pt` 把"空箱 + 泡沫槽中间黑色横缝"稳定误识别成"传动杆"（conf 0.88~0.92）。定量分析（11390 帧全视频）发现两分布反向：
  - 合法期 rod: median conf **0.686**，max **0.883**
  - 误判期 rod: median conf **0.900**，max **0.932**
  - 说明 per-class conf 阈值方案根上无解（拔到 0.93 → fp 还剩 1%，tp 先砍到 0）
- **方案**: 推理端两层叠加过滤，和后续模型重训（`best_v3.pt`）是**叠加关系**，换模型不撤过滤
  - **第 1 层 空间共现 `filter_rod_by_companion`**: 同一帧里 `传动杆` 必须和任一 companion (`大框架 / 小框架 / 侧板`) 满足 `center-in-bbox OR IoU ≥ 0.25`，否则丢弃。**主力**，实测砍掉 **97% 误判** / 保留 **97.5% 真阳**
  - **第 2 层 软时序 `RodSessionGate`**: 当前周期从未检出过 `大框架 / 小框架` 时抑制所有 `传动杆`；见过之后放行。每个新周期 / stop_detection 时 reset
- **实现**:
  - 新增 `backend/api/rod_filter.py`: `filter_rod_by_companion` / `RodSessionGate` / `read_rod_filter_config`。全按 **label 字符串** 判断，不硬编码 `class_id`
  - `backend/api/source.py`:
    - `__init__` 挂 `self._rod_gate` / `self._rod_filter_cfg`
    - `set_project_config` 每次变更重新读开关并重建 gate
    - `_apply_rod_filters(detections)` helper 统一封装
    - 三个推理入口 `_detect_only` / `_detect_and_track` / `_detect_segment` 在 `return detections` 前一律走 helper
    - `start_cycle` 新周期落地点 / `stop_detection` 分别 `gate.reset()`
- **默认全关**（安全底线）。要生效在 `project_config` 里显式配置：
  ```json
  {
    "rod_companion_filter": {
      "enabled": true,
      "iou_threshold": 0.25,
      "rod_label": "传动杆",
      "companion_labels": ["大框架", "小框架", "侧板"]
    },
    "rod_session_gate": {
      "enabled": true,
      "rod_label": "传动杆",
      "gate_labels": ["大框架", "小框架"]
    }
  }
  ```
- **验证产物**（仓库 `tune_rod_conf/`）:
  - `analyze_rod.py` + `out/timeline.json` + `out/conf_hist.png`: 原始分布分析
  - `out/samples/`: 15 张证据截图（含 `A_fp_*` 高置信度误判、`C_tp_highconf_*` 真阳、`raw_t*s.jpg` 原始帧）
  - `verify_filter.py` + `out/verify_filter.json`: 端到端过滤效果对比
- **影响文件**: `backend/api/rod_filter.py`（新增）, `backend/api/source.py`
- **测试**: `test_rod_filter.py` 16 用例全过

## 配置变更

### [CONFIG-001] UI 工位编号统一为 1-indexed，消除"工位 0"
- **需求**: 界面上双工位写着"工位 1 / 工位 2"，但扫码器和外部设备面板的下拉里硬编码 `[0,1,2,3]` 直接显示成"工位 0 / 工位 1 / 工位 2 / 工位 3"，客户会以为存在一个不存在的"工位 0"。
- **实现**:
  - 后端 `channel_id` 保持 0-indexed（不改数据模型和 API 语义）
  - 前端 UI 显示统一 +1，即 `工位 ${channel_id + 1}`
  - `ScannerPanel.vue` / `ExternalDevicePanel.vue`:
    - "绑定工位" / "广播工位" 下拉改为根据 `getWorkstations().channel_count` 动态生成
    - `{value: i, label: '工位 ${i + 1}'}`
    - "绑定工位" 从 `el-input-number` 改为 `el-select`，避免手填超界
  - 设备卡片现有 `channel_id` / 广播工位标签全部 +1 显示
- **影响文件**: `frontend/src/views/MES/ScannerPanel.vue`, `frontend/src/views/MES/ExternalDevicePanel.vue`

## 已知问题 / 注意事项

- **两层 rod 过滤默认关**。紧急客户项目今晚部署时需在 `project_config` 里显式打开两个开关（见 FEAT-003 的 JSON 示例）。
- 后续 `best_v3.pt` 到位后过滤**不撤**，和新模型叠加。
- `rod_companion_iou_threshold` 默认 0.25，现场误杀真杆时降到 0.15 / 0.10；误判未砍干净时先把 `rod_session_gate.enabled` 打开。
- "有重无码告警"默认关，避免误触发；开启时请按现场扫码时长估计 `delay_sec`，建议 10~30 秒。

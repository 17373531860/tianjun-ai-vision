> v3.10.0 用户系统主线之后的"客户机视觉行为"补丁版。
> 聚焦 PT/CT 显示口径、防重复结算、Splash 与窗口模式三大块, 都是客户现场常见反馈的"显示不准 / 启动太重 / 全屏不舒服"。

## Bug 修复

### [BUG-001] PT 多段策略选"仅首段"显示 0.0s / "--"
- **症状**:
  显示设置切到 PT 多段合并策略 = 仅首段 (`first_only`) 后,
  Monitor 步骤统计的 PT 列大面积变成 `0.0s` 或 `--`,
  本应显示首段时长 (例如 2.24s) 的步骤完全显示不出来。
- **根因**:
  `_supplement_step_durations` (settle 时的"画面还在的 label 兜底落账") 用
  `if duration >= 0` 守门, **放过了 duration == 0** 的同帧场景:
  当 `step_last_seen == step_start_time` (单帧消失 / 兜底首帧) 时, `duration = 0`,
  `0.0` 被 `_accumulate_step_pt` 追加进 `step_cycle_segments[label]` 历史。
  一个周期触发十几次这种 0.0 落账, 真实首段 (如 2.24) 被挤到 list 中后,
  前端 `first_only = segments[0]` 取到 `0.0` → `if duration <= 0 return '--'` → 显示 `--`。
  `sum` 不受影响 (加 0 = 加 0), `max` 不受影响 (最大值跟 0 无关) ──
  **只有 first_only 暴露了这个污染**。
- **修复**:
  `_accumulate_step_pt` 入口加守门: `rounded_dur <= 0.005` 直接返回, 不进 segments / 不累加 sum,
  5 个调用点共用一道守门, 不用每处分别加。
- **影响文件**: `backend/api/source.py`
- **真测**: 同视频跑完整 OK 周期, 4 步 segments 都是单段干净数据, first_only 显示正常 (4.78 / 1.63 / 2.93 / 1.15)。

### [BUG-002] 严格顺序模式 PT 负 `interval`
- **症状**:
  严格顺序模式下, 某些步骤的 `interval_from_prev` 出现负值, 落库与导出 CSV 都显示异常。
- **根因**:
  PT 起点 (`step_start_time`) 取的是 YOLO 第一次见到该 label 的瞬间,
  但严格顺序模式下, 上一步在该步骤前就已经完成 → 当前步骤的 `start_time` < 上一步 `end_time`
  → `interval = current_start - prev_end < 0`。
- **修复**:
  新增 `_resolve_step_pt_anchor(label, raw_start)`:
  把 PT 起点夹到 `max(raw_start, 上一步完成时刻)`,
  保证 sequential / custom 顺序模式下 interval 永远非负。
  视频源场景同步加 `_resolve_step_pt_anchor_frame_pos` (帧号版, 跟 B 方案 v2 同口径)。
- **影响文件**: `backend/api/source.py`, `backend/api/source_sequential_mixin.py`, `backend/api/source_step_stats_mixin.py`, `backend/api/source_session_lifecycle_mixin.py`

### [BUG-003] "防重复结算"开关 UI 打开但实际不落库 → 反复结算
- **症状**:
  项目页 → 防重复结算开关打开, 但同一节拍仍连续触发 OK / NG 多次结算。
  推 MES 重复, 报警重复, 步骤计数翻倍。
- **根因**:
  `Project/index.vue:saveProject` 写 `pipeline_config` 时 **漏写 `settle_dedup` 字段**,
  UI 开关只在前端 state 里转, 没进 DB, 后端永远读到 `False` → 老守门永远不生效。
- **修复**:
  - 前端: `saveProject` 显式写 `settle_dedup` + `settle_dedup_window_seconds`。
  - 后端: 重写防重复结算逻辑为"任意事件后冷却窗口", 不再依赖 `current_cycle_id`,
    覆盖 OK → NG / 同节拍重发 / 自定义事件连发等所有方向 (老版本只挡空周期)。
- **影响文件**: `backend/api/source_event_trigger_mixin.py`, `frontend/src/views/Project/index.vue`

## 功能变更

### [FEAT-001] PT/CT 显示口径重做 (B 方案 v2 — 视频源帧号锚)
- **需求**:
  客户机解码速度 / 视频快进慢放 / FFmpeg 卡顿 都会让 wall-clock PT/CT 偏差很大,
  原始 "硬调试效果还行, 视频回放严重失真"。
- **实现**:
  视频源场景下镜像维护一组帧号锚字段, PT / CT / in-flight 全用帧号差 / 视频原 fps 算秒:
  - `cycle_start_frame_pos` — 周期开始时的视频帧号
  - `step_start_frame_pos[label]` — 步骤起点帧号
  - `step_last_frame_pos[label]` — 步骤末次见到帧号
  - `_compute_duration_sec(start_fr, end_fr, fallback_start_wall, fallback_end_wall)` —
    视频源走帧号差, 非视频源 fallback 回 wall-clock, 一处出口统一。
  - 所有 `step_start_time / step_last_seen / cycle_start_time` 赋值点同步镜像写入帧号字段
    (state_init / session_lifecycle / settlement / sequential / step_stats / per_item / tracking 全覆盖)。
  - PT/CT/in-flight 三处计算口都换成新函数, 视频源 / 实时摄像头互不干扰。
- **影响文件**:
  `backend/api/source.py`,
  `backend/api/source_state_init.py`,
  `backend/api/source_session_lifecycle_mixin.py`,
  `backend/api/source_settlement_mixin.py`,
  `backend/api/source_sequential_mixin.py`,
  `backend/api/source_step_stats_mixin.py`,
  `backend/api/source_per_item_mixin.py`,
  `backend/api/source_tracking_mixin.py`,
  `backend/api/source_routes.py`
- **兼容性**: 非视频源 (USB / RTSP / 海康相机) 帧号字段写 0, 计算口自动 fallback 回 wall-clock, 行为完全不变。

### [FEAT-002] PT 多段合并策略 — 三档可切 (`sum` / `max` / `first_only`)
- **需求**:
  YOLO 抖动严重时, 步骤被识别成多段 (例如 `[0.14, 0.65, 2.04]`),
  默认 `sum` 累加显示 2.83s 比实际操作时间偏大。
  客户想要可切换的"取最长 / 仅首段"两档兜底, 不破坏 `sum` 默认行为。
- **实现**:
  - 后端: 新增 `_accumulate_step_pt(label, rounded_dur)` 统一出口,
    始终维护 `step_cycle_durations` (按 `sum` 累加, 老接口语义不变)
    与 `step_cycle_segments` (完整分段时长列表)。
  - 前端 (`useSystemStore`): 新增 `display.monitor.ptAccumulateStrategy` 字段,
    默认 `sum` (保持客户默认体验不变)。
  - 前端 (`Settings/index.vue`): "PT 多段合并策略" 三档下拉 (仅当 `ptAggregate=sum` 时展示)。
  - 前端 (`Monitor/index.vue`): `formatStepPT` 在 `sum + current` 时根据策略对 segments 现算 max / first_only,
    后端权威字段不动, 切换无需重启。
  - 后端 `_routes`: 把 `step_cycle_segments` 加进 detection results, 前端订阅。
- **影响文件**:
  `backend/api/source.py`,
  `backend/api/source_routes.py`,
  `backend/api/source_state_init.py`,
  `backend/api/source_session_lifecycle_mixin.py`,
  `backend/api/source_step_stats_mixin.py`,
  `backend/api/source_sequential_mixin.py`,
  `frontend/src/store/useSystemStore.js`,
  `frontend/src/views/Monitor/index.vue`,
  `frontend/src/views/Settings/index.vue`
- **关键: 配合 BUG-001 才完整可用** — 没修 0.0 段守门, first_only 会持续显示 0.0s。

### [FEAT-003] 防重复结算 → 时间窗口冷却模式
- **需求**:
  同一动作节拍因 YOLO 切换 / 状态机抖动 / disappear_delay 等原因连续触发多次结算,
  导致 MES 重推 / 计数翻倍 / 报警重发。
  老版本只挡"无周期空跑", 挡不住 OK 后又来 NG, 也挡不住同步连发自定义事件。
- **实现**:
  - 后端: `_trigger_event` 入口加冷却窗口 — 任意事件触发后, 在 `settle_dedup_window_seconds` (默认 2.0s) 内,
    所有事件 (OK / NG / 自定义) 一律 `_discard_empty_cycle()` 并返回 False。
    可与 `ng_cycle_protect_seconds` (老版 NG → NG 守门) 共存, 互补不冲突。
  - 前端: Project 页"防重复结算"开关旁边加 `冷却时长(秒)` 数字输入框, 默认 2.0, 0 等同于关闭。
- **影响文件**:
  `backend/api/source_event_trigger_mixin.py`,
  `backend/api/source_state_init.py`,
  `frontend/src/views/Project/index.vue`
- **新增配置**: `pipeline_config.settle_dedup`, `pipeline_config.settle_dedup_window_seconds`。

### [FEAT-004] Splash 行为可配 + 默认关闭
- **需求**:
  老板要求"客户机启动直接进主程序, 不要那个 splash 动画" (客户反馈"等得太久 / 看着像没启动")。
  同时保留启用选项, 给少量需要 demo 效果的客户用。
- **实现**:
  - 后端 `channel_manager.py`: `splash` 配置段新增 `enabled` 字段 (默认 False),
    保留老的 `camera_mode / device_id / device_label / idle_timeout_sec` 字段不动。
  - Electron `main.js`: 启动早期直读 `workstation_config.json`, 根据 `splash.enabled` 决定:
    - `False` (默认): 走"无 splash 路径", 直接建主窗 + 后台预热后端, 后端 ready 后立即 show, 不经过 splash IPC。
    - `True`: 老行为, 走 splash 完整流程 (摄像头 / 手动跳过 / 闲置超时)。
- **影响文件**: `backend/api/channel_manager.py`, `electron/main.js`

### [FEAT-005] 窗口模式 — 默认窗口模式 + 全屏热切 + 最小化按钮
- **需求**:
  v3.8.2 起默认全屏 + 无标题栏 (kiosk 风格), 客户在桌面办公场景反馈"不能最小化 / 不能调大小 / 无法切别的程序"。
  老板要求"默认窗口模式, 全屏可选, 加最小化"。
- **实现**:
  - 后端 `channel_manager.py`: `workstation_config.json` 顶层加 `window` 段, 含 `fullscreen` 字段 (默认 False)。
    暴露 `get_window_config / set_window_config`, 跟 splash 段同级。
  - Electron `main.js`:
    - `createWindow(opts)` 接受 `opts.fullscreen`, 启动时根据 `workstation_config.window.fullscreen` 决定:
      - `True` (kiosk): `fullscreen: true, frame: false`。
      - `False` (默认): 1600×900 居中, 带 Windows 原生标题栏 (最小化 / 最大化 / 关闭三件套)。
    - 新增 IPC: `window:minimize` (收任务栏), `window:set-fullscreen` (热切 + 持久化)。
  - Electron `preload.js`: 暴露 `electronAPI.minimizeWindow / setFullScreen` 给前端。
  - 前端 `Settings/index.vue`: 显示设置加"窗口模式"卡片 — 主窗口全屏开关 + 最小化按钮 (仅打包桌面版生效)。
- **影响文件**:
  `backend/api/channel_manager.py`,
  `electron/main.js`,
  `electron/preload.js`,
  `frontend/src/views/Settings/index.vue`

## 已知问题 / 暂不修

### [KNOWN-001] YOLO 把"正面涂黑"识别成 4-6 秒连续段
- **现象**:
  历史 10 个周期对比, 正面涂黑稳定 4-6s, 反面涂黑稳定 1-3s, 比例 1.6× ~ 5.1×。
- **真测确认**:
  YOLO 每帧高频采样, 单帧只输出一个标签, 没有同帧并存, 也没有软件层吞段。
  正面涂黑 segments = `[4.78]` 一段, 三种显示策略 (sum / max / first_only) 完全等价 — 都救不了。
- **结论**:
  这是 YOLO 模型边界判定问题, 不是软件 bug。可调方向:
  - 调高"正面涂黑" `confidence` 阈值 (例 0.96+) 切断过渡帧
  - 给"正面涂黑"配 `max_duration=3.5s` 截断超长段
  - 加负样本重训
- **本版决策**: 视频回放问题, 客户现场实际识别效果可接受, 暂不动 → 等真实工厂数据验证后再调。

### [KNOWN-002] `step_start_frame_pos` / `step_last_frame_pos` 在 cycle 切换不显式 clear
- v3.10.x B 方案 v2 引入的帧号锚字段, 跨周期没显式置零。
- 实际无害: 每个 `step_start_time` 赋值点都同步镜像写帧号, 新周期 step 首次出现时帧号会被新值覆盖。
- 真测跨多周期数据正常, 不影响 PT/CT 计算。
- 留作 v3.10.2 / v3.11.0 整理时一并处理。

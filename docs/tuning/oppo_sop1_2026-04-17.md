# 调参记录: oppo_sop1 (2026-04-17)

## 环境
- 项目: oppo_sop1 (id=12)
- 模型: oppo1.pt (detect, 3 classes: 顶卡拖/撕膜/点亮屏幕)
- 视频: Video_20260320203958253.avi
- GPU: 桌面开发机 RTX 3070
- 逻辑模式: sequential (顺序检测)
- 顺序: 顶卡拖 → 撕膜 → 点亮屏幕 (A-B-C)

## 初始配置
| 步骤 | 置信度 | 最短持续 | 最少帧数 | 最大间隔 | 丢帧容忍 |
|------|--------|----------|----------|----------|----------|
| 顶卡拖 | 0.50 | - | - | 3s | 0 |
| 撕膜 | 0.50 | - | - | 3s | 0 |
| 点亮屏幕 | 0.50 | - | - | 3s | 0 |

## 调优过程

### 第1轮: 发现步骤回退误判问题
- 观察: 视频中操作顺序为 A-B-A-B-C（工人反复操作），系统判定为 OK
- 调整: 这不是参数问题，是代码逻辑 bug
- 依据: 步骤入队逻辑使用全局去重 `if label not in current_cycle_steps`，当 A 第二次出现时被静默丢弃，导致实际入队序列为 A-B-C（与期望一致），误判 OK
- 结果: 引入 `_cycle_regression` 标志。仅连续相同步骤去重（last_added_step==label），非连续重复步骤仍入队并标记回退，结算时判 NG
- 状态: 代码修复，转入参数调优

### 第2轮: 调整顶卡拖置信度阈值
- 观察: 顶卡拖动作在视频中检测不够稳定，部分帧置信度偏低
- 调整: threshold 从 0.50 降到 0.49
- 依据: 顶卡拖动作幅度小，模型置信度分布集中在 0.45-0.60 区间，适当降低避免漏检
- 结果: 检测更稳定，顶卡拖步骤能正确触发
- 状态: 通过

### 第3轮: 调整撕膜最大间隔和最短持续
- 观察: 撕膜动作持续时间较短但间歇性出现
- 调整: max_interval 从 3s 提高到 4s，min_duration 设为 0.2s
- 依据: 操作人员撕膜时偶尔停顿，3s 间隔会导致步骤提前超时被清除
- 结果: 撕膜步骤不再被提前清除
- 状态: 通过

### 第4轮: 调整各步骤最短持续时间
- 观察: 极短的误检（1-2帧闪烁）偶尔触发步骤
- 调整: 顶卡拖 min_duration=0.5s，撕膜 min_duration=0.2s，点亮屏幕 min_duration=0.5s
- 依据: 给每个步骤设置合理的最短持续时间，过滤掉瞬间误检
- 结果: 误检消除，三个步骤均能稳定触发
- 状态: 通过

### 第5轮: 最终验证
- 观察: 完整视频跑一遍，确认 OK/NG 判定正确
- 调整: 无
- 结果: 正常操作序列 A-B-C 判定 OK；回退序列 A-B-A-B-C 判定 NG（步骤回退）
- 状态: 通过 ✓

## 最终配置

|------|--------|----------|----------|----------|----------|

| 撕膜 | 0.50 | 0.2s | - | 4s | 0 |
| 点亮屏幕 | 0.50 | 0.5s | - | 3s | 0 |

## 调优总结
- **关键发现**: 顺序检测的步骤去重逻辑存在根本缺陷——全局去重会丢弃非连续重复步骤，导致 A-B-A-B-C 误判为 OK。这不是参数能解决的问题，需要代码修复
- **推荐参数范围**: 
  - 置信度: 0.45-0.55（该模型在此视频上的检测置信度普遍不高）
  - min_duration: 0.2s-0.5s（过滤闪烁误检，同时不影响快速操作）
  - max_interval: 3s-4s（根据操作速度调整，撕膜需要更长容忍）
- **注意事项**: 
  - 本次调优发现了一个代码级 bug（已在 v2.7.1 中修复），参数调整仅是辅助
  - 操作人员如果习惯性回退操作，_cycle_regression 机制会正确判 NG
  - 该项目的步骤配置相对宽松，适合首次部署后根据实际情况微调

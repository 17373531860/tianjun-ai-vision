## 一、通用架构决策（5 套共用，先看这节再看参数表）

### 1. 判定模式：检测计数，不是顺序

工时测量场景里工人动作**真实交叠**（例：检查内框活动性和转动滑轮谁先确认逐周期随机互换），
顺序模式会海量误报「顺序错误」「步骤回退」NG。计数模式 = 必做步骤都出现即 OK，
工时（PT）照常逐步骤记录，符合"测工时不管工序卡控"的业务语义。

- `logic_mode = detection`
- `pipeline_config.detection_steps = [必做步骤 id 列表]`（弱检出步骤**不进**这个列表，见下）
- 结算锚点 = 列表里第一个步骤（"拿取产品"类）重现时自动收上一周期

### 2. 非锚步骤全部 `accept_once = true`

周期内只认第一次出现。后段重闪（检查外观在放板后又亮一下）不会判「重复步骤」NG，
PT 用第一次出现计。

### 3. 结算锚步骤（首步）三件套 ⚠ 最关键

| 参数 | 值 | 作用 |
|---|---|---|
| `threshold` | 40~60 | 拦低置信度中途闪现，防周期切碎 |
| `disappear_delay = 0.8` + `disappear_uninterruptible = true` | 固定 | 桥住段内闪断；不加会一段计两次、周期边界错乱 |
| `min_duration = 0.6~1.0`（视工位） | 见各表 | **双手并行工位的"每帧重结算风暴"止血阀**（见故障手册 A） |

### 4. 尾步（放计数板/装袋类）：消失等待必须短且可打断

尾步结束距下一周期锚步只有 ~0.3~0.7s。`disappear_delay = 0.4~0.5`、**不要**开不可打断——
等待跨过结算边界会把尾步漏进下一周期，出现「周期只剩[拿取产品,放计数板]」的旋转错位。

### 5. 中段易分裂步骤：桥接 + 帧数门

部分视频里转动滑轮/检查外观一个周期分裂成两段（间隔 ~0.8s）：
`disappear_delay = 1.0` + `disappear_uninterruptible = true` 合并成一段。
噪声闪现是 1~4 帧、真实段 ≥6 帧（双峰分布），`min_frames = 5` 干净切开。

### 6. 弱检出步骤：保留观测、不进判定

某机位某类天生检不出（如 2K17421 的「确认内框有无下落」、K10916 的「转动滑轮」）：
步骤保持 `enabled = true`（有检出时工时照记、看板照显示），但**不进 `detection_steps`**，
不因它缺席判 NG。阈值提到 40 消音（防止它以超长假持续时间刷操作日志）。

## 三、调优过程（12 轮，症状→处方对照供现场排障）

### 第1轮: 基线（顺序模式 + 2倍速 + CPU）→ 0% OK
- 观察: 推理仅 8.9fps；2 倍速把 0.2s 级步骤压到采样线以下；通道被前次压测钉在 CPU
- 调整: 通道钉回 mps、1 倍速、min_frames 全降 1
- 结果: 34%。**顺手挖出主程序回归 bug**：`/workstations/{ch}/gpu` 改设备后重启检测不生效
  （幂等守门比对期望设备而非实际设备，模型滞留 CPU），已修 `channel_manager.py`

### 第2~4轮: 首步噪声治理 → 仍 0~34%
- 观察: 满帧后「拿取产品」150s 计 84 次（真实 ~45 周期）——段内闪断被"规则B"
  （其他步骤出现即掐断消失等待）切成两次，周期边界错乱、记录序列整体旋转一位
- 调整: 拿取产品 `disappear_delay=0.8 + disappear_uninterruptible=true`
- 结果: **90%**（视频1）。首步三件套定型

### 第5~7轮: 中段分裂与尾步跨界 → 视频2 33%
- 观察A: 转动滑轮/检查外观一周期分裂两段（间隔~0.8s）→「步骤回退」NG
- 处方A: 这两步 dd=1.0 不可打断 + min_frames=5（噪声≤4帧/真实≥6帧双峰切分）
- 观察B: 放计数板 1.0s 不可打断等待**跨过结算边界**，完成时刻漏进新周期
  （周期变成 `[拿取产品,放计数板]`、下一周期以放计数板开头）
- 处方B: 尾步 dd 回 0.4、可打断（定为通用规则）

### 第8~9轮: 顺序判定撞墙 → 37%
- 观察: 步骤全齐但确认顺序随机互换（动作真实交叠），顺序模式必误 NG；
  参数已无操作空间
- 决策: **切换 detection 计数模式 + 非锚步 accept_once**（架构性转折点）

### 第10~11轮: 计数模式落地 → 92~97%
- 观察: runner 的视频未回零导致假 100%（修 runner：start 后强制 seek 0）
- 结果: 2K17421 三视频 97/92/95%，定稿

### 第12轮: 推广到其余 4 套 + 结算风暴止血
- 观察: 3K11311/5K15111/K10916 出现「每帧重结算风暴」（150s 刷 165~248 个 NG，
  拿取产品/放计数板成对 0 秒完成）——双手并行工位在结算瞬间锚步+尾步同框，
  结算重置清了 step_last_seen 后每帧都被当"锚步重现"
- 处方: **锚步 `min_duration` 门**（风暴 held 仅 0.06~0.14s 被挡，真实锚步 1.2~3.2s 放行）；
  0.4 太松（风暴部分复发），0.6~1.0 稳定
- 结果: 全部达标（见验收表）

## 四、现场故障手册（症状 → 处方）

| 症状 | 根因 | 处方 |
|---|---|---|
| **A. NG 刷屏**（每秒多个 NG，周期时长 0.0x 秒，锚步/尾步计数爆炸且成对） | 双手并行工位结算风暴 | 锚步加 `min_duration`（0.6 起步，仍风暴加到 1.0；先确认真实锚步可见时长 > 门值） |
| B. 周期数只有真实一半，OK 里步骤数翻倍 | 锚步漏检，两周期合并 | 降锚步 threshold；确认 min_duration 没超过真实可见时长 |
| C. 缺某步 NG，但画面里明明有 | 该步被 min_frames 挡掉或段内闪断 | min_frames 降到 2；该步 dd 加到 0.8 + 开不可打断 |
| D. 周期开头混进上周期的尾步 | 尾步消失等待跨界 | 尾步 dd ≤0.5 且**关**不可打断 |
| E. 某步在某机位永远检不出（全置信度无框） | 模型盲区 | 参数无解。把该步移出 detection_steps 转观测，补采数据重训 |
| F. 改了 GPU 设备后推理 fps 没变 | v3.45 前的守门 bug | 升级到含 2026-08-06 channel_manager 修复的版本；或改设备后重启后端 |

## 五、调优总结

- **关键发现**
  1. 工时测量与质量卡控是两种判定语义：前者用计数模式，后者才用顺序模式。选错模式参数怎么调都救不回来。
  2. 锚步是整条状态机的命门：threshold/桥接/时长门三件套。锚步稳，周期就稳。
  3. 离线分析必须与真机同 imgsz（模型自带训练分辨率），否则阈值结论会漂。
  4. 双峰分布是 min_frames 的定标依据：先探"噪声闪多少帧 vs 真实段多少帧"再定值，不要拍脑袋。
- **推荐参数范围**（同类工位新模型冷启动值）
  - 锚步: threshold 40~60, min_frames 3, dd 0.8 不可打断, min_duration 0.6
  - 中段步: threshold 15~35, min_frames 2~5, dd 0.5~1.0（分裂就开不可打断）
  - 尾步: threshold 15~30, min_frames 2~4, dd 0.4 可打断
- **注意事项**
  - 全部参数可在前端「项目管理 → 步骤设置」直接改，改完重新激活项目生效
  - `detection_steps`（必做集合）目前在 pipeline_config JSON 里，前端计数模式配置页可勾选
  - LG 看板全局参数（默认价值类型/等待归属/统计口径/趋势天数）在系统设置「LG 工时参数」卡片

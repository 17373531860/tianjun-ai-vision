# 称重检测应用 · 主程序落地设计 RFC

> 状态：**✅ 已落地（2026-06-29）**——主程序原生「称重投料模式」已实现并通过真机+浏览器验证，bestar 插件已退役。**第 1–8 节为当初的设计提案与决策记录（保留作背景）；最终落地实现与验证见第 9 节，以第 9 节为准。**
> 触发：萍乡百斯特项目终验收（称重投料防错）。但本 RFC 主张把「称重检测」做成**主程序原生、可配置的通用检测应用**，百斯特只是它的第一个实例。
> 作者：AI agent + 项目主作者
> 关联：`feature-placement` skill、`add-detection-mode` skill、`modify-model` skill、《萍乡百斯特项目 终验收标准》第六章

---

## 0. 结论先行（给老板 30 秒版）

1. **称重投料防错不该是「百斯特专属插件」，应该是主程序原生的一类「检测应用」。** 理由：称重器接入 + 读数稳定判定 + 标准量对比（缺料/超量）+ 去皮置零控制，是任何「按重量配料/配重」工厂都要的基础能力，不是百斯特独有的小众变种。食品分装、化工配料、五金配重都能用。
2. **归位拆两层**：
   - **进主程序（基础设施）**：称重检测模式本身 + 型号标准量配方表 + 逐件称重记录表 + 称重器软件控制（去皮/置零，**已落盘**）+ 三色灯报警联动（**已复用**）+ MES 上传。
   - **进配置 / 薄插件（客户变种）**：百斯特特有的「钢帽水泥 / 钢脚水泥双料顺序」「三盆三工位聚合」「特定型号的标准量数值」——这些是实例化数据和编排，不污染主程序。
3. **已经做了什么**：平台地基（`external_device_data` 钩子 + `host.send_device_command` 去皮置零 API）+ 一个能跑通验收逻辑的 `bestar` 插件骨架（状态机 + 判定 + 单测）**都已真实落盘**。本 RFC 决定的是：**把其中通用的部分上提进主程序**，让插件回归只承担百斯特编排。
4. **要你拍板的**：① 称重检测是否进主程序（同意则按第 5 节施工）；② 第 7 节待确认清单（标准量数值、料别识别方式、工位数）。

## 1. 背景与问题

### 1.1 验收要的是什么（终验收第六章摘要）

| 条目 | 客户要求 | 本质能力 |
|------|----------|----------|
| 6.1 | 每件逐件记录初值/终值/料别/判定/时间，并上传 | 逐件称重记录 + MES 上传 |
| 6.1 | 按型号绑定标准用量 | 型号→标准量配方 |
| 6.2 | 缺料（< 标准）报警；超量（> 标准）报警，上下限容差可配 | 标准量对比判定 + 三色灯联动 |
| 6.3 | 钢帽水泥 / 钢脚水泥防错（投错品类拦截） | 料别识别（视觉，待客户模型标签）|
| 6.4 | 放件后自动去皮 | 软件控制称重器去皮（T 指令）|
| 6.5 | 必须先选人员 / 型号，否则持续报警 | 前置校验 |
| — | 单 / 多工位可配，不改软件 | 工位列表配置化 |

### 1.2 问题：这套能力放哪？

最初按「客户专属」做成了 `bestar` 插件。但复盘发现：**上表「本质能力」列没有一项是百斯特独有的**。它们是「称重 + 比标准 + 报警 + 记录」这一类检测的通用骨架。按 AGENTS.md 第三节产品决策原则：

> 多客户都会用、影响检测/MES/数据核心通路 → **主程序原生**（且给插件平台留 hook 给变种）

所以称重检测应进主程序。把它锁死在一个客户插件里，等于下一个配料客户来了又要重写一遍——这正是规则里点名禁止的反模式。

## 2. 归位决策（feature-placement 判定）

逐条过一遍判据：

| 能力 | 判据 | 归位 |
|------|------|------|
| 称重器接入 + 读数稳定判定 | 多客户通用、属采集/检测核心通路 | **主程序原生** |
| 软件去皮 / 置零（T/Z 指令） | 设备控制基础能力 | **主程序原生**（✅ 已落盘 `send_device_command`）|
| 标准量对比（缺料/超量 + 容差） | 通用结算判定 | **主程序原生**（新结算模式）|
| 型号 → 标准量配方表 | 数据模型，所有配料客户都要 | **主程序原生**（新表）|
| 逐件称重记录 + 导出/上传 | 数据通路 | **主程序原生**（复用 session/cycle/step + 自定义导出）|
| 三色灯报警联动 | 已有 alarm 系统 | **主程序原生**（✅ 复用现有事件）|
| 「先选人员/型号否则报警」前置校验 | 通用前置闸门 | **主程序原生**（配置开关）|
| **钢帽/钢脚双料顺序编排** | 百斯特特有的两道料先后 | **配置**（料别列表）/ 必要时薄插件 |
| **三盆三工位聚合 all_ok** | 百斯特物理布局 | **配置**（复用 RFC10 工位组）|
| **具体型号标准量数值** | 百斯特工艺数据 | **配置数据**（配方表里维护）|
| **料别视觉识别（钢帽水泥 vs 钢脚水泥）** | 依赖客户训练的模型标签 | **主程序留 hook** + 客户模型 |

**结论**：建一类主程序原生的「称重检测应用」（新 `detection_mode` 或 `settlement_mode = weighing`），百斯特用它 + 配方配置 + 一个极薄的编排插件（仅放双料顺序/工位组这种纯编排）即可，**不再需要重逻辑插件**。

## 3. 主程序落地设计

### 3.1 数据模型（详见动手前过 `modify-model` skill）

新增两张表（沿用 SQLite + `migrate_database()` ALTER 兼容老库）：

**`weighing_recipes` 配方表**
```
id, project_id, model_name, material,          -- 型号 + 料别
standard, low_tol, high_tol,                   -- 标准量 + 上下容差 (kg)
created_at, updated_at
唯一约束 (project_id, model_name, material)
```

**`weighing_records` 逐件称重记录表**（满足 6.1 逐件记录）
```
id, session_id, cycle_id,                      -- 挂到现有 session/cycle 链
operator, model_name, product_sn,             -- 人员/型号/产品码
material, init_weight, final_weight, net,     -- 料别/初值/终值/净重
verdict, reason,                              -- ok|shortage|over|wrong + 原因
station_name, ts
```

> 优先复用现有 `Session/Cycle/Step` 状态机记录通路，`weighing_records` 作为称重特化视图；不另起一套数据生命周期。配方表是新概念，必须建表。

### 3.2 检测/结算模式

新增一类称重结算（走 `add-detection-mode` skill 全链路）：
- `pipeline_config` 增加 `weighing` 模式分支；
- 状态机：把已落盘的 `bestar/backend/state.py` 纯逻辑（`idle → await_tare → filling → done` 四相 + 稳定判定 + 双料推进）**上提为主程序通用称重状态机**，型号/料别/标准量从配方表注入，不写死百斯特字样。

### 3.3 称重器联动（✅ 已落盘，无需重做）

- 读数：`external_device_data` 钩子 → 喂状态机（已通）；
- 去皮/置零：`host.send_device_command(device_id, 'T'/'Z')`（已通，主程序原生 API）；
- 协议：`serial_command` 应答式（R 读 / T 去皮 / Z 置零），现场把秤设为传送方式 5。

### 3.4 报警 / MES（复用）

- 缺料/超量/投错/前置失败 → `trigger_alarm(event)` 打三色灯（复用现有 alarm 事件，现场对齐颜色）；
- 一件完成 → MES 上传 payload（型号/产品码/双料净重/判定/时间）。

### 3.5 前端（碰 .vue，开工须走 T4/T5/T6 强制验证）

- **配置页**：型号配方维护表（型号×料别→标准量/容差）、工位列表、去皮方式、前置开关、报警事件映射；
- **监控看板**：当前件状态（人员/型号/产品码/当前料别/实时净重/判定）、报警横幅；
- **数据页**：逐件称重记录查询 + 导出（复用自定义导出字段仓库）。

## 6. 与现有 `bestar` 插件的关系

现有 `plugins-examples/bestar/`（状态机/判定/单测）是**这套设计的可运行原型**，价值在于已经把验收逻辑跑通、单测绿。落地路径：

- `state.py` 纯状态机 → 上提为主程序通用称重状态机（去掉「钢帽/钢脚」硬编码字样，改由配方/料别列表注入）；
- `config.py judge_amount/get_model_spec` → 上提为主程序判定；
- `config.models` 临时配方 → 迁到 `weighing_recipes` 表；
- 插件**瘦身**为只剩百斯特编排（双料顺序 + 工位组绑定），或在主程序配置足够表达时直接退役插件。

## 7. 待确认清单（卡住施工的外部依赖）

1. **称重检测进主程序是否拍板？**（同意 → 按第 5 节开 S1）
2. **各型号标准量数值**：每个型号、钢帽水泥/钢脚水泥的标准量 + 上下容差（kg）。没有数值判定无从落地。
3. **料别识别方式**：钢帽水泥 vs 钢脚水泥怎么区分？
   - (a) 纯顺序（先帽后脚，软件按序）——最省，无需视觉；
   - (b) 视觉识别料别（需客户训练模型 + 标签名）；
   - (c) 扫码/工位区分。
4. **工位数与物理布局**：百斯特实际几个称重工位/几盆？是否要三盆聚合 all_ok。
5. **MES 上传字段与协议**：上传给谁、字段格式、触发时机（每件/每料）。
6. **三色灯事件颜色映射**：缺料/超量/投错/前置 分别对应现场哪个灯。

## 8. 风险与权衡

- **主程序原生 vs 插件**：进主程序后维护责任在主线，回归测试范围变大；但避免下一个配料客户重写，长期更省。
- **配方表是新 schema**：必须走 ALTER 兼容老库，别破坏存量客户升级（不变量 #8）。
- **料别视觉防错依赖客户数据**：模型标签没到位前，6.3 只能先用「纯顺序」兜底，验收时需和客户说明。
- **状态机上提**：从插件搬进主线要保留错误隔离，称重逻辑异常不能拖垮主检测通路。

## 9. 落地完成记录（2026-06-29）

主程序原生「称重投料模式」（`logic_mode='weighing'`）已实现并验证，**bestar 示例插件已退役删除**（逻辑已上提主线，由原生引擎承接）。

**后端**
- `backend/services/weighing_engine.py`：原生称重引擎（工位状态机 + 配置 + 副作用执行，错误隔离）。
- `backend/api/weighing.py`：`/api/v1/weighing/*`（状态/上下文/扫码/去皮/置零/复位/视觉料别/记录/虚拟喂重）。
- `backend/api/source_project_config_apply.py`：激活 weighing 项目时按通道登记/注销引擎（非 weighing 通道主动注销，零残留）。
- `backend/services/external_device_pipeline.py`：称重器读数仅对 `is_weighing_channel` 的通道喂入引擎（其它通道零影响）。
- 配方/标准量存 `pipeline_config.weighing`（型号→料别→标准量+上下公差），未新增 ORM 表。

**前端**
- Project 页新增「称重投料模式」单选 + 「称重配置」页签（前置要求/料别顺序/型号标准量表/去皮稳定/校验报警）。仅 weighing 项目注入配置，**非称重项目零污染**（存库不含 weighing 键，已验）。
- Monitor 页 `WeighingPanel.vue`：人员/型号选择 + 扫码开始 + 实时重量 + 各料投料进度看板 + 本件结论。
- Data 页：称重项目时主区切为逐件记录表（统计 + 字段表 + CSV 导出），其它项目原样不动。

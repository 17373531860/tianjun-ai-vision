# 120 工位 AI 视觉检测系统 — 方案 B：中心服务器 + 边缘算力机分布式架构

> 文档版本：v1.0　|　编制日期：2026-06-22　|　适用项目：大客户 120 工位产线视觉检测
> 配套方案：方案 A（单服务器集中式），两份对照阅读
> **本方案为推荐方案**（理由见第七节）

---

## 一、方案概述

### 1.1 一句话定位

**算力下沉到产线边缘——用 30 台边缘算力机（每台带 4 个工位）就近承载视频解码与 AI 推理；中心服务器只做控制下发、状态聚合、数据存储与 MES 外推；所有工位现场不再配独立屏幕，统一由一块数据总控大屏实时监控、配置参数、启停控制。**

### 1.2 核心特征

| 特征 | 说明 |
|---|---|
| 算力分布 | 120 路拆给 30 台边缘机，每台只扛 4 路，互相物理隔离 |
| 边缘自治 | 中心或网络断开时，边缘机本地继续检测 + 缓冲，恢复后补传 |
| 工位无屏 | 现场工位只保留相机 + 报警/IO，边缘机就近壁挂/机柜安装，无屏 |
| 单一大屏 | 一块总控大屏（Web 应用）聚合 120 工位状态、画面、控制 |
| 中心配置 | 工位参数、开始/停止集中在大屏端设置，下发到对应边缘机 |
| 数据集中 | 检测记录、缺陷、MES 汇聚中心库，录像可中心存或边缘分存 |

### 1.3 与现有天军系统的关系

天军现有的**集群主从机制（心跳、从机上报主机、超时检测）是本方案唯一能直接当地基复用的部分**——它已有「从机上报主机」雏形，控制平面可在其上扩展为双向。其余改造：

- 边缘机**无头化**：砍掉 Electron 桌面壳 + 前端，只留检测引擎 + 受控/上报客户端
- 前端从「单机 4 工位监控」重写为「120 工位聚合大屏」
- 数据库从 SQLite 迁移到 **PostgreSQL**（中心库）
- 配置改为「中心下发 + 边缘缓存」，支撑断网自治

## 二、测算基准（所有数字的根，必须先对齐）

```
负载:     120 路 × 1080p × 25fps = 3000 帧/秒解码 + 3000 次/秒推理
模型假设:  YOLOv8s @640 + TensorRT FP16（工业检测典型配置）

单卡全链路带路数（含解码 + 推理 + 录像编码）:
   YOLOv8n/s @640  → 中端卡(4070/A4000) 4~6 路/卡   ← 本方案每台带 4 路
   YOLOv8m  @640  → 中端卡 2~4 路/卡
   重模型/imgsz1280 → 1~2 路/卡
```

> ⚠️ **关键风险前提**：若客户实际模型更重或推理分辨率要 1280，每台边缘机带路数下降，**边缘机台数需相应增加**（如每台降到 2 路 → 需 60 台）。立项前必须用客户真实模型实测。

## 四、数据流与软件改造点

### 4.1 控制平面（下行：配置 + 启停）

1. 操作员在大屏点选「工位 37 → 修改阈值 / 开始 / 停止」
2. 大屏 → 中心控制平面 → 定位工位 37 所属边缘机 → 下发命令
3. 边缘机执行后**回执确认**，中心更新状态，大屏据此刷新
4. 配置同时存中心 PostgreSQL **并下发缓存到边缘机本地**（断网自治前提）
5. 批量启停（一键停全线）做成**幂等可重试**

### 4.2 数据平面（上行：状态 + 画面 + 结果）

1. **实时状态**：各边缘机主动推送状态到中心聚合层，大屏订阅增量（**推送模型，非轮询**）
2. **视频画面**：120 路绝不全推高清。两级——概览墙显示**分页低帧率缩略图**（每页如 24/30 路，带状态角标、NG/停止提示、FPS/节拍摘要），大屏点选某工位才向对应边缘机按需请求高清流中转
3. **检测结果/缺陷**：边缘机上报中心写入 PostgreSQL；录像可中心集中存或边缘本地存（断网时先存本地，恢复补传）

### 4.3 必须的软件改造清单

| 改造项 | 现状 | 目标 |
|---|---|---|
| 边缘节点形态 | Electron 胖客户端 | 无头检测引擎 + 受控/上报客户端 |
| 前端 | 单机 4 工位监控 | 120 工位聚合大屏（分页缩略图墙 + 下钻高清） |
| 状态传输 | 前端轮询本机后端 | 边缘→中心推送 + 大屏订阅 |
| 控制下发 | 本机前端控本机 | 中心→边缘命令通道 + 回执（扩展集群机制） |
| 数据库 | SQLite 单文件 | PostgreSQL 中心库 |
| 配置 | 本地存本地用 | 中心存 + 边缘缓存 + 热加载 |
| 断网行为 | 无 | 边缘本地自治 + 缓冲补传 |
| 视频 | 本机 MJPEG 直推 | 中心按需向边缘拉流中转 |

## 七、风险与利弊

### 7.1 优点 / 好处（本方案核心价值）

| 优点 | 说明 |
|---|---|
| **故障域隔离** 🟢 | 单台边缘机故障只影响其 4 个工位，其余 116 工位照常运行 |
| **断网自治** 🟢 | 中心/网络断开时边缘机本地继续检测 + 缓冲, 不停产 |
| **线性扩展** 🟢 | 加工位 = 加边缘机, 平滑扩展, 无单机算力天花板 |
| **网络压力分散** 🟢 | 相机流就近进边缘机, 中心只收状态/结果, 不汇聚 120 路原始流 |
| **中心负载轻** | 中心不背推理, 普通服务器即可, 无需多卡高密度机 |
| **就近部署** | 边缘机靠工位安装, 布线短, 适配分散产线 |
| **边缘延迟低** | 检测在本地完成, 不依赖往返中心 |

### 7.2 风险 / 弊端

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| 运维点多 | 🟠 中 | 30 台边缘机需统一运维 | 远程批量运维/监控 + 标准化镜像 |
| 中心仍是单点 | 🟠 中 | 中心服务器故障影响聚合/控制（但边缘仍自治检测） | 中心主备双机 |
| 边缘机环境 | 🟠 中 | 现场粉尘/温度/振动对设备要求高 | 选工业级机型 + 防护机柜 |
| 边缘算力浪费 | 🟡 低 | 每台 4 路, 卡可能未跑满 | 可调每台带路数（4→6） |
| 分布式软件复杂 | 🟠 中 | 控制下发回执 + 断网补传 + 配置同步 | 走 RFC 立项, 复用集群机制 |
| 部署工作量 | 🟡 低 | 30 台逐台部署 | 标准化镜像 + 自动注册 |

### 7.3 适用场景

- 产线级关键生产，**不可接受全线停产风险**（绝大多数工厂）
- 工位物理分散，就近边缘部署比集中布线更经济
- 未来有扩工位/扩产线的扩展需求
- 现有天军集群机制可复用，软件演进路径更顺

## 八、存储与 180 天数据

```
存储内容          单路/天      120路/天      180天总量      落点
---------------   ---------    ----------    -----------    ----------------------
仅结构化数据      50~200 MB    6~24 GB       1~4 TB         中心 PostgreSQL
事件片段录像      5~15 GB      0.6~1.8 TB    110~320 TB     中心存储池 或 边缘分存
7×24连续录像      ~42 GB       ~5 TB         ~900 TB(≈1PB)  中心存储集群
```

- **结构化数据必须 PostgreSQL**（中心库），SQLite 在 120 工位 ×180 天必崩
- 录像可**中心集中存**（便于统一回放）或**边缘分散存**（省中心带宽，但回放需中转）——建议中心集中存
- 关键待客户确认：180 天存的是**仅结构化数据 / 事件片段 / 连续录像**，量级差几十倍

## 九、实施路线（建议）

1. 客户真实模型实测单台边缘机带路数 → 锁定边缘机台数（30 或 60）
2. 数据库迁 PostgreSQL（中心库, 前置）
3. 边缘节点无头化（砍 Electron + 前端, 留检测引擎 + 受控客户端）
4. 中心控制平面（命令下发 + 回执 + 配置下发, 扩展现有集群机制）
5. 状态聚合 + 推送通道（边缘推 + 大屏订阅）
6. 断网自治 + 缓冲补传（边缘本地缓存 + 恢复同步）
7. 120 工位聚合大屏前端
8. 按需视频中转（最吃带宽, 最后做）
9. 整线联调 + 断网/故障演练（拔网线/关边缘机验证不停产）

> 本方案属架构级重构，**必须先写 RFC 立项**，重点定清断网语义、配置同步、控制回执的一致性。

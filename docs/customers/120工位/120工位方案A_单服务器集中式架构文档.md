# 120 工位 AI 视觉检测系统 — 方案 A：单服务器集中式架构

> 文档版本：v1.0　|　编制日期：2026-06-22　|　适用项目：大客户 120 工位产线视觉检测
> 配套方案：方案 B（中心服务器 + 边缘算力机分布式），两份对照阅读

---

## 一、方案概述

### 1.1 一句话定位

**用一台（或一对）高密度多卡 GPU 服务器，集中承载全部 120 个工位的视频解码、AI 推理、数据汇聚与控制下发；所有工位现场不再配独立屏幕，统一由一块数据总控大屏实时监控、配置参数、启停控制。**

### 1.2 核心特征

| 特征 | 说明 |
|---|---|
| 算力集中 | 全部 120 路 1080p@25fps 的解码 + 推理跑在单台 GPU 服务器内 |
| 工位无屏 | 现场工位只保留相机 + 报警/IO 设备，不装工控机、不装屏幕 |
| 单一大屏 | 一块总控大屏（Web 应用）聚合显示 120 工位状态、画面、控制 |
| 中心配置 | 每个工位的检测参数、开始/停止等全部在大屏端集中设置与下发 |
| 数据集中 | 检测记录、缺陷、MES 数据、录像全部落在服务器/存储池 |

### 1.3 与现有天军系统的关系

天军现有形态是「一机一屏胖客户端」——每台工控机自带后端 + 前端 + 大屏，自己配自己、自己控自己，集群只汇总 MES/结算数据。本方案需要对软件做**架构级重构**：

- 后端检测引擎在单服务器内以**多实例/多进程**方式并行承载 120 路（突破现有单实例 4 工位上限）
- 前端从「单机 4 工位监控」重写为「120 工位聚合大屏」
- 数据库从 SQLite 单文件迁移到 **PostgreSQL**
- 桌面壳（Electron）在服务器侧保留或改为纯 Web 部署，工位侧彻底取消

## 二、测算基准（所有数字的根，必须先对齐）

```
负载:     120 路 × 1080p × 25fps = 3000 帧/秒解码 + 3000 次/秒推理
模型假设:  YOLOv8s @640 + TensorRT FP16（工业检测典型配置）

单卡全链路带路数（含解码 + 推理 + 录像编码，4090 / L40S 级）:
   YOLOv8n/s @640        → 12 ~ 16 路/卡   ← 本方案按 15 路/卡估
   YOLOv8m  @640         → 6 ~ 10 路/卡
   YOLOv8l/x 或 imgsz1280 → 3 ~ 5 路/卡
```

> ⚠️ **关键风险前提**：以上是整套配置的根。若客户实际模型更重、或推理分辨率要 1280，单卡带路数下降，**GPU 数量需按上表比例整体上调（最多翻 2~3 倍）**。立项前必须用客户真实模型实测单卡带路数。

### 3.2 物理节点构成

| 节点 | 数量 | 职责 |
|---|---|---|
| GPU 服务器 | 1 台（极限）/ 2 台（冗余） | 全部解码 + 推理 + 控制 + 聚合 + 数据库 |
| 总控大屏 | 1 套（大屏一体机或拼接屏 + 瘦客户端） | 监控 + 配置 + 控制的唯一人机界面 |
| 存储池 | 1 台存储服务器 / NAS | 录像 + PostgreSQL 数据盘（大容量） |
| 工业交换机 | 按端口数 | 120 路相机汇聚 + 上联服务器 |
| 网络相机 | 120 台 | 现场采集（1080p@25fps，POE/RTSP） |

## 四、数据流与软件改造点

### 4.1 控制平面（下行：配置 + 启停）

1. 操作员在大屏点选「工位 37 → 修改阈值 / 开始 / 停止」
2. 大屏 → 控制平面下发命令到对应检测实例
3. 实例执行后**回执确认**（已启动/已停止/已生效），大屏据回执更新状态
4. 工位配置统一存 PostgreSQL，下发即改库 + 推送实例热加载

### 4.2 数据平面（上行：状态 + 画面 + 结果）

1. **实时状态**：各检测实例把状态变化（运行/停止/当前步骤/OK·NG 计数/FPS）推送到聚合层，大屏订阅增量（**推送模型，非轮询**）
2. **视频画面**：120 路绝不全推高清。两级策略——概览墙显示**分页低帧率缩略图**（每页如 24/30 路，带状态角标、NG/停止提示、FPS/节拍摘要），大屏点选某工位才按需拉该路高清流
3. **检测结果/缺陷**：写入 PostgreSQL，录像落存储池

### 4.3 必须的软件改造清单

| 改造项 | 现状 | 目标 |
|---|---|---|
| 检测引擎并发 | 单实例 ≤4 工位 | 单机多实例承载 120 路 + GPU 亲和绑定 |
| 前端 | 单机 4 工位监控 | 120 工位聚合大屏（分页缩略图墙 + 下钻高清） |
| 状态传输 | 前端轮询本机后端 | 边缘→中心推送 + 大屏订阅 |
| 数据库 | SQLite 单文件 | PostgreSQL |
| 配置 | 本地存本地用 | 中心库统一存 + 下发热加载 |
| 视频 | 本机 MJPEG 直推 | 按需拉流中转 |
| 控制 | 本机前端控本机 | 大屏集中下发 + 回执 |

## 七、风险与利弊

### 7.1 优点 / 好处

| 优点 | 说明 |
|---|---|
| 运维点单一 | 只有 1 台服务器要管，机房集中，巡检/升级/备份都在一处 |
| 机房集中 | 算力、存储、网络全在机房，工位现场零主机、零屏幕、极简 |
| 无边缘延迟 | 所有数据在一台机内流转，无跨节点网络往返 |
| 部署快 | 一台服务器装好即整线就绪，无需逐台部署 30 台边缘机 |
| 成本可能更省卡 | 卡集中复用，避免边缘机各自算力浪费 |

### 7.2 风险 / 弊端（必须向客户明示）

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| **全线单一故障域** | 🔴 极高 | 服务器宕机/关键部件故障 → **120 条产线全停** | 上双机热备（但即失去"单服务器"经济性） |
| **满载无冗余** | 🔴 高 | 8 卡每卡压 15 路是极限, 一张卡掉 → 丢 15 工位 | 降到每卡 8 路需 2 台机 |
| **网络汇聚瓶颈** | 🟠 中 | 120 路 RTSP 全汇一台, 25G 网卡 + 交换机必须到位 | 双 25G 聚合 + 工业级交换 |
| **机房依赖** | 🟠 中 | 高密度 5kW/4U, 对机房供电/散热要求高 | 机房空调 + UPS |
| **扩展性差** | 🟠 中 | 8 卡到顶, 再加工位需换机或加机 | 预留下一台位置 |
| **断网无自治** | 🟠 中 | 工位无本地算力, 服务器或网络断 → 工位直接瞎 | 无解（架构固有） |
| **软件重构量大** | 🟠 中 | 单机多实例 + 聚合 + 大屏全新做 | 走 RFC 立项 |

### 7.3 适用场景

- 机房条件好、可接受「集中故障域」换「集中运维」的客户
- 工位物理集中、布线到机房成本可控
- 对单点停产风险有冗余预算（实际建议双机）

## 八、存储与 180 天数据

```
存储内容          单路/天      120路/天      180天总量      落点
---------------   ---------    ----------    -----------    -------------
仅结构化数据      50~200 MB    6~24 GB       1~4 TB         PostgreSQL
事件片段录像      5~15 GB      0.6~1.8 TB    110~320 TB     存储服务器
7×24连续录像      ~42 GB       ~5 TB         ~900 TB(≈1PB)  存储集群
```

- **结构化数据必须 PostgreSQL**，SQLite 在 120 工位 ×180 天（可能几十亿条记录）必崩
- **录像独立存储池**，绝不进数据库；采购按净容量 ×1.4 留冗余余量
- 关键待客户确认：180 天存的是**仅结构化数据 / 事件片段 / 连续录像**，量级差几十倍

## 九、实施路线（建议）

1. 客户真实模型实测单卡带路数 → 锁定 GPU 数量
2. 数据库迁 PostgreSQL（前置）
3. 检测引擎单机多实例 + GPU 亲和改造
4. 控制平面（命令下发 + 回执 + 配置中心）
5. 状态聚合 + 推送通道
6. 120 工位聚合大屏前端
7. 按需视频中转（最吃带宽，最后做）
8. 整线联调 + 压测（满 120 路满载稳定性）

> 本方案属架构级重构，**必须先写 RFC 立项**，定清接口、故障语义、断网行为再动手。

## 二、接口落实（含我方实际地址）

### 2.1 开工信息推送（A → B，我方接收）

- 我方提供入站接收接口，收到后：① 以**任务号**登记一次生产任务；② 按**产品代号自动切换到对应检测项目与模型**；③ 在检测界面显示任务号 / 产品代号 / 工序工步 / 操作人员；④ 返回 `{code,message}`，异常按贵司业务错误码回报（如重复开工 40001）。
- **⚠️ 关键：我方实际接收地址与协议示例不同。**
  协议示例写的是 `/api/v1/task/start`；我方实际暴露的接收地址会带我方约定前缀，**形如**：

  ```
  POST  http://{我方IP}:{端口}/api/v1/integrations/chuannan/task/start
  ```

  > 接收 URL 由我方（服务端）定义。上面仅为示意，**最终完整地址清单（开工 / 健康检查等）我方在联调前一次性提供并锁定**，请贵司**以我方提供的最终地址为准调用**，不要使用协议示例里的占位路径。

### 2.2 报警信息推送（B → A，我方发送）

- 触发报警时，我方向贵司 `POST /api/v1/warning/report` 推送（地址以贵司提供为准），含：任务号、产品代号、工序工步、操作人员、**报警截图（JPEG 纯 Base64，不含 data 前缀）**、报警文本、报警时间。
- 重试：失败重试最多 3 次、指数退避 1s→2s→4s、仅对网络超时与 5xx 重试、4xx 不重试。
- 节流：同一任务、同一类型报警 5 秒内不重复推送。

### 2.3 完工信息上报（B → A，我方发送）

- 当前零件装配完成后，我方向贵司 `POST /api/v1/task/complete` 推送，含：任务号、产品代号、工序工步、操作人员、`IsComplete=true`、完工时间。

### 2.4 健康检查（双向）

- 我方提供 `GET .../health` 返回 `{code:0,message:"ok"}`；亦定期探测贵司健康接口。

## 三、最终报文样例（按贵司协议字段）

### 3.1 开工（贵司 → 我方）

请求：

```json
{
  "TaskNo": "TASK-20260623-001",
  "ProductCode": "PROD-X9-02",
  "StepCode": "1.1",
  "Operator": "张三",
  "BeginTime": "2026-06-23T08:30:00"
}
```

我方响应（成功 / 失败）：

```json
{ "code": 0, "message": "success" }
```
```json
{ "code": 40001, "message": "TaskNo 已存在，该任务已开工" }
```

### 3.2 报警（我方 → 贵司）

```json
{
  "TaskNo": "TASK-20260623-001",
  "ProductCode": "PROD-X9-02",
  "StepCode": "1.1",
  "Operator": "张三",
  "Image": "<JPEG 纯 Base64，不含 data:image 前缀>",
  "WarningText": "XXX零件装配顺序错误",
  "BeginTime": "2026-06-23T09:15:32"
}
```

### 3.3 完工（我方 → 贵司）

```json
{
  "TaskNo": "TASK-20260623-001",
  "ProductCode": "PROD-X9-02",
  "StepCode": "1.1",
  "Operator": "张三",
  "IsComplete": true,
  "BeginTime": "2026-06-23T09:45:10"
}
```

> 业务错误码我方按贵司 4.2 节执行（40001 重复开工 / 40002 未开工 / 40003 重复完工 / 40004 字段缺失 / 40005 图片解码失败 / 40006 状态不允许）。

## 四、仍需贵司确认（请逐条回填，尤其第 1、2、3 条）

| 编号 | 事项 | 说明 | 贵司确认 / 填写 |
|------|------|------|------|
| 1 | **产品代号 ↔ 检测项目 对应关系** | `ProductCode`（如 `PROD-X9-02`）需对应我方一个检测项目。二选一：(a) 我方项目直接命名为产品代号（最简单）；(b) 贵司提供对照表。**另**：推来的产品代号我方尚未配置项目时，期望：报错返回 / 忽略继续 / 用默认项目？ |  |
| 2 | **网络环境** | 因开工为贵司主动推给我方，我方工控机需作为**服务端被访问**。请确认：① 双方 IP / 端口；② 是否同一局域网可互通；③ 现场防火墙放行我方接收端口；④ 我方工控机能否分配**固定 IP**。 |  |
| 3 | **接口安全** | 协议为"无鉴权"。开工接口可触发**建任务 + 切检测项目**，建议至少加一道防护：(a) IP 白名单（仅放行贵司中控 IP）或 (b) 固定 Token（Header 携带）。或贵司确认"仅可信内网，无需鉴权"。 |  |
| 4 | **报警推送粒度** | 「每出现一件不良即时推一条」还是「按工序/批次汇总推」？我方默认「即时推 + 同任务同类型 5 秒去重」。 |  |
| 5 | **图片格式与大小** | 报警截图我方以 **JPEG 纯 Base64**发送。请确认：① 贵司按 JPEG 解码（协议示例串为 PNG 头，以 JPEG 为准）；② 单次请求体上限（我方建议原始 ≤2MB / Base64 ≤2.7MB，超出自动压缩）。 |  |
| 6 | **批次 / 数量** | 协议未含「批次」「数量」。确认以**任务号为唯一生产单元**管理、无需批次/数量？ |  |

## 五、我方实现要点（供贵司知悉）

1. **任务状态机**：我方维护未开工 → 进行中 → 已完工，异常跃迁按贵司业务错误码回报。
2. **入站健壮性**：开工接口做字段校验（缺失返 40004），「按产品码切项目」失败给明确错误码，不静默失败。
3. **图片压缩兜底**：截图超约定大小自动压缩再传，避免 413。
4. **日志可追溯**：开工 / 报警 / 完工全程记录通讯日志（时间、耗时、响应码），便于联调与现场排查。

## 一、总体确认

收到贵司《通信接口协议文档 v1.0》，**整体方案我方认可**：

- 采用 **双向 HTTP / JSON、互为服务端** 的通信模型；
- 数据格式 `application/json; charset=utf-8`、UTF-8 编码、时间统一 ISO 8601（本地时间），我方遵循；
- 三个业务接口（开工 / 报警 / 完工）+ 健康检查的划分清晰，我方可按此实现；
- 通用响应 `{ code, message, data? }`、`code=0` 为成功，我方遵循。

下面先逐接口确认我方的实现承诺，再列出**仍需贵司进一步明确**的事项（第三节，最关键）。

## 二、逐接口确认（我方实现承诺）

### 2.1 开工信息推送（A → B，我方作为服务端接收）

- 我方提供接收接口 `POST /api/v1/task/start`，接收贵司开工信息。
- 收到后我方处理：
  1. 以 **任务号（TaskNo）** 建立 / 登记一次生产任务；
  2. 按 **产品代号（ProductCode）自动切换到对应的检测项目与模型**；
  3. 在检测界面显示 **任务号 / 产品代号 / 工序工步（StepCode）/ 操作人员（Operator）**；
  4. 返回 `{ code, message }`，并按贵司业务错误码约定回报（如重复开工返回 40001）。

> 说明：贵司确认为「中控系统主动推送给我方」（A→B），与我方现有「我方主动查询」方向相反，因此我方将**新增此入站接收接口**承接，符合贵司协议设计。

### 2.2 报警信息推送（B → A，我方作为客户端发送）

- 触发报警时，我方向贵司 `POST /api/v1/warning/report` 推送，字段含：
  任务号、产品代号、工序工步、操作人员、**报警截图（Base64 JPEG，不含 data 前缀）**、报警文本、报警时间。
- 重试策略遵循贵司约定：失败重试最多 3 次、指数退避 1s→2s→4s、仅对网络超时与 5xx 重试、4xx 不重试。
- 报警节流：同一任务、同一类型报警 5 秒内不重复推送（与贵司注意事项第 3 条一致）。

### 2.3 完工信息上报（B → A，我方作为客户端发送）

- 当前零件装配完成后，我方向贵司 `POST /api/v1/task/complete` 推送，字段含：
  任务号、产品代号、工序工步、操作人员、`IsComplete=true`、完工时间。

### 2.4 健康检查（双向）

- 我方提供 `GET /api/v1/health`，返回 `{ code: 0, message: "ok" }`，供贵司探活；我方亦会定期探测贵司健康接口。

## 四、我方实现要点说明（供贵司知悉）

1. **任务状态机**：我方将维护任务状态（未开工 → 进行中 → 已完工），对异常跃迁（重复开工、未开工就完工、重复完工等）按贵司业务错误码（40001~40006）回报。
2. **入站接口健壮性**：开工接口将做参数校验（必填字段缺失返回 40004），并在「按产品码切项目」失败时给出明确错误码，避免静默失败。
3. **图片压缩兜底**：报警截图超过约定大小，我方自动压缩后再传，避免触发 413。
4. **日志可追溯**：所有接口调用（开工 / 报警 / 完工）我方均记录完整通讯日志（时间、耗时、响应码），便于双方联调与现场排查。

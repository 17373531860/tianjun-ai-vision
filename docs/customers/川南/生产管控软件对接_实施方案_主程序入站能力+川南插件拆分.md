## 〇、一句话结论

川南这套对接 **整体走"客户专属 Tier3 全栈插件"**（属"客户对接自家 IT 系统"一档，绝不污染主程序）。
但其中"开工推送（中控主动推给我方 → 自动切检测项目）"依赖两个**当前插件平台还没有的入站能力**，必须**先补进主程序平台**（给所有客户复用），再由川南插件调用——不允许插件越权或在主程序硬编码川南逻辑。

## 一、归位判定

| 子项 | 调用方向 | 类型 | 归位 |
|------|---------|------|------|
| 开工信息接收 | A → B（我方收） | C 客户 IT 对接 + 依赖平台入站能力 | **川南插件** + 先补主程序平台能力 |
| 报警信息推送 | B → A（我方发） | C 客户 IT 对接 | **川南插件**（复用现有出站网关） |
| 完工信息上报 | B → A（我方发） | C 客户 IT 对接 | **川南插件**（复用现有出站网关） |
| 健康检查 | 双向 | 基础设施 | 主程序已具备 `GET /health` 类探活，插件补川南约定格式 |

**反模式自检（均不踩）**：
- ❌ 主程序加 `if customer == 川南` 切项目 → 用平台通用 API
- ❌ 主程序 schema 加川南专用字段 → 任务态/映射全进插件
- ❌ "先在主程序临时加开工接口，以后迁插件" → 直接走插件 + 平台能力

## 二、现状能力盘点

| 能力 | 现状 | 证据 | 结论 |
|------|------|------|------|
| 出站推送（报警/完工 B→A） | ✅ 现成 | MES Gateway 5 适配器 + 重试 + 鉴权；`PluginHost.mes_push`（cap `runtime.mes_push`） | 插件配置连接 + 模板即可 |
| 报警触发时机 | ✅ 现成 | 插件 hook：`event_fire` / `pre_cycle_end` / `trigger_alarm` | 插件挂 hook 捕获 NG/报警 |
| 报警截图（Base64 JPEG） | ⚠️ 有底层无主动 API | `VideoSourceManager.get_snapshot()` + `GET /snapshot?channel=N` | **需包成插件可调的主动 API**（缺口 P2） |
| 插件挂自有后端路由（收开工） | ✅ 现成 | `RoutesRegistry.include_router` → 挂到 `/api/v1/plugins/{客户码}/{子路径}` | 插件 Tier3 全栈实现入站接口 |
| 按产品代号切换当前检测项目 | ❌ 缺 | `PluginHost` 无 `activate_project`/`switch_project`；主程序有 `POST /projects/{id}/activate` 但插件无主动 API 入口 | **必须补主程序平台能力**（缺口 P1） |
| 任务信息（任务号/产品/工序/操作员）显示到检测界面 | ✅ 可拼 | `PluginHost.write_system_config`（cap `runtime.system_config_write`）+ 监控页 `TjSlot` | 插件前端 slot + 系统配置即可，无需新 API |
| 任务状态机（未开工→进行中→已完工） | ❌ 川南专属 | 川南错误码 40001~40006 是其业务约定 | 全进插件，主程序不背 |

## 三、拆分方案

### 3.1 主程序平台能力（基础设施，给所有客户复用）

> 原则：只补"通用入站能力"，不含任何川南字段/逻辑。补的同时保证别家客户的中控/MES 主动推送对接都能复用。

**P1 — 新增插件主动 API：切换当前检测项目**
- 位置：`backend/plugin_system/registry.py: PluginHost`
- 形如 `activate_project_by(self, project_id=None, project_name=None) -> bool`
- 实现：包装现有 `projects.py` 的 `_sync_project_config_to_channels` + `_reload_model_for_active_project` 激活逻辑（复用，不重写）
- 守门：新增 capability `runtime.project_activate` + audit log + 错误隔离（切换失败不崩主程序）
- 价值：任何"外部系统按产品码让我方切项目"的对接都用得到

**P2 — 新增插件主动 API：取指定通道当前帧截图**
- 位置：同上 `PluginHost`
- 形如 `get_channel_snapshot(self, channel_id=0, fmt="jpeg") -> bytes|base64`
- 实现：包装现有 `VideoSourceManager.get_snapshot()` + `cv2.imencode`
- 守门：capability `runtime.frame_snapshot` + audit log
- 价值：报警推送/事件留证类对接通用

**P3 —（可选，能力已够，仅约定用法）任务信息上屏**
- 不新增 API：插件用 `write_system_config` 写任务号/产品/工序/操作员 + 监控页 `TjSlot`（如 `monitor.layout.*`）渲染
- 仅需在插件侧实现，主程序零改动

> P1/P2 都是"插件平台主动 API 面"的扩展，与 v3.13.1 既有的 `trigger_alarm`/`mes_push` 同构，风险可控、可单测。

### 3.2 川南专属插件（Tier3 全栈，所有川南逻辑收敛于此）

**后端（插件挂载路由 + 业务）**
1. 入站接口：在 `/api/v1/plugins/chuannan/...` 下挂 3 条路由
   - `POST .../task/start`：校验字段 → 按 `ProductCode` 查映射 → 调 `host.activate_project_by(...)` → 写任务态 → 返川南 `{code,message}`（重复开工 40001 等）
   - `POST .../warning/report`、`.../task/complete`：见下"出站"
2. **ProductCode ↔ 检测项目映射**：存插件自有配置（plugin_data / 插件配置表），不进主程序 schema
3. **任务状态机**：未开工→进行中→已完工 + 川南错误码 40001~40006，全在插件内
4. 出站封装：
   - 报警：挂 `event_fire`/`trigger_alarm` hook → `host.get_channel_snapshot()` 取截图 → 组川南报警报文（TaskNo/Image/WarningText…）→ `host.mes_push()` 推给中控 `/api/v1/warning/report`
   - 完工：挂 `pre_cycle_end`/工件流完成 hook → 组完工报文 → `host.mes_push()` 推 `/api/v1/task/complete`
   - 节流：同任务同类型报警 5 秒去重（插件内）
5. 健康检查：插件暴露川南约定格式 `GET .../health` → `{code:0,message:"ok"}`

**前端（插件 slot）**
- 监控页显示 任务号/产品代号/工序工步/操作员（读 system_config 或 plugin_data）

## 五、必须先与客户确认（阻塞联调，已在 v2 回复稿列出）

1. **接口 URL 前缀**：我方入站接口实际落在 `/api/v1/plugins/chuannan/task/start`（插件命名空间隔离），**与协议示例 `/api/v1/task/start` 不同**。请中控按我方实际 URL 调用（这些 URL 由我方定义，A 调用即可）。
2. **ProductCode ↔ 项目映射**：项目直接命名为产品代号 / 还是给对照表；未配置产品码时如何处置。
3. **网络与安全**：我方需作为服务端被访问 → 固定 IP + 端口 + 防火墙放行；"无鉴权"建议加 IP 白名单或固定 Token 兜底（开工接口能建任务+切项目，安全敏感）。
4. **图片**：JPEG 纯 Base64（协议示例串是 PNG 头，确认按 JPEG 解码）+ 请求体上限。

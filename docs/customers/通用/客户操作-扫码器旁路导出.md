# 扫码器旁路导出 — 客户操作指引

> v3.7.2 新增。当客户扫码器无法直接接入软件、但会在固定目录里生成 txt 文件（含序列号）时使用。

## 场景

```
[扫码器扫码]   →   [固定目录写一个 txt]   →   [产线开始检测]   →   [一轮检测结束]
   ↑                                                                       ↓
   客户的设备，我们不控制                                            我们做的: 读这份 txt + 拼上检测结果 + 写到客户指定文件夹
```

最终输出文件每个周期一份，5 行（中间一行空）：

```
WP20260513_001    ← 扫码序列号（来自客户扫码器的 txt）
                  ← 空行
合格              ← 本周期判定 OK/NG
取件: 2.34s | 装配: 5.67s | 检查: 1.89s    ← 各步骤检测时长
v3.7.2            ← 软件版本号
```

## 步骤

### 1. 复制系统预设模板

进入「数据 → 自定义导出 → 模板管理」，找到系统预设：

> **扫码器旁路三行 TXT (序列号+OK/NG+步骤时长+版本)**

点击「复制为自建模板」，命名为「客户扫码器旁路」之类的。

### 2. 新建实时规则

进入「数据 → 实时导出规则」→ 「新建规则」，填如下字段：

| 字段 | 填写 |
|---|---|
| 规则名称 | 任意，例如「扫码器旁路-工位1」 |
| 启用 | ✅ |
| 绑定模板 | 选刚才复制的「客户扫码器旁路」 |
| 触发事件 | **cycle_end** |
| 输出目录 | 客户希望结果落到的文件夹，例 `D:/检测结果输出/` |
| 输入目录 | **客户扫码器生成 txt 的目录**，例 `D:/扫码器输入/` |
| 输入文件改写模式 | **none**（注意：不要选 append） |
| 文件名模板 | 三选一，见下 |
| 换行符 | **crlf**（Windows 客户必选） |
| 编码 | utf-8（或 utf-8-sig 如果客户用 Excel 打开） |
| 取文件策略 | **C · 周期开始锁快照**（推荐） |
| 同名去重 | 看下方说明决定开不开 |

### 3. 文件名模板（三选一）

| 风格 | 模板 | 输出样例 |
|---|---|---|
| **跟扫码 txt 同名** | `{{ latest_input_filename() }}` | `WP20260513_001.txt` |
| **加 cycle ID** | `{{ latest_input_filename() \| replace('.txt','') }}_{{ cycle.id }}.txt` | `WP20260513_001_42.txt` |
| **时间戳命名** | `{{ now('%Y%m%d_%H%M%S') }}.txt` | `20260513_031500.txt` |

如果客户要自定义命名规则，可以按 Jinja2 语法自由组合，例如：

```
{{ workpiece.serial_no or latest_input_filename() | replace('.txt','') }}_{{ '%.0f' % cycle.duration }}s.txt
```

## 取文件策略详解

### C 策略（推荐，默认选这个）

**周期开始那一刻就锁住扫码 txt 内容，写到数据库，结束渲染时直接用快照。**

- 准确度最高：周期内即使扫码器又写了新文件，本周期用的还是开始时锁定的那份
- 数据库留痕：`cycle.external_meta` 字段保存「这一轮锁了哪份扫码 txt」，事后追溯查得到
- 唯一前提：扫码器必须**先于**周期开始就完成 txt 写入（你客户场景符合）

### B 策略（保险）

**结束时去翻文件夹，但加两个保险**：

- **稳定等待 (毫秒)**：先看一次 size+mtime，等 N 毫秒，再看一次，一致才采纳。挡掉「扫码器还在写、文件没刷盘完」的情况。建议 100ms。
- **最大年龄 (秒)**：只接受 mtime 在最近 N 秒内的文件。超期不要。挡掉「客户那一轮扫码器没写、把上一轮的旧 txt 误用了」。建议 60 秒。

### A 策略（最简单）

**结束时直接按 mtime 取最新**。无保险。调试用，生产慎用。

## 同名去重

**默认关闭**。开启后逻辑：

- 本轮取到的扫码 txt 文件名 = 上一轮成功用过的 → 命中重名
- 主流程立即写一条 `dedupe_queued` 日志，**不阻塞下一轮检测**
- 后台异步线程开始轮询输入目录，间隔默认 100 毫秒
- 拿到一份**新文件名**（≠ 上一轮）→ 重新走渲染落盘流程
- 超过「重试最大等待秒数」（默认 5 秒）还是同名 → 写 `dedupe_timeout` 日志，**跳过本规则**（这一轮不导出文件）

适用场景：
- 客户产线节拍紧，怕扫码器偶尔卡一下生成不出新文件 → 开
- 客户产线节拍宽松、扫码器稳定 → 不用开

## 多工位场景

每个工位**各建一条独立规则**，输入目录可以不同（如 `D:/扫码器1/`、`D:/扫码器2/`），用「通道过滤」字段区分。例如：

| 规则 | 通道过滤 | 输入目录 |
|---|---|---|
| 扫码器旁路-工位1 | `0` | `D:/扫码器1/` |
| 扫码器旁路-工位2 | `1` | `D:/扫码器2/` |

## 验证 / 调试

1. **测试触发**：规则建好后点列表里的「测试」按钮，挑一条历史 cycle ID，看输出文件能不能落地、内容对不对
2. **查运行日志**：规则详情→「运行日志」Tab，能看每一轮的成功/失败/跳过原因
3. **检查 cycle 留痕**（C 策略才有）：在数据库 `detection_cycles` 表查 `external_meta` 列，能看到这一轮锁定的扫码 txt 详情

## 常见问题

**Q: 客户的扫码 txt 文件夹里堆积了几千个文件，会变慢吗？**
A: 取最新文件的 `glob` 扫描目录 + 排序操作，对 1 万以内文件几乎无感（< 10ms）。客户最好定期归档/清理旧 txt。

**Q: 扫码 txt 文件名带中文 / 空格 / 特殊字符，能处理吗？**
A: 能。helper 用 `os.path.basename()` 提取文件名，对中文/空格透明。但输出文件名经过 Jinja2 模板后会去除非法字符（`< > : " / \ | ? *` 替换为下划线）。

**Q: 扫码器还没写完，我们读到一半怎么办？**
A: 开 B/C 策略 + 「稳定等待 100ms」基本能挡住。如果客户的扫码器写入特别慢（超过 200ms），调大稳定等待到 500ms 即可。

**Q: 客户希望"扫码失败时不要输出文件"，怎么做？**
A: 开「同名去重」+ 最大年龄设置较短（如 5 秒）。如果扫码器没写新文件，超期被拒，规则会跳过本周期。

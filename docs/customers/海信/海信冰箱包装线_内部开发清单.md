## ① 人脸识别终端集成（外购设备）

- **现状**：系统无人脸能力；有「当前操作员/当前登录用户」概念（落 current_user.json / current_operator.json）。
- **目标**：员工上岗刷脸 → 识别身份 → 自动设为该工位当前操作员 → 识别通过才允许开始检测。
- **方向（已定）**：**购买第三方人脸识别设备/一体机集成**，不自研算法。
- **技术要点**：
  1. 设备选型关注「识别结果输出方式」：优先 HTTP 回调 / SDK / TCP 推送（拿到 员工工号/ID），慎选只有继电器/Wiegand 门禁信号的（拿不到具体是谁）。
  2. 新增一个对接服务/端点：接收人脸设备识别结果 → 映射到系统用户/操作员 → 调用现成的「设置当前操作员 / 登录」逻辑。
  3. 人脸库与系统用户/操作员建立映射表（人脸设备里的人员 ID ↔ 系统 user/operator）。
  4. 「识别通过才放行检测」：在开始检测入口加门禁判断（无有效当前操作员时拒绝 start detection，或仅 monitor 不计数）。
- **依赖**：设备到货 + 厂商接口文档。
- **难点**：现场光照/口罩/角度准确率；多工位是每工位一台还是班组共用一台。
- **工作量**：中（设备对接 3-5 人天 + 联调）。
- **验证**：刷脸→看当前操作员是否正确切换→检测记录 operator 是否绑定正确。

## ② MES 反向查询适配器（序列号 → 冰箱型号）

- **现状**：MES 对接是**只出不进**（mes_gateway 只推送，5 个适配器都是发送方向）。
- **目标**：扫到序列号 → 向客户 MES 发查询 → 拿到该序列号对应的冰箱型号/标签种类。
- **技术要点**：
  1. 新增「MES 查询适配器」（入方向），与现有推送适配器并列；支持 HTTP GET/POST 查询、或数据库直连/中间表轮询（看客户 MES 能力）。
  2. 查询触发点：扫码成功事件 → 拿序列号调查询 → 缓存结果到该冰箱 ID。
  3. 容错：MES 查不到/超时的兜底策略（重试、降级为人工选型号、或判可疑）。
- **依赖**：**客户必须提供查询接口**（协议、字段、鉴权）——这是外部强依赖，需尽早确认。
- **难点**：客户 MES 接口规范不确定性最大。
- **工作量**：中（适配器 3-5 人天，主要看客户接口）。
- **验证**：扫一个已知序列号→能正确返回型号。

## ③ 护角按型号动态切换检测

- **现状**：检测的期望目标在项目配置里是静态的（一个项目一套期望步骤/标签）。
- **目标**：凭 ② 拿到的型号，**运行时把第四/五工位的期望护角目标切到对应型号**；漏装/放错型号判 NG。
- **技术要点**：
  1. 维护「冰箱型号 ↔ 前护角型号 / 后护角型号」对照表（系统内配置或由 MES 直接给护角型号）。
  2. 运行时按冰箱 ID/型号动态设置下游工位的期望检测目标（可借项目多配置切换，或运行时覆盖 steps_config 期望标签）。
  3. 模型要能区分护角型号：单模型多类别，或按型号切模型/切标签。
  4. 不匹配判定走现成的「期望未达成 → NG」。
- **依赖**：② 的型号结果；分型号样本与模型。
- **难点**：护角型号数量、外观差异是否足够模型区分；动态切换与检测周期时序对齐（别切晚了检错件）。
- **工作量**：大（动态切换逻辑 5-8 人天 + 建模调参另计）。
- **验证**：不同型号冰箱过站→期望护角是否正确切换→放错型号能否报 NG。

## ④ 全线协调追溯中枢（六实例串联）★核心

- **现状**：六实例是独立进程，互不通信；有集群（cluster_collector）和工件队列基础可借鉴。
- **目标**：一个中枢服务，负责：
  - 冰箱 ID **队列**管理（先进先出，每台一个 ID）；
  - 把扫码拿到的序列号 + 型号 **下发**给后续工位；
  - 汇集六工位对同一 ID 的检测状态 / NG；
  - 支撑 ⑤ NG 回溯、⑦ 视频按序列号聚合、⑧ 大屏聚合。
- **技术要点**：
  1. 选型：扩展现有 cluster 汇总能力，或新增一个轻量协调服务（建议独立进程 + 各实例 HTTP/消息上报）。
  2. 定义实例间协议：冰箱 ID 入队、型号下发、工位状态上报、NG 广播。
  3. 解决时序：冰箱在产线上的物理顺序与各实例检测完成顺序的对齐（队列锚定）。
  4. 容错：某实例掉线/重启时队列与状态不丢。
- **依赖**：无外部依赖，但是后续 ⑤⑦⑧ 的地基。
- **难点**：**本项目工程量与风险最大项**；分布式状态一致性、时序对齐。
- **工作量**：大（10-15 人天起，建议先做 PoC）。
- **验证**：模拟六台冰箱依次过六工位，ID/型号/状态在中枢正确串联。

## ⑤ 跨工位 NG 回溯确认重做

- **现状**：人工确认重做（require_ack/ack-event）是**单实例内**的，无法跨工位。
- **目标**：后道工位判 NG → 凭序列号定位 → 在相关工位同步弹「确认重做」提示。
- **技术要点**：
  1. NG 事件经 ④ 中枢广播到目标工位实例。
  2. 目标实例进入人工确认阻塞态（复用现成 require_ack 机制）。
  3. 明确业务规则：在「当前报 NG 工位」弹框，还是回退「上一道工序」弹框（待客户确认）。
- **依赖**：④ 中枢。
- **难点**：回溯目标定义 + 跨实例触发阻塞态的可靠性。
- **工作量**：中（依赖 ④ 后 4-6 人天）。
- **验证**：后护角工位报 NG→指定工位是否弹确认框。

## ⑥ 末工位顶部外观检查 + 顶角复检

- **现状**：单工位单检测路径；无外观缺陷检查、无复检概念。
- **目标**：第六工位同时跑 顶盖步骤监测 + 顶部外观检查 + 顶角到位复检。
- **技术要点**：
  1. 同工位叠加多检测路径（步骤监测 + 外观检测模型 + 顶角复检判定）。
  2. 外观检查需明确缺陷类型（破损/错位/脏污…）并单独建模。
  3. 顶角复检：明确复检对象（本工位顶角，还是回检前/后护角结果）。
- **依赖**：外观/复检建模需样本。
- **难点**：检查标准与样本定义；三路检测在一帧/一周期内的协调。
- **工作量**：大（逻辑 5-8 人天 + 建模另计）。
- **验证**：顶部缺陷件/顶角未到位件能否检出。

## ⑦ 录像绑序列号 + 按序列号检索

- **现状**：录像（VideoClip）按周期/工位关联，无序列号维度，无跨实例检索。
- **目标**：后三工位录像打上序列号；输入序列号 → 跨实例返回该冰箱后三工位录像。
- **技术要点**：
  1. VideoClip 增加序列号字段（改 ORM + 加 ALTER TABLE 迁移）。
  2. 录像结束时把当前冰箱 ID 写入。
  3. 统一检索入口（经 ④ 中枢聚合三实例结果）。
- **依赖**：④ 中枢（跨实例聚合）；modify-model 改 schema。
- **难点**：录像与冰箱 ID 的时序绑定（确保这段视频确属这台）。
- **工作量**：中（6-8 人天）。
- **验证**：输入序列号→拉到正确的后三工位视频。

## ⑧ 六实例汇总大屏

- **现状**：有整页覆盖大屏框架（RFC12）+ 各实例实时数据接口；无六实例聚合大屏。
- **目标**：一块大屏显示六路实时视频 + 六工位关键数据（节拍/良品/NG/在检 ID/操作员）。
- **技术要点**：
  1. 定制大屏前端（插件形式，基于 RFC12 整页覆盖框架）。
  2. 聚合六实例视频流（MJPEG）+ 数据（经 ④ 中枢或直连各实例）。
  3. 大屏作为独立展示端（同机另开窗口或单独大屏主机）。
- **依赖**：④ 中枢（数据聚合）。
- **难点**：六路视频流同时拉取的性能；布局与刷新。
- **工作量**：中（8-12 人天）。
- **验证**：大屏六路视频流畅 + 数据实时准确。

## ⑨ 物理确认按钮接入

- **现状**：确认重做已有接口（ack-event）；有外部设备/串口接入能力。
- **目标**：物理按钮按下 → 调用 ack-event 解除阻塞、重做本周期。
- **技术要点**：按钮接串口/IO 或网络 → 监听到按下 → 调 ack-event（带 channel）。
- **依赖**：按钮硬件。
- **难点**：小。
- **工作量**：小（1-2 人天）。
- **验证**：按按钮→当前阻塞态解除、周期重置。

## ⑩ 多渠道告警推送（APP / 短信 / 呼麦机 / 电话）

- **现状**：异常告警目前是现场声光 + MES 上报；无手机端/短信/对讲机推送。
- **目标**：不合格结果（工位/结论/照片/视频片段/语音）除上报 MES 外，推送到手机APP/平台APP、短信，并通过呼麦机（对讲机）语音播报、可拨打电话。
- **技术要点**：
  1. 移动端 APP（或对接客户已有平台）：接收推送、查看不合格信息/照片/视频片段。短信走第三方短信网关；电话走语音网关。
  2. 呼麦机：多为对讲机系统（如 POC 公网对讲），需对接其播报接口/网关，把告警转语音播到指定群组。
  3. 触发点：NG 事件 → 打包（工位+结论+截图+短视频+语音）→ 多渠道分发服务。短视频需从该周期录像裁剪。
- **依赖**：短信/语音/对讲机网关；APP 开发或客户平台接口。
- **难点**：短视频裁剪与分发体积；呼麦机网关协议不统一。
- **工作量**：大（APP + 分发服务 8-15 人天，按渠道增减）。

## ⑪ 自学习闭环（指定置信度区间导出帧 → 训练软件迁移学习）

- **现状**：检测程序无"按置信度区间导出帧"能力；训练软件（Yan_biaozhu / YOLO Vision Platform）已具标注+训练+迁移学习基础。
- **目标**：检测中按指定置信度区间导出帧图（难例/边界样本）→ 导入训练软件做正负样本迁移学习 → 模型持续增强，应对换人/换护角颜色型号。
- **技术要点**：
  1. 检测端新增"按置信度区间采样导出帧"开关（如导出 0.4-0.7 区间的可疑帧）。
  2. 导出帧 + 上下文（工位/序列号/判定）打包，对接训练软件数据集导入。
  3. 迁移学习后产出新模型，回灌检测端（见 ⑫）。
- **依赖**：⑫ 互联通道。
- **难点**：采样策略避免数据爆炸；正负样本自动/半自动标注。
- **工作量**：中（检测端采样 3-5 人天 + 训练软件对接）。

## ⑫ 训练软件 ↔ 检测程序互联（天军生态）

- **现状**：检测程序（本系统）与训练软件（C#/WinUI3）是两个独立产品，无打通。
- **目标**：天军产品生态互联——模型、样本、数据在检测程序与训练软件间流转，未来扩展到更多天军产品。
- **技术要点**：定义产品间互联协议/接口（模型下发、样本回传、版本管理）；可做一个轻量"天军生态总线/账号体系"。
- **依赖**：两产品都要开对接口。
- **难点**：跨技术栈（Python/FastAPI ↔ C#/.NET）协议设计；模型版本/兼容管理。
- **工作量**：大（生态打通是战略级，建议分阶段）。

## ⑬ 手势 / 关键点检测辅助（目标检测为主）

- **现状**：检测以目标检测为主；v3.8.0 已有"二段管线（MediaPipe 手部）"框架基础 + 训练软件支持关键点/骨骼标注。
- **目标**：目标检测为主 + 手势（人体/手部关键点）检测为辅，提升"动作做没做、规不规范"的判定精度。
- **技术要点**：在现有二段管线基础上接入关键点检测，与目标检测结果融合判定动作。
- **依赖**：关键点模型/样本。
- **难点**：双引擎结果融合规则；性能（多一路推理）。
- **工作量**：中-大（融合逻辑 + 建模）。

## ⑭ 在岗 / 放行控制（全员登录放行 + 离岗登出 + 单工位开关）

- **现状**：有账号/操作员体系；无"全员登录才放行""离岗自动登出""单工位检测开关联动人脸"这套产线放行控制。
- **目标**：
  - 六工位全部人脸登录后产线才放行；任一未登录则强制停线。
  - 员工离岗超时（如 10min）自动登出，需重新刷脸。
  - 可单独关闭某工位检测，关闭后该工位免人脸登录、不影响其余工位放行。
- **技术要点**：协调中枢统一管理六工位在岗/登录状态 + 放行闸门；离岗判定（结合人脸终端心跳或工位画面无人）。
- **依赖**：④ 协调中枢、① 人脸终端。
- **难点**：放行闸门与产线 PLC 联动；离岗判定准确性。
- **工作量**：中（依赖 ④ 后 4-6 人天）。

## 一、关键外部依赖（需尽早锁定）

1. **客户 MES 查询接口**（②）——协议/字段/鉴权，外部强依赖，最可能拖进度。
2. **人脸识别设备选型 + 接口**（①）——优先能输出"具体是谁"的设备。
3. **护角型号清单 + 分型号样本**（③⑥）——建模前置。
4. **工控机 GPU 配置**——六路推理压测，决定是否升级硬件/合并工位。

## 二、建议开发顺序

1. PoC：④ 协调中枢 + GPU 六路压测 + ② MES 连通（三大高风险先验证）
2. ⑨ 按钮 + 单工位现成功能闭环（快出可演示成果）
3. ② + ③ 扫码-MES-护角联动（核心难点）
4. ⑤ + ⑦ 跨工位 NG 回溯 + 录像追溯（依赖 ④）
5. ① 人脸 + ⑧ 大屏 + ⑥ 末工位复检（外围与展示）
6. 现场建模调参验收

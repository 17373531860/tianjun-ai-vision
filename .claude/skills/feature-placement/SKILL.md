# feature-placement: 新功能归位决策

> 这是 AGENTS.md 第三节"产品决策原则（功能分层归位）"的**可检索详细版**。每次接到"加功能"诉求时读完本 skill 再动手。

需求：$ARGUMENTS

---

## 零、一句话核心

> **接到任何"加功能"诉求，先问自己一句：**
>
> **"这是给所有客户的基础设施，还是给这一家的小众功能？"**
>
> - 基础设施 → **进主程序**（且必须给插件平台留可扩展钩子）
> - 小众变种 → **进客户专属插件**（绝不污染主程序）

如果回答这一句话已经清楚，可以跳过本 skill 直接动手。如果**不清楚**或**需要给主作者/客户解释为什么这么归位**，往下读。

## 一、五分钟决策流程

### Step 1：识别诉求类型

把诉求按下面 5 类对号入座：

| 类型 | 特征 | 例子 |
|---|---|---|
| **A. 基础设施** | 多客户都会用 / 影响检测核心通路 / 数据模型扩展 | 工位组联动结算 / 新视频源类型 / 新结算模式 |
| **B. 客户业务变种** | 仅这一家客户的业务规则 / 字段定制 / 参数定制 | 步骤耗时警告档（这家厂特殊节拍）/ 客户特殊 NG 抑制规则 |
| **C. 客户 IT 对接** | 客户自家 MES / BI / 通讯协议 | 推 ClickHouse / 企业微信通知 / 客户自家 ERP 接口 |
| **D. 主程序底层架构** | 新表 / 新字段 / 状态机分支 / 跨模块联动 | 用户系统 / per_item 模式 / last_first 模式 / 工位组 |
| **E. UI 个性化** | 客户嫌某模块碍眼 / 想隐藏 / 想换布局 / 想换主题 | 双工位左右半屏 / 隐藏报表 tab / 客户 logo |

如果一个诉求**横跨多类**（很常见），拆开看每个子项各归哪类。

### Step 2：归位决策表

| 类型 | 归位 | 立项前置 |
|---|---|---|
| **A. 基础设施** | 主程序原生 + 同时给插件平台留 hook 给变种 | 写主程序 RFC + 评估 hook 留口 |
| **B. 客户业务变种** | 客户专属插件 | 评估当前插件平台 hook / 主动 API / 配置扩展是否够用；不够则**先升级平台**再做客户插件 |
| **C. 客户 IT 对接** | 客户专属插件 | 同 B |
| **D. 主程序底层架构** | 主程序原生（必须） | 写主程序 RFC，**同时**评估给插件平台留对应 hook |
| **E. UI 个性化** | 客户专属插件（Tier 1 主题或 Tier 2 视图覆盖） | 评估插件平台 UI 扩展（slot 化）是否够用 |

### Step 3：自检反模式（**必查**）

如果你的方案命中下面任何一条 → **方案错了**，重新走 Step 1-2：

- ❌ "客户 X 急要，先在主程序加个开关默认关，不影响其他客户" → **默认关的开关也是污染**，改插件
- ❌ "插件平台还没接入这能力，先在主程序临时加，后面再迁移" → **没有'后面再迁移'**，先升级插件平台再做客户插件
- ❌ "这功能小众但通用，干脆主程序加" → 通用就所有客户都开，不通用就插件；**没有"小众但通用"**
- ❌ "这是客户改 UI，但反正在 Vue 组件里改个 v-if 也很快" → 主程序 Vue 组件加 customer_code 条件判断 = 污染最快路径
- ❌ "客户要的就是改主程序行为，不改主程序怎么实现" → 看插件平台 hook / 主动 API / Returnable 契约够不够（RFC 09/10）；不够则升级平台

### Step 4：决策留痕

立项前在以下至少一个地方写一句话**说明为什么归这一档**：

- commit message（如果是直接动手的小改）
- PR description（如果是 PR 立项）
- 对应 RFC 的"动机"节（如果新加 RFC）
- AGENTS.md / 对应 skill 的"历史踩坑"节（如果涉及边界判定）

## 二、典型案例库（项目真实案例）

### 案例 1：客户要"步骤耗时三档颜色"（v3.13 当前案例）

**诉求**：客户 hb-foo 希望每个步骤耗时显示三档颜色（OK 绿 / 警告黄 / 超时红），阈值各步骤独立可配。

**归位分析**：
- 类型识别：B（客户业务变种）+ E（UI 个性化）
- 多客户都会用？— 不会，这家厂的节拍很特殊
- 影响主程序数据模型？— 不影响（仅前端展示 + 配置）
- 现有插件平台能不能接？— 当前**不能**：没有 step 级 hook、没有步骤 cell 的 slot、没有 Project plugin_data 透传

**正确归位**：客户专属插件。但**先升级插件平台**（RFC 09 M1.1 加 step_change hook、M2.2 加 monitor.step-cell.duration slot、M3.1 加 plugin_data 透传），再做客户插件。

**反模式（错误归位）**：
- ❌ 主程序 Project 配置加"warn_duration"字段（其他客户用不到，污染 schema）
- ❌ 主程序 Monitor.vue 里 if-else 客户 code（一旦开了头停不下来）

---

### 案例 2：客户要"双工位 A NG → B 同步 NG"（v3.13 当前案例）

**诉求**：双工位场景，同一物件被两个角度同时检测，A NG → B 也 NG。

**归位分析**：
- 类型识别：D（主程序底层架构）+ A（基础设施）
- 多客户都会用？— **会**。任何"多通道复检""多角度联动"场景都用得到
- 影响主程序数据模型？— **会**（cycle 联动结算需要新概念 ChannelGroup）
- 现有插件平台能不能接？— **不能纯靠插件做**（涉及跨通道状态机协同，插件作用域是单 customer_code 不该跨通道）

**正确归位**：**主程序原生**，加 ChannelGroup 概念 + Coordinator + 4 种 settle_strategy。**同时**给插件平台留 `channel_group_settle_start/done` 两个 hook，让客户级"主从权重""复检阈值"等变种走插件。

**反模式（错误归位）**：
- ❌ 仅靠客户插件 hook 改另一通道 cycle（跨通道写权限越权，违反命名空间隔离）
- ❌ 主程序硬编码"客户 X 时双工位联动"（不通用，污染）

承载文档：`docs/plugin-system/design/10_channel_group_rfc.md`

---

### 案例 3：用户系统（v3.10.0 已落地）

**诉求**：客户希望加多角色登录系统，区分超级管理员 / 工程师 / 操作员。

**归位分析**：
- 类型识别：D（主程序底层架构）+ A（基础设施）
- 多客户都会用？— **会**，工业场景通用
- 影响主程序数据模型？— **会**（5 张新表）

**正确归位**：主程序原生。但**默认关闭**（`auth.enabled=false`），客户不开启时体验与无鉴权一致。

**反模式（错误归位）**：
- ❌ "用户系统是客户 X 要的，写成插件"（多客户都要，不该走插件）
- ❌ "默认开启所有客户都强制用"（破坏老客户体验）

正解：主程序原生 + **默认关**的总开关（与"反模式 #1（默认关开关 = 污染）"看起来矛盾但**不矛盾**：用户系统是基础设施，关闭也是基础设施的一部分；步骤警告档是客户变种，加默认关开关才是污染）。

---

### 案例 4：客户要"推数据到自家 ClickHouse"

**诉求**：客户 hb-bar 希望把所有 cycle 结果实时推到自家 ClickHouse。

**归位分析**：
- 类型识别：C（客户 IT 对接）
- 多客户都会用？— 不会，只这家有 ClickHouse
- 影响主程序数据模型？— 不影响

**正确归位**：客户专属插件。利用 RFC 09 M1.1 的 `cycle_end` hook + M1.3 的 `PluginHost.mes_push` 类主动 API。

**反模式（错误归位）**：
- ❌ 主程序 mes_gateway 加 ClickHouse adapter（特定客户的 IT 系统不该进主程序）

注意区别：如果**多个客户**都开始要"推自家数据库"，那时再评估：
- 仍然全走插件（每客户一个 adapter）
- 升级到主程序的 mes_gateway adapter 框架（已有 6 种适配器机制）— 这才算"基础设施"

---

### 案例 5：客户要"隐藏报表 tab"

**诉求**：客户嫌报表 tab 没用，希望主界面不显示。

**归位分析**：
- 类型识别：E（UI 个性化）
- 多客户都会用？— 不通用
- 影响主程序数据模型？— 不影响

**正确归位**：客户专属插件（Tier 1 主题包 `uiHidden: ['navbar.menu.report']`）。

**反模式**：
- ❌ 主程序 SystemConfig 加 `display.hide_report_tab` 开关 — 又是污染默认关开关

## 三、模糊地带的判断技巧

### 模糊点 1："听起来通用，但只一家客户提"

**问法**：等第二家客户提同样诉求时再做主程序原生改造？还是这家先做插件？

**答**：**先做插件**。"一家客户提的通用诉求"和"真正通用的诉求"是两回事。等真有两家客户都提，再考虑提升为主程序基础设施。

### 模糊点 2："改起来主程序最快"

**问法**：客户急要，写插件要先升级平台、写 manifest、签名验证全套，三天搞不定；主程序改 if-else 半天就行。

**答**：**没有这种特例**。"主程序改半天就行"的成本不是半天 — 是后续每次升级、每次新客户来都要回看这段代码、每次重构都要绕开它。**项目寿命越长，污染成本越大**。

唯一例外：**hotfix**（客户机已经挂了，先救命）— 这种情况下做主程序 hotfix 是允许的，但**必须**同时立工单跟踪"把这段 hotfix 改回插件"，否则就是永久债务。

### 模糊点 3："这次客户暂时不用插件平台，先按客户定制版本编译"

**问法**：能不能不走插件，直接在 fork 一个客户分支改主程序？

**答**：**严禁**。一旦每客户一个分支，主程序维护成本爆炸，再没法升级所有客户。"客户定制版本"必须走插件，主程序对所有客户保持一致。

### 模糊点 4："客户要的是改主程序 UI 的某个核心组件"

**问法**：客户要 Monitor 主区域完全换布局，不只是某个 cell 换颜色。

**答**：看是不是触碰**主视图功能**（不是仅仅外观）：
- 仅外观重排（位置 / 大小 / 颜色） → 客户插件 + slot 化（升 M2 平台）
- 触碰功能（删除某个核心数据展示 / 改逻辑）→ **拒绝**或建议客户提"基础设施层"诉求，由主程序原生实现

参 `design/00_overview.md` 第二节"档位 2 不能改主视图功能"边界。
